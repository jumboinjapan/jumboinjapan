# Коллектор POI с порталов Японии

**Статус: актуальный документ.** Сверен с `collect-pois.mjs` и стережётся
`npm run check:docs`: флаги здесь и флаги парсера обязаны совпадать.

Каноническая операционная инструкция — [`docs/poi-intake/runbook.md`](../../docs/poi-intake/runbook.md).
Порядок запуска, разрешения владельца, разбор отчёта и порядок действий при
сбое описаны там; здесь только то, что относится к самому коллектору.
Источники, лицензии, скоринг и стоимость каскада — в
[`docs/poi-portal-collector.md`](../../docs/poi-portal-collector.md).

## Установка

Отдельной установки нет. Зависимости ставятся один раз на весь проект:

```bash
npm ci
```

`npm ci`, а не `npm install`: он падает при рассинхроне `package-lock.json`
с `package.json`, а не переписывает лок молча.

## Запуск

```bash
# один портал, отчёт в файл
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --out tmp/osaka.json

# обкатка на первых 300 записях
node scripts/poi-portals/collect-pois.mjs --portal bodik-kyoto-tourism --limit 300

# сверка с текущей базой POI на дубли
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --existing tmp/poi-dump.json

# мониторинг: что изменилось у источника с прошлого прогона
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --monitor tmp/osaka.json
```

Тот же список печатает сама команда; равенство парсера, `--help` и этого
файла стережёт `npm run check:docs`:

```bash
node scripts/poi-portals/collect-pois.mjs --help
```

## Флаги

Неизвестный аргумент — отказ, а не предупреждение: опечатка обязана падать,
а не выполняться наполовину.

| Флаг | Что делает |
|---|---|
| `--portal <id>` | один портал из реестра |
| `--all` | все активные порталы с реализованным адаптером |
| `--limit <n>` | ограничить число записей, для обкатки |
| `--existing <file>` | JSON с текущей базой POI для сверки на дубли |
| `--monitor <file>` | сравнить с предыдущим снимком прогона |
| `--out <file>` | записать полный отчёт JSON |
| `--names <file>` | JSON `sourceKey → {nameRu, nameEn, siteCity}` |
| `--samples <n>` | сколько примеров решений попадёт в отчёт, по умолчанию 8 |
| `--help` | справка |

Формат `--existing`: массив объектов
`{ poiId, nameRu, nameEn, nameJa?, lat?, lon?, sourceKey? }`.

## Режим discovery: japan-guide

`japan-guide` — источник другого рода. Он не даёт кандидатов в POI: он
отвечает на вопрос, КАКИЕ объекты существуют, и приносит неподтверждённые
подсказки. Поэтому у него отдельный адаптер `japan-guide-html`, отдельная
таблица `DISCOVERY_ADAPTERS` и отдельная ветка в `runPortal`, срабатывающая
ДО оценки кандидатов.

```bash
# discovery-обход, отчёт в файл
node scripts/poi-portals/collect-pois.mjs --portal japan-guide --out tmp/jg.json

# что изменилось с прошлого прогона
node scripts/poi-portals/collect-pois.mjs --portal japan-guide --monitor tmp/jg.json --out tmp/jg-2.json
```

Любой режим записи или планирования с discovery-порталом в наборе отказывает
**до первого сетевого запроса**: `--write`, `--dry-write`, `--base-snapshot`,
`--model-plan`, `--model-provider-profile`, `--names`, `--existing`. Read-only
`--all` discovery-портал включает, и его отчёт лежит рядом с обычными.

### Что собирается и чего не собирается

Собирается: имя объекта с H1; связи с коллекциями и каталогом (`placements`
— вид размещения, позиция в списке, уровень рекомендации, категория); подсказки
`hours_hint`, `closed_hint`, `admission_hint`, `official_url_hint`, `name_en`.

Не собирается ничего из прозы: Intro, описания карточек, «как добраться»,
история, подписи к фотографиям, изображения. Сырые байты страниц не
сохраняются нигде.

Каждая подсказка приходит с `confidence: 'unverified'` и `verified_at: null`.
Повысить её правкой поля нечем: у перечисления ровно одно значение.
Подтверждать факты будет отдельный этап по официальным японским источникам.

`name_ja` и `name_kana` объявлены контрактом и не порождаются: японская форма
имени встречается только внутри прозы, а в байтах записана так, что принятая
политика декодирования её не восстанавливает.

### Кодировка

HTTP-заголовок и `<meta charset>` этого сайта не описывают фактические байты:
строгое декодирование по каждой из двух объявленных меток завершается
ошибкой. Разрешённые локаторы извлекаются после replacement-aware разбора и
отдельной проверки КАЖДОГО значения по закрытому алфавиту кодовых точек.
Наблюдаемая комбинация трёх сигналов зафиксирована в реестре вместе с датой
измерения; её изменение — отказ страницы до разбора, а не подбор новой
кодировки.

### robots.txt читается первым и спрашивается перед каждым обменом

`robots.txt` — первый сетевой обмен КАЖДОГО прогона. Он разбирается один раз
в неизменяемую policy, и дальше policy спрашивается перед каждым запросом:
каталог, направление, объект, цель каждого редиректа. Проверить один каталог
и считать разрешённым весь сайт — это не проверка robots, а её имитация.

Сопоставление по RFC 9309: шаблон `*` — любая последовательность, `$` в конце
— конец пути, percent-encoding нормализуется, выигрывает самое длинное
совпадение, при равной длине — `Allow`. Группы выбираются тоже по RFC:
объединяются все, совпавшие с нашим product token; `*` берётся только при
отсутствии именной группы.

Product token и заголовок разделены. В `robots.txt` мы ищем группу
`jumboinjapan-poi-discovery`; в заголовке идёт
`jumboinjapan-poi-discovery/1.0 (+https://jumboinjapan.com/contact)`.

Недоступный, негодный или запрещающий robots останавливает прогон до первого
HTML. Стандарт трактует 4xx как «можно всё» — здесь это отказ: временное
исчезновение файла остановит расписание, а не откроет обход. Редиректы для
robots не допускаются: снимок обязан ссылаться ровно на канонический адрес.

### Четыре формы ссылок, и ни одна не задаёт роль

Измерено 17.08.2026: в региональных списках 208 ссылок, из них 206 вида
`/e/eNNNN[a]?.html` и две вида `/destinations/<slug>/`. Они несут тот же
класс `dest_top_destinations__destination`, тот же набор атрибутов и лежат
вперемешку с остальными в том же контейнере: структурно неотличимы.

Обход поддерживает четыре измеренные формы:

| семейство | шаблон пути | ключ источника |
|---|---|---|
| `legacy` | `^/e/e\d+[a-z]?\.html$` | `japan-guide:eNNNN` |
| `legacySuffix` | `^/e/e\d+_(?:[a-z]+\|\d{3})\.html$` | `japan-guide:eNNNN_<suffix>` |
| `destinationRoot` | `^/destinations/<slug>/$` | `japan-guide:destinations:<slug>` |
| `destinationNested` | `^/destinations/<parent>/<leaf>\.html$` | `japan-guide:destinations:<parent>:<leaf>` |

где `<slug>` — `[a-z0-9]+(?:-[a-z0-9]+)*`. Ключ описывает ПУТЬ страницы, а не
её роль: роль определяется содержимым и может смениться независимо от адреса,
а ключ, зависящий от роли, показал бы смену роли как исчезновение одного
объекта и появление другого. Одинаковые сегменты не схлопываются:
`/destinations/nozawa-onsen/nozawa-onsen.html` даёт
`japan-guide:destinations:nozawa-onsen:nozawa-onsen`.

У `legacySuffix` измерены две закрытые ветви: строчные буквы и ровно три
цифры. Буквенная подтверждена тремя объектами, цифровая — семейством
`e3034_001…e3034_006`. `_999` проходит как граница грамматики, но живое
измерение других цифровых семейств ещё не проводилось; нестандартная
разрядность отказывает с `pathDenied`, а не нормализуется.

**Форма адреса роли НЕ несёт, и это измерено:**
`/destinations/nozawa-onsen/` — коллекция объектов,
`/destinations/motonosumi-shrine/` той же формы — объект. Правило
«`/destinations/<slug>/` = направление» измерением опровергнуто: оно записало
бы POI в направления.

Роль вычисляется по структуре для КАЖДОЙ цели, включая legacy, и хранится
единственным полем `pageEvidence.pageRole` ∈ `catalogue | collection | poi`.
Страница, проходящая обе грамматики сразу, — отказ `pageRoleAmbiguous`; не
проходящая ни одной — `pageRoleUnknown`. Обе делают снимок неполным: догадка
о более вероятной роли здесь была бы молчаливым выбором.

Ссылка, не попадающая ни в одно семейство (чужой хост, query, fragment,
percent-encoding, путь вне `/e/` и `/destinations/`), называется поимённо в
`rejected.targets` с кодом `unsupportedCatalogueLinkShape` и делает снимок
неполным.

### Три способа найти объект

`placements` дискриминированы по `kind`:

* `destinationRanking` — объект стоит карточкой в списке коллекции. Есть
  `listPosition`, `editorialLevel`, `categoryHint`; порядок коллекции
  сообщается `orderDigest`.
* `catalogueDirect` — объект указан прямо в каталоге. Все три поля
  ранжирования равны `null`, и `collectionSourceKey` — ключ каталога.
* `containerChild` — объект найден топологией: зонтичная страница
  `/e/eNNNN.html` ссылается на своих детей `/e/eNNNN_ddd.html`. Ранга сайт
  не показывает, поэтому все три поля ранжирования равны `null`, а
  `collectionSourceKey` — ключ зонтичной страницы.

Три `null`, а не значения по умолчанию: выдуманную единицу невозможно отличить
от измеренной. Порядок ведётся только для коллекций; требовать его от прямого
объекта значило бы выдумать список, которого у него нет.

**Вид размещения сверяется с видом коллекции.** `orderRecord` несёт
`collectionKind` — `ranked` либо `container`, — и поле входит в `orderDigest`.
`destinationRanking` разрешён только при `ranked`, `containerChild` — только
при `container`. Без этой сверки происхождение размещения нельзя было
проверить из снимка: достаточно было заменить вид и пересчитать отпечатки.

### Версии формата

Текущие — `poi-discovery-record/v2`, `poi-discovery-order/v2`,
`poi-discovery-snapshot/v2`; `poi-fact-lead/v1` не менялся. Формат `v1`
заморожен и по-прежнему **читается**: снимки, снятые до 20.08.2026,
проверяются правилами `v1`. Домены отпечатков выведены из версии, поэтому
байты `v1` и `v2` не совпадают ни при каких данных.

Правила `v1` не пересказаны по памяти, а сняты с опубликованного коммита
`bd8ebe6` — того самого, чей строитель эти снимки и делал. Измеренная
разница:

| что | `v1` | `v2` |
|---|---|---|
| виды размещения | `catalogueDirect`, `destinationRanking` | те же и `containerChild` |
| коды отказа страницы | 22, ни одного `pageRole*` | 25: добавлены `pageRoleAmbiguous`, `pageRoleUnknown`, `containerTopologyAmbiguous` |
| коды пропуска | 5 | 6: добавлен `unknownAdmissionLabel` |
| семейства URL | `legacy`, `destinationRoot`, `destinationNested` | те же и `legacySuffix` |
| `collectionKind` в `orderRecord` | нет | обязателен |

Отдельных исходов классификатора у `v1` не было вовсе: страница, чью роль
определить не удалось, давала один общий `structureMismatch`. Приписать
`v1` новые коды задним числом значило бы объявить старые снимки годными по
правилам, которых при их съёмке не существовало.

Разница записана один раз — в реестре `VERSION_POLICY`: спецификации
записи, порядка и снимка, набор полей порядка, виды размещения, коды отказа
страницы и карточки, коды пропуска, семейства URL, наличие `collectionKind`.
Проверяющие функции берут набор оттуда по версии САМОГО объекта, а не по
текущей константе. Списки читаемых версий тоже выведены из политики, а не
набраны рядом с ней.

«Источник один» — утверждение проверяемое, а не декларация. Каждое из
десяти полей политики портится отдельной мутацией, и каждая порча обязана
уронить набор. Поле, которого не читает ни одна проверка, свою мутацию
переживёт — так и был найден `cardRejectionCodes`: он лежал в политике, а
снимок сверялся с глобальной константой, и обе версии можно было опустошить
не уронив ни одного теста.

Заморозка проверяется чтением, а не утверждением. Фикстура
`tests/fixtures/discovery/v1-snapshot.json` построена строителем из
`bd8ebe6` (генератор сохранён рядом, `README-v1-snapshot.mjs.txt`), и
текущий код обязан её принять. Генераторы подделок лежат там же —
`README-v1-forgeries.mjs.txt` и `README-v1-forgeries-one.mjs.txt`.

Отрицательная сторона — `tests/fixtures/discovery/v1-forgeries.json`:
тринадцать снимков `v1`, у каждого поле `verdict` — что обязан сделать
читатель, и `patched` — вносилась ли заплата в копию коммита. Восемь снимков
подделаны точечной заплатой и обязаны быть отвергнуты. Один законен и обязан
приниматься — на нём держится единственное поле политики, которого подделать
нельзя, потому что коды отказа карточек у обеих версий совпадают. Ещё четыре
собраны НЕТРОНУТЫМ строителем: опубликованный `v1` принимал их сам, и это не
подделки версии, а дыры в связности. Подделки НЕ отредактированы вручную. Правка готового снимка ломает отпечаток, и такой снимок
отвергается отпечатком, а не версией: снять версионную проверку — тест всё
равно красный, только на другой строке, и проверял бы он не то. Каждая
подделка собрана строителями `bd8ebe6` с одной точечной заплатой в
перечислении `v1`, поэтому отпечатки настоящие и сходятся. Единственное,
что стоит между такой подделкой и приёмом, — проверка версии. Так `v1`
отвергает `pageRoleAmbiguous`, `pageRoleUnknown`,
`containerTopologyAmbiguous`, `unknownAdmissionLabel`, `containerChild`,
семейство `legacySuffix` и `collectionKind`.

**Семейство адреса проверяется у каждого адреса снимка, а не только у
записи.** Цель каталога попадает в снимок раньше записи и может остаться без
неё вовсе — при ограниченном охвате или при отказе. Пока проверка стояла
только у `record.url`, ограниченный снимок `v1` с целью
`/e/e5036_fish.html` проходил целиком: запись оставалась законной `legacy`,
и смотреть на цель было некому. У свидетельства каталога проверки нет
намеренно — его адрес обязан совпасть с точкой входа, которая заморожена
константой, и проверка была бы недостижима.

**Ключ без адреса проверяется так же, как адрес.** `orderRecord.order[]`,
`rejected.targets[].ref`, `rejected.pois[].ref` и
`rejected.cards[].destination` хранят ключ, а не URL, и принимали любую
строку: ограниченный снимок `v1` принял `japan-guide:e5036_fish` в порядке,
потому что записи для него нет и до проверки `record.url` дело не доходит.
Семейство берётся обратным разбором ключа `sourceKeyFamily` — из ключа
собирается кандидат-адрес, прогоняется через ту же `canonicalDiscoveryUrl`,
и ответ принимается, только если `discoverySourceKey` вернёт исходный ключ
побуквенно. Второго набора выражений нет: круг и есть проверка, и
`…e5036_fish/../e4000` его не замыкает. Исключение одно —
`unsupportedCatalogueLinkShape`, где `ref` намеренно хранит сырой адрес: ключ
из ссылки непригодной формы не строится вовсе, ради этого код и заведён.

**Отказ обязан ссылаться на то, что снимок видел.** Отвергнутый объект
обязан быть в достижимом множестве, не повторяться и не иметь записи;
отвергнутая карточка — принадлежать наблюдённой коллекции, и одна позиция
не может быть отвергнута дважды. Счётчики это не ловили: `poisFound`
считается по достижимым, а отвергнутые в них не входили, и суммы сходились
при отказе объекта `japan-guide:e9999`, которого снимок не находил.

Из этого следует и снятое: сравнение «посещено больше, чем найдено» стало
недостижимым — посещение пришпилено к сумме «записи + отказы», обе части
обязаны быть достижимы и не пересекаться. Недостижимую проверку здесь не
держат: её не убивает ни одна мутация, то есть её никто не проверяет. По той
же причине снята проверка семейства у `rejected.cards[].destination` — он и
так обязан лежать среди наблюдённых коллекций.

**Версия читается как данные, а не обращением к свойству.** `contractVersion`
берётся из собственного дескриптора: свойство, описанное accessor'ом, —
отказ. Обращение запускало бы чужой код внутри валидатора раньше любой
проверки, и один и тот же объект мог бы отдать `v1` проверяющему и `v2`
потребителю. Снимок с диска — всегда данные, поэтому геттер здесь признак
подделки, а не ограничение формата.


### Снимок, а не «что успели собрать»

Результат обхода — снимок `poi-discovery-snapshot/v2` с явными полями
`scope`, `complete` и `incompleteReasons`. `complete: true` ставится ровно
тогда, когда обход был полным и не потерял ни одной страницы. Любая потеря —
недоступное направление, отвергнутая карточка, применённый `--limit`,
нехватка бюджета — делает снимок неполным.

Мониторинг принимает только два ПОЛНЫХ снимка одинакового охвата и оба
проверяет контрактом до сравнения. Иначе страницы, до которых обход не
дошёл, читались бы как удалённые источником. Поэтому `--monitor` несовместим
с `--limit`, а негодный старый снимок даёт ненулевой исход процесса, а не
строчку в отчёте.

Снимок несёт свидетельства родительских страниц: robots, каталога и каждого
направления. Без них смена вёрстки каталога была бы неотличима от смены
состава направлений. Изменения родительских страниц идут отдельным разделом
и семантическими изменениями объектов не считаются.

### Бюджет обменов

Считаются ОБМЕНЫ по сети, а не страницы: каждый шаг редиректа и запрос
robots проходят через тот же счётчик и ту же паузу. Потолок 6000 —
ОПЕРАЦИОННЫЙ, а не верхняя граница задачи: 25 карточек измерены на ОДНОМ
направлении, и что на остальных их не 26, не доказано. При интервале 2000 мс
потолок означает до 3 часов 20 минут работы. Перед уровнем объектов бюджет
проверяется явно: если нижняя граница не помещается, уровень не начинается
вовсе.

Тело ответа читается ограниченным ридером и обрывается на первом же куске,
который переводит сумму за предел, — а не скачивается целиком, чтобы потом
быть измеренным.

### Отпечатки и мониторинг


У записи их пять, и у каждого одна роль: `leadDigest` (содержимое подсказки
без момента наблюдения), `recordDigest` (канонические поля и `omissions`),
`semanticDigest` (основание мониторинга), `pageEvidence` (байты, сырой
отпечаток, момент, диагностика кодировки) и `observationDigest` (весь
снимок). Позиция в списке в `semanticDigest` не входит: перестановка карточек
сообщается один раз на направление через `orderDigest`, а не превращается в
сообщение об изменении каждого объекта.

### Диагностический план модельной классификации

| Флаг | Что делает |
|---|---|
| `--model-plan` | локальный план: модель не вызывается, в базу ничего не пишется, ключи не нужны. Требует `--out` внутри `tmp/poi-model-plans/` |
| `--model-provider-profile <id>@<version>` | точный профиль из канонического реестра, только вместе с `--model-plan` |

`--model-provider-profile` **связывает локальный план v2 с профилем**. Это не
вызов модели: прогон по-прежнему обходит источники обычным адаптером, пишет
отчёт и ничего не отправляет провайдеру. Флаг несовместим с `--limit`:
ограничение корпуса не входит в план, и повторный запуск источников его не
воспроизведёт. Пара задаётся ровно как `id@version` — ближайшей версии,
отката и частичного совпадения нет.

Канонический профиль и таблица цены **объявлены** (`openai-responses-luna@1.0.0`,
модель `gpt-5.6-luna`), поэтому пара теперь может разрешиться. Что при этом
по-прежнему невозможно:

- `executionPermitted` остаётся `false`, пока policy источника запрещает
  обработку, — а сегодня её запрещают все двенадцать источников;
- исполнитель модельного запроса ни одним production-путём не вызывается:
  на `model-executor.mjs` нет ни одной ссылки из production-исходников;
- разрешения владельца в репозитории нет;
- реальных журналов исполнения не существует.

Профиль объявляет модель наблюдаемым алиасом со сроком сверки каталога:
после **17 сентября 2026, 00:00 JST** флаг начнёт отказывать до первого
адаптера, пока владелец не пересверит каталог новым коммитом.

`--model-plan` несовместим с любым режимом записи.

### Запись

**В Airtable по умолчанию не уходит ничего.** Без флагов записи прогон только
считает и показывает. Локальный файл при этом создаётся: его пишет `--out`, и
это выгрузка данных источника, а не запись в базу — обращаться с ней нужно
соответственно.

| Флаг | Что делает |
|---|---|
| `--write` | записать корзину import через `ingestPoiBatch` |
| `--dry-write` | полный конвейер записи против живой базы, без создания записей |
| `--base-snapshot <file>` | то же против снимка базы из файла, без токена |

`--write` требует **отдельного разрешения владельца** на каждый прогон.
Порядок получения и что делать при сбое — в
[`runbook.md`](../../docs/poi-intake/runbook.md).

Записываются кандидаты из корзины import, у которых **собралось** русское имя.
Источников три, по убыванию надёжности: файл `--names` (владелец уже выбрал
форму — она переопределяет машинную), кана источника, английское название.
`--names` обязательным не является: собранного из каны или английского
достаточно.

Запись идёт через `ingestPoiBatch`, то есть через тот же гейт, что и остальные
пути приёма: канон → идемпотентность по `Source Key` → гейт дублей и родителя
→ черновик.

Форма строки снимка для `--base-snapshot` — в
`scripts/poi-portals/lib/base-snapshot.mjs`.

## Координаты и срок их хранения

`npm run backfill:coords` берёт координаты из Wikidata (CC0, хранить можно
бессрочно) и заодно проставляет `Wikidata QID` и `Name (JA)`.
`npm run backfill:coords-google` добирает остальное из Google Places.

**У координат из Google есть срок годности.** Условия Maps Platform разрешают
хранить `place_id` бессрочно, остальное содержимое — тридцать дней. Поэтому
рядом с координатой лежит `Google Place ID`, а `npm run refresh:coords`
перечитывает координаты по нему. Не запускать этот прогон — значит хранить
чужие данные дольше разрешённого и называть это иначе.

`Name (JA)` здесь важнее координат: имена на латинице у нас и у портала
расходятся всегда, японские — почти никогда, и сверка по ним надёжнее.

## Лицензии источников

**Источник с `licence.commercial !== true` пропускается автоматически.**
Проприетарные порталы лежат в реестре как проверенные, но в прогон не
берутся, пока не решён вопрос прав.

## Добавление портала

Только запись в `registry.mjs`. Поля `verified.at` и `licence` обязательны:
непроверенный источник в реестр не попадает.

Если источник — CSV в стандарте `自治体標準オープンデータセット`, адаптер
`opendata-csv` подхватит его без правок кода: колонки читаются через таблицу
алиасов с нормализацией ширины символов. Проверено на двух несовпадающих
схемах (Осака 58 колонок, Киото 32).

Для нового класса источников — новый адаптер в `lib/` и регистрация
в `ADAPTERS` внутри `collect-pois.mjs`.

Таблиц адаптеров две, и путать их нельзя. В `ADAPTERS` живут те, кто
производит КАНДИДАТОВ в POI: их результат идёт в оценку, дедуп, очереди и
запись. В `DISCOVERY_ADAPTERS` — те, кто производит discovery-записи с
неподтверждёнными подсказками; в конвейер кандидатов они не попадают ни одним
путём.


## Что в отчёте

- `totals.autoImportable` — сколько прошло все четыре условия автоимпорта
- `totals.needsLlmCategory` — очередь на ступень 1 каскада
- `totals.volatileFieldsUnverified` — записи, чьи часы и цены публиковать нельзя
- `rejectReasons` — причины отбраковки со счётчиками
- `aiCost` — оценка стоимости прогона по фактическому корпусу
- `samples` — примеры решений, числом из `--samples`
- `all` — полный список решений по каждой записи, не только примеры

У discovery-портала отчёт другой: `mode: 'discovery'`, `meta` со счётчиками
прогона и `discovery` с записями, порядком объектов по направлениям и списком
отказов. Полей `writable`, `queues` и `all` у него нет — кандидатов он не
производит.


Последнее важно: на вопрос «почему эта точка не прошла» надо уметь отвечать
без перезапуска прогона.
