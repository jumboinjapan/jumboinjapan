# Коллектор POI с порталов Японии

**Статус: актуальный документ.** Сверен с `collect-pois.mjs` и стережётся
`npm run check:docs`: флаги здесь и флаги парсера обязаны совпадать.

Каноническая операционная инструкция — [`docs/poi-intake/runbook.md`](../../docs/poi-intake/runbook.md).
Порядок запуска, разрешения владельца, разбор отчёта и порядок действий при
сбое описаны там; здесь только то, что относится к самому коллектору.
Источники, лицензии, скоринг и стоимость каскада — в
[`docs/poi-portal-collector.md`](../../docs/poi-portal-collector.md).

## Установка

Отдельной установки нет. Зависимости ставятся один раз на весь проект:

```bash
npm ci
```

`npm ci`, а не `npm install`: он падает при рассинхроне `package-lock.json`
с `package.json`, а не переписывает лок молча.

## Запуск

```bash
# один портал, отчёт в файл
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --out tmp/osaka.json

# обкатка на первых 300 записях
node scripts/poi-portals/collect-pois.mjs --portal bodik-kyoto-tourism --limit 300

# сверка с текущей базой POI на дубли
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --existing tmp/poi-dump.json

# мониторинг: что изменилось у источника с прошлого прогона
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --monitor tmp/osaka.json
```

Тот же список печатает сама команда; равенство парсера, `--help` и этого
файла стережёт `npm run check:docs`:

```bash
node scripts/poi-portals/collect-pois.mjs --help
```

## Флаги

Неизвестный аргумент — отказ, а не предупреждение: опечатка обязана падать,
а не выполняться наполовину.

| Флаг | Что делает |
|---|---|
| `--portal <id>` | один портал из реестра |
| `--all` | все активные порталы с реализованным адаптером |
| `--limit <n>` | ограничить число записей, для обкатки |
| `--existing <file>` | JSON с текущей базой POI для сверки на дубли |
| `--monitor <file>` | сравнить с предыдущим снимком прогона |
| `--out <file>` | записать полный отчёт JSON |
| `--names <file>` | JSON `sourceKey → {nameRu, nameEn, siteCity}` |
| `--samples <n>` | сколько примеров решений попадёт в отчёт, по умолчанию 8 |
| `--max-place-lookups <n>` | потолок платных обращений к Google Places за прогон |
| `--model-execute` | исполнить подписанный план модельной классификации, § «Production-исполнение» |
| `--model-plan-file <name>` | ИМЯ исполняемого конверта `<имя>.envelope.json` в `tmp/poi-model-plans/`, только с `--model-execute` |
| `--model-approval <name>` | ИМЯ файла разрешения в `tmp/poi-model-approvals/`, только с `--model-execute` |
| `--help` | справка |

Формат `--existing`: массив объектов
`{ poiId, nameRu, nameEn, nameJa?, lat?, lon?, sourceKey? }`.

## Режим discovery: japan-guide

`japan-guide` — источник другого рода. Он не даёт кандидатов в POI: он
отвечает на вопрос, КАКИЕ объекты существуют, и приносит неподтверждённые
подсказки. Поэтому у него отдельный адаптер `japan-guide-html`, отдельная
таблица `DISCOVERY_ADAPTERS` и отдельная ветка в `runPortal`, срабатывающая
ДО оценки кандидатов.

```bash
# discovery-обход, отчёт в файл
node scripts/poi-portals/collect-pois.mjs --portal japan-guide --out tmp/jg.json

# что изменилось с прошлого прогона
node scripts/poi-portals/collect-pois.mjs --portal japan-guide --monitor tmp/jg.json --out tmp/jg-2.json
```

Любой режим записи или планирования с discovery-порталом в наборе отказывает
**до первого сетевого запроса**: `--write`, `--dry-write`, `--base-snapshot`,
`--model-plan`, `--model-provider-profile`, `--names`, `--existing`. Read-only
`--all` discovery-портал включает, и его отчёт лежит рядом с обычными.

### Что собирается и чего не собирается

Собирается: имя объекта с H1; связи с коллекциями и каталогом (`placements`
— вид размещения, позиция в списке, уровень рекомендации, категория); подсказки
`hours_hint`, `closed_hint`, `admission_hint`, `official_url_hint`, `name_en`.

Не собирается ничего из прозы: Intro, описания карточек, «как добраться»,
история, подписи к фотографиям, изображения. Сырые байты страниц не
сохраняются нигде.

Каждая подсказка приходит с `confidence: 'unverified'` и `verified_at: null`.
Повысить её правкой поля нечем: у перечисления ровно одно значение.
Подтверждать факты будет отдельный этап по официальным японским источникам.

`name_ja` и `name_kana` объявлены контрактом и не порождаются: японская форма
имени встречается только внутри прозы, а в байтах записана так, что принятая
политика декодирования её не восстанавливает.

### Кодировка

HTTP-заголовок и `<meta charset>` этого сайта не описывают фактические байты:
строгое декодирование по каждой из двух объявленных меток завершается
ошибкой. Разрешённые локаторы извлекаются после replacement-aware разбора и
отдельной проверки КАЖДОГО значения по закрытому алфавиту кодовых точек.
Наблюдаемая комбинация трёх сигналов зафиксирована в реестре вместе с датой
измерения; её изменение — отказ страницы до разбора, а не подбор новой
кодировки.

### robots.txt читается первым и спрашивается перед каждым обменом

`robots.txt` — первый сетевой обмен КАЖДОГО прогона. Он разбирается один раз
в неизменяемую policy, и дальше policy спрашивается перед каждым запросом:
каталог, направление, объект, цель каждого редиректа. Проверить один каталог
и считать разрешённым весь сайт — это не проверка robots, а её имитация.

Сопоставление по RFC 9309: шаблон `*` — любая последовательность, `$` в конце
— конец пути, percent-encoding нормализуется, выигрывает самое длинное
совпадение, при равной длине — `Allow`. Группы выбираются тоже по RFC:
объединяются все, совпавшие с нашим product token; `*` берётся только при
отсутствии именной группы.

Product token и заголовок разделены. В `robots.txt` мы ищем группу
`jumboinjapan-poi-discovery`; в заголовке идёт
`jumboinjapan-poi-discovery/1.0 (+https://jumboinjapan.com/contact)`.

Недоступный, негодный или запрещающий robots останавливает прогон до первого
HTML. Стандарт трактует 4xx как «можно всё» — здесь это отказ: временное
исчезновение файла остановит расписание, а не откроет обход. Редиректы для
robots не допускаются: снимок обязан ссылаться ровно на канонический адрес.

### Четыре формы ссылок, и ни одна не задаёт роль

Измерено 17.08.2026: в региональных списках 208 ссылок, из них 206 вида
`/e/eNNNN[a]?.html` и две вида `/destinations/<slug>/`. Они несут тот же
класс `dest_top_destinations__destination`, тот же набор атрибутов и лежат
вперемешку с остальными в том же контейнере: структурно неотличимы.

Обход поддерживает четыре измеренные формы:

| семейство | шаблон пути | ключ источника |
|---|---|---|
| `legacy` | `^/e/e\d+[a-z]?\.html$` | `japan-guide:eNNNN` |
| `legacySuffix` | `^/e/e\d+_(?:[a-z]+\|\d{3})\.html$` | `japan-guide:eNNNN_<suffix>` |
| `destinationRoot` | `^/destinations/<slug>/$` | `japan-guide:destinations:<slug>` |
| `destinationNested` | `^/destinations/<parent>/<leaf>\.html$` | `japan-guide:destinations:<parent>:<leaf>` |

где `<slug>` — `[a-z0-9]+(?:-[a-z0-9]+)*`. Ключ описывает ПУТЬ страницы, а не
её роль: роль определяется содержимым и может смениться независимо от адреса,
а ключ, зависящий от роли, показал бы смену роли как исчезновение одного
объекта и появление другого. Одинаковые сегменты не схлопываются:
`/destinations/nozawa-onsen/nozawa-onsen.html` даёт
`japan-guide:destinations:nozawa-onsen:nozawa-onsen`.

У `legacySuffix` измерены две закрытые ветви: строчные буквы и ровно три
цифры. Буквенная подтверждена тремя объектами, цифровая — семейством
`e3034_001…e3034_006`. `_999` проходит как граница грамматики, но живое
измерение других цифровых семейств ещё не проводилось; нестандартная
разрядность отказывает с `pathDenied`, а не нормализуется.

**Форма адреса роли НЕ несёт, и это измерено:**
`/destinations/nozawa-onsen/` — коллекция объектов,
`/destinations/motonosumi-shrine/` той же формы — объект. Правило
«`/destinations/<slug>/` = направление» измерением опровергнуто: оно записало
бы POI в направления.

Роль вычисляется по структуре для КАЖДОЙ цели, включая legacy, и хранится
единственным полем `pageEvidence.pageRole` ∈ `catalogue | collection | poi`.
Страница, проходящая обе грамматики сразу, — отказ `pageRoleAmbiguous`; не
проходящая ни одной — `pageRoleUnknown`. Обе делают снимок неполным: догадка
о более вероятной роли здесь была бы молчаливым выбором.

Ссылка, не попадающая ни в одно семейство (чужой хост, query, fragment,
percent-encoding, путь вне `/e/` и `/destinations/`), называется поимённо в
`rejected.targets` с кодом `unsupportedCatalogueLinkShape` и делает снимок
неполным.

### Три способа найти объект

`placements` дискриминированы по `kind`:

* `destinationRanking` — объект стоит карточкой в списке коллекции. Есть
  `listPosition`, `editorialLevel`, `categoryHint`; порядок коллекции
  сообщается `orderDigest`.
* `catalogueDirect` — объект указан прямо в каталоге. Все три поля
  ранжирования равны `null`, и `collectionSourceKey` — ключ каталога.
* `containerChild` — объект найден топологией: зонтичная страница
  `/e/eNNNN.html` ссылается на своих детей `/e/eNNNN_ddd.html`. Ранга сайт
  не показывает, поэтому все три поля ранжирования равны `null`, а
  `collectionSourceKey` — ключ зонтичной страницы.

Три `null`, а не значения по умолчанию: выдуманную единицу невозможно отличить
от измеренной. Порядок ведётся только для коллекций; требовать его от прямого
объекта значило бы выдумать список, которого у него нет.

**Вид размещения сверяется с видом коллекции.** `orderRecord` несёт
`collectionKind` — `ranked` либо `container`, — и поле входит в `orderDigest`.
`destinationRanking` разрешён только при `ranked`, `containerChild` — только
при `container`. Без этой сверки происхождение размещения нельзя было
проверить из снимка: достаточно было заменить вид и пересчитать отпечатки.

### Граф коллекций, а не два уровня

**Измерено 21.08.2026 первым полным обходом.** Карточка внутри ранжированной
коллекции ведёт не обязательно на объект. Из 1170 «объектов» того обхода 29
оказались коллекциями: 28 каталог уже классифицировал сам, и второй запрос
отверг fetch-boundary кодом `urlRepeated`; двадцать девятая — `e5041` —
коллекция, которой среди 208 целей каталога нет вовсе, и она разобралась
сломанным объектом. Настоящий уникальный корпус — **1141** объект.

Прежний обход держал уровни: каталог даёт цели, коллекция даёт карточки,
карточка — объект. Комментарий в коде прямо утверждал, что вложенная
коллекция «пришла бы целью каталога или не пришла бы вовсе». Измерение это
опровергло.

Теперь обход — **детерминированный BFS по графу**. Узел — страница; ребро —
карточка ранжированного списка либо ребёнок зонтичной страницы. Держатся
пять инвариантов:

1. один GET и один разбор на канонический URL — единственный владелец кэша
   узлов, второго места, где можно позвать сеть, в обходе нет;
2. роль решает СТРАНИЦА, а не позиция ссылки;
3. коллекция никогда не попадает в очередь объектов;
4. объект нескольких родителей строится один раз и сохраняет ВСЕ привязки;
5. цикл `A → B → A` — обычное ребро: страница уже посещена, второго запроса
   нет. Граница `urlRepeated` при этом НЕ ослаблена — автомат её просто не
   зовёт.

Страница, на которую сослалась коллекция и чью роль установить не удалось,
уходит в отдельный канал `rejected.nodes` с ключом, происхождением и кодом.
Сводить её к `rejected.pois` нельзя: роль как раз и неизвестна, а отказ
объекта утверждал бы, что она измерена.

### Версии формата

Текущие — `poi-discovery-record/v2`, `poi-discovery-order/v3`,
`poi-discovery-snapshot/v3`; `poi-fact-lead/v1` не менялся. Форматы `v1` и
`v2` заморожены и по-прежнему **читаются**: снимок проверяется теми
правилами, по которым построен. Домены отпечатков выведены из версии, поэтому
байты трёх версий не совпадают ни при каких данных.

**Версия записи НЕ поднята до `v3` намеренно.** Формат записи не изменился ни
полем, ни перечислением; поднятая версия объявила бы несовместимыми байты,
которые совпадают. То, что два формата снимка ссылаются на один формат
записи и не разошлись в правилах для неё, проверяется исполнением: сборка
указателя `POLICY_BY_RECORD_SPEC` роняет модуль, если правила разошлись.

Правила `v1` не пересказаны по памяти, а сняты с опубликованного коммита
`bd8ebe6` — того самого, чей строитель эти снимки и делал. Измеренная
разница:

| что | `v1` | `v2` |
|---|---|---|
| виды размещения | `catalogueDirect`, `destinationRanking` | те же и `containerChild` |
| коды отказа страницы | 22, ни одного `pageRole*` | 25: добавлены `pageRoleAmbiguous`, `pageRoleUnknown`, `containerTopologyAmbiguous` |
| коды пропуска | 5 | 6: добавлен `unknownAdmissionLabel` |
| семейства URL | `legacy`, `destinationRoot`, `destinationNested` | те же и `legacySuffix` |
| `collectionKind` в `orderRecord` | нет | обязателен |

Разница `v2` → `v3` — измерение 21.08.2026:

| что | `v2` | `v3` |
|---|---|---|
| порядок коллекции | `order` — список ключей объектов | `items` — последовательность `{role, sourceKey}`, роль входит в `orderDigest` |
| свидетельства коллекций | только `catalogueTargetEvidence` | и `nestedCollectionEvidence` — коллекции ниже каталога |
| каналы отказа | `targets`, `cards`, `pois` | те же и `nodes` — узел графа с неустановленной ролью |
| счётчик коллекций | одно `collectionsFound` | `catalogueCollectionsFound` и `nestedCollectionsFound` |
| коды отказа страницы | 25 | 26: добавлен `roleFamilyMismatch` |
| причины неполноты | 8, среди них `budgetInsufficient` | 9: без `budgetInsufficient` и без `poiFetchFailed`, зато с `nodeFetchFailed` и `nodeStructureMismatch` |
| счётчик попыток | `poisVisited` | `recordsAttempted` |
| нижняя граница обменов | нет | выводится из состава снимка |
| потолки обхода | не записываются | `networkPolicy` в снимке и в его отпечатке |

**`poisVisited` стал `recordsAttempted`, потому что имя перестало описывать
величину.** У `v1` и `v2` посещение страницы объекта и попытка построить
запись были одним событием: предел резал список ДО получения страниц. В графе
страница объекта получена ещё на классификации, и «посещено 50» при 1141
полученной странице означало бы прямо обратное правде. Величина та же —
сколько раз обход пытался построить запись; имя приведено к ней.

**Число обменов у `v3` снизу ограничено самим снимком:**

```
2 + свидетельств целей каталога
  + свидетельств вложенных коллекций
  + достижимых объектов вне прямых
  + отказов целей ПОСЛЕ обмена
  + отказов узлов ПОСЛЕ обмена
```

Неравенство, а не равенство: каждый шаг редиректа проходит через тот же
счётчик. К `v1` и `v2` граница неприменима и применяться не должна — у них
`--limit` действительно экономил сеть, и снимок canary честно объявлял 259
обменов при 1170 найденных объектах. Проверено аудитом 24.08.2026: тот же
снимок, объявленный `v3`, контракт принимал, хотя физически необходимо было
1322 обмена — разрыв в 1063.

**Полученная и отвергнутая страница тоже стоила обмена.** Первая редакция
границы считала только успешные свидетельства, и аудит 24.08.2026 предъявил
через production builders два снимка, которые она пропускала: цель, отвергнутая
с `statusDenied`, объявляла 4 обмена при физическом минимуме 5, а отвергнутый
узел графа — 3 при минимуме 4. Оба принимались.

**Код отказа стадию обмена НЕ определяет.** Вторая редакция классифицировала
отказы одним глобальным списком кодов и оказалась обходима редиректом.
`canonicalDiscoveryUrl` действительно бросает `urlNotCanonical` до запроса — но
`fetchHtmlPage` зовёт ту же функцию ВТОРОЙ раз, для `Location` уже полученного
3xx-ответа. Настоящий обход дал 7 обменов и отвергнутую цель с этим кодом;
снимок, объявивший 6, контракт принимал. Один код, две разные стадии.

Поэтому классификация снимается с ПУТИ ПОТРЕБИТЕЛЯ и у каждого канала своя:

| канал | досетевые исходы | почему остальные — после обмена |
|---|---|---|
| `rejected.targets` | `networkBudgetExhausted`, `unsupportedCatalogueLinkShape` | адрес цели канонизирован ещё в `parseCatalogue`, а негодная ссылка уходит отдельным кодом; значит любой код канонизации пришёл из `Location` после 3xx. `urlRepeated` — тем же путём: кэш узлов не даёт повторить исходный запрос |
| `rejected.nodes` | `networkBudgetExhausted` | то же рассуждение; `unsupportedCatalogueLinkShape` у узла НЕПРЕДСТАВИМ и отвергается отдельной проверкой |
| `rejected.pois` | — | в границу не входят вовсе: отвергнутый объект обязан лежать в достижимом множестве, его страница уже посчитана слагаемым «достижимых объектов вне прямых». Прибавить их значило бы посчитать один обмен дважды |

Списки живут в политике версии (`preNetworkRejectionCodes`), у замороженных
`v1`/`v2` это `null`, а не пустая таблица: пустая означала бы «все отказы после
обмена», то есть действующее правило, применённое задним числом.

Направление fail-closed: код, забытый в списке, будет сочтён состоявшимся
обменом и ПОДНИМЕТ границу, то есть отвергнет снимок. Обратное направление при
забытом коде границу бы опустило и пропустило подделку.

**Остаток закрывает не классификация, а потолок в снимке.**
`networkBudgetExhausted` бывает и на шаге редиректа — тогда обмен состоялся, а
слагаемое не прибавлено. Прежняя редакция оценивала это как «не больше одного
обмена» и была НЕВЕРНА: одна цель успевает получить до `maxRedirects` ответов
3xx прежде, чем упереться в потолок. Аудит 25.08.2026 предъявил это настоящим
обходом при `maxNetworkRequests` = 4: robots, каталог и два 302 первой цели —
четыре обмена; все три цели отвергнуты кодом `networkBudgetExhausted`, состав
снимка требовал всего двух, и снимок с объявленными двумя принимался.

Считать этот код состоявшимся обменом всё равно нельзя: тогда честный снимок,
у которого бюджет кончился до первого запроса цели, отвергался бы как подделка.
Поэтому `v3` носит в себе `networkPolicy`:

```
networkPolicy: { maxNetworkRequests, maxRedirects }
```

`maxNetworkRequests` не меньше единицы: обход, которому не разрешён ни один
обмен, не получит даже `robots.txt`. `maxRedirects` не меньше НУЛЯ — ноль это
законный режим «за редиректами не ходить», в котором первый же 3xx отвергает
цель кодом `redirectLimit`. Отрицательное значение невозможно: это не режим.

Поле входит в `snapshotDigest` — подогнать бюджет под счётчик после прогона
нельзя, — и даёт два безусловных правила:

- `networkRequests <= maxNetworkRequests` — обход не мог потратить больше
  собственного бюджета;
- при ЛЮБОМ `networkBudgetExhausted` (у цели или у узла) —
  `networkRequests === maxNetworkRequests`: бюджет исчерпан ровно тогда, когда
  счётчик дошёл до потолка, так его и проверяет `pacer.take`.

Вместе с нижней границей это оставляет для утаивания ноль обменов: снимок,
объявивший исчерпание, обязан объявить и весь бюджет. Потолки записывает сам
обход из тех `limits`, под которыми шёл, — прогон с урезанным бюджетом пишет
свой, а не значение по умолчанию.

**Чего это НЕ доказывает.** Что объявленный потолок — тот самый, под которым
шёл обход: настройка прогона снимку не принадлежит. Она защищена от подмены
после прогона отпечатком, а сверять её с `FETCH_LIMITS` — дело операционного
потребителя.

**Офлайн-приёмка canary объявлена `v1`/`v2`-only.** Её условия — буквально
операционная цель этапа 10c: обход с `--limit 50` под потолком 300 обменов.
В `v3` предел сеть не экономит, поэтому ограниченный обход графа стоит
столько же, сколько полный, и под этот потолок нынешний корпус не помещается
ни при каких данных. Операционная цель для `v3` владельцем не задана, и
подгонять формулу — значило бы выдать собственный критерий за согласованный;
приёмка отказывает именованным кодом `unsupportedSnapshotVersion`. Целостность
снимка при этом проверяется строже прежнего: нижняя граница обменов живёт в
контракте и действует на КАЖДЫЙ снимок `v3`, а не только на canary.

`order` не дополнен `items`, а **заменён** им: два поля об одной
последовательности разошлись бы на один элемент молча, и отпечаток покрыл бы
только одну из копий. По той же причине не перенесено имя `collectionsFound`:
у него не было определения, а в графе 150 коллекций каталога плюс одна
вложенная — это не «151 цель каталога».

`budgetInsufficient` и `poiFetchFailed` из `v3` убраны не для красоты, а
потому что породить их граф не может. Нехватка бюджета стала отказом
конкретного узла `networkBudgetExhausted`; страница объекта к моменту
построения записи уже получена, поэтому сетевого отказа объекта не бывает.
Причина, которую формат не может произвести, — это объявленное состояние,
которого нет.

Отдельных исходов классификатора у `v1` не было вовсе: страница, чью роль
определить не удалось, давала один общий `structureMismatch`. Приписать
`v1` новые коды задним числом значило бы объявить старые снимки годными по
правилам, которых при их съёмке не существовало.

Разница записана один раз — в реестре `VERSION_POLICY`: спецификации записи,
порядка и снимка, наборы ключей порядка, снимка и счётчиков, каналы отказа,
виды размещения, коды отказа страницы и карточки, коды пропуска, причины
неполноты, семейства URL, наличие `collectionKind`. Проверяющие функции берут
набор оттуда по версии САМОГО объекта, а не по текущей константе. Списки
читаемых версий и поле, которым формат хранит последовательность, тоже
выведены из политики, а не набраны рядом с ней.

«Источник один» — утверждение проверяемое, а не декларация. Каждое поле
политики портится отдельной мутацией, и каждая порча обязана уронить набор. Поле, которого не читает ни одна проверка, свою мутацию
переживёт — так и был найден `cardRejectionCodes`: он лежал в политике, а
снимок сверялся с глобальной константой, и обе версии можно было опустошить
не уронив ни одного теста.

Заморозка проверяется чтением, а не утверждением. Фикстура
`tests/fixtures/discovery/v1-snapshot.json` построена строителем из
`bd8ebe6` (генератор сохранён рядом, `README-v1-snapshot.mjs.txt`), и
текущий код обязан её принять. Генераторы подделок лежат там же —
`README-v1-forgeries.mjs.txt` и `README-v1-forgeries-one.mjs.txt`.

Отрицательная сторона — `tests/fixtures/discovery/v1-forgeries.json`:
тринадцать снимков `v1`, у каждого поле `verdict` — что обязан сделать
читатель, и `patched` — вносилась ли заплата в копию коммита. Восемь снимков
подделаны точечной заплатой и обязаны быть отвергнуты. Один законен и обязан
приниматься — на нём держится единственное поле политики, которого подделать
нельзя, потому что коды отказа карточек у обеих версий совпадают. Ещё четыре
собраны НЕТРОНУТЫМ строителем: опубликованный `v1` принимал их сам, и это не
подделки версии, а дыры в связности. Подделки НЕ отредактированы вручную. Правка готового снимка ломает отпечаток, и такой снимок
отвергается отпечатком, а не версией: снять версионную проверку — тест всё
равно красный, только на другой строке, и проверял бы он не то. Каждая
подделка собрана строителями `bd8ebe6` с одной точечной заплатой в
перечислении `v1`, поэтому отпечатки настоящие и сходятся. Единственное,
что стоит между такой подделкой и приёмом, — проверка версии. Так `v1`
отвергает `pageRoleAmbiguous`, `pageRoleUnknown`,
`containerTopologyAmbiguous`, `unknownAdmissionLabel`, `containerChild`,
семейство `legacySuffix` и `collectionKind`.

**Семейство адреса проверяется у каждого адреса снимка, а не только у
записи.** Цель каталога попадает в снимок раньше записи и может остаться без
неё вовсе — при ограниченном охвате или при отказе. Пока проверка стояла
только у `record.url`, ограниченный снимок `v1` с целью
`/e/e5036_fish.html` проходил целиком: запись оставалась законной `legacy`,
и смотреть на цель было некому. У свидетельства каталога проверки нет
намеренно — его адрес обязан совпасть с точкой входа, которая заморожена
константой, и проверка была бы недостижима.

**Ключ без адреса проверяется так же, как адрес.** `orderRecord.order[]`,
`rejected.targets[].ref`, `rejected.pois[].ref` и
`rejected.cards[].destination` хранят ключ, а не URL, и принимали любую
строку: ограниченный снимок `v1` принял `japan-guide:e5036_fish` в порядке,
потому что записи для него нет и до проверки `record.url` дело не доходит.
Семейство берётся обратным разбором ключа `sourceKeyFamily` — из ключа
собирается кандидат-адрес, прогоняется через ту же `canonicalDiscoveryUrl`,
и ответ принимается, только если `discoverySourceKey` вернёт исходный ключ
побуквенно. Второго набора выражений нет: круг и есть проверка, и
`…e5036_fish/../e4000` его не замыкает. Исключение одно —
`unsupportedCatalogueLinkShape`, где `ref` намеренно хранит сырой адрес: ключ
из ссылки непригодной формы не строится вовсе, ради этого код и заведён.

**Отказ обязан ссылаться на то, что снимок видел.** Отвергнутый объект
обязан быть в достижимом множестве, не повторяться и не иметь записи;
отвергнутая карточка — принадлежать наблюдённой коллекции, и одна позиция
не может быть отвергнута дважды. Счётчики это не ловили: `poisFound`
считается по достижимым, а отвергнутые в них не входили, и суммы сходились
при отказе объекта `japan-guide:e9999`, которого снимок не находил.

Из этого следует и снятое: сравнение «посещено больше, чем найдено» стало
недостижимым — посещение пришпилено к сумме «записи + отказы», обе части
обязаны быть достижимы и не пересекаться. Недостижимую проверку здесь не
держат: её не убивает ни одна мутация, то есть её никто не проверяет. По той
же причине снята проверка семейства у `rejected.cards[].destination` — он и
так обязан лежать среди наблюдённых коллекций.

**Версия читается как данные, а не обращением к свойству.** `contractVersion`
берётся из собственного дескриптора: свойство, описанное accessor'ом, —
отказ. Обращение запускало бы чужой код внутри валидатора раньше любой
проверки, и один и тот же объект мог бы отдать `v1` проверяющему и `v2`
потребителю. Снимок с диска — всегда данные, поэтому геттер здесь признак
подделки, а не ограничение формата.


### Снимок, а не «что успели собрать»

Результат обхода — снимок `poi-discovery-snapshot/v3` с явными полями
`scope`, `complete` и `incompleteReasons`. `complete: true` ставится ровно
тогда, когда обход был полным и не потерял ни одной страницы. Любая потеря —
недоступная цель каталога, неклассифицированный узел графа, отвергнутая
карточка, применённый `--limit` — делает снимок неполным.

Мониторинг принимает только два ПОЛНЫХ снимка одинакового охвата и оба
проверяет контрактом до сравнения. Иначе страницы, до которых обход не
дошёл, читались бы как удалённые источником. Поэтому `--monitor` несовместим
с `--limit`, а негодный старый снимок даёт ненулевой исход процесса, а не
строчку в отчёте.

Снимок несёт свидетельства родительских страниц: robots, каталога, каждой
цели каталога и каждой вложенной коллекции. Без них смена вёрстки каталога
была бы неотличима от смены состава направлений. Изменения родительских
страниц идут отдельным разделом и семантическими изменениями объектов не
считаются.

**Мониторинг наблюдает ВЕСЬ граф, а не только каталог и его цели.** Разделов
теперь шесть: семантика объектов, наблюдение объектов, перестановки внутри
коллекций, родительские страницы, топология графа и сигналы кодировки.
Топология — появление и исчезновение самой коллекции: до 24.08.2026 такой
узел мог прийти и уйти при нулевом отчёте, если его объекты уже лежали в
других коллекциях. Перестановкой при этом называется только изменившаяся
последовательность: `orderDigest` покрывает и байты страницы, поэтому
переверстанная коллекция с тем же списком карточек прежде сообщалась как
перестановка с `moved: 0` — сообщение, неотличимое от настоящей.

### Бюджет обменов

Считаются ОБМЕНЫ по сети, а не страницы: каждый шаг редиректа и запрос
robots проходят через тот же счётчик и ту же паузу. Потолок 6000 —
ОПЕРАЦИОННЫЙ, а не верхняя граница задачи: 25 карточек измерены на ОДНОМ
направлении, и что на остальных их не 26, не доказано. При интервале 2000 мс
потолок означает до 3 часов 20 минут работы.

**Заранее бюджет больше не проверяется, и это не послабление.** Нижняя
граница «по обмену на объект» была вычислима, пока список объектов был
известен до их обхода. У графа он неизвестен: чтобы узнать, объект ли
карточка, её страницу надо получить. Поэтому нехватка бюджета перестала быть
решением прогона и стала отказом КОНКРЕТНОГО узла с кодом
`networkBudgetExhausted` — fail-closed ровно там, где случилась, и с именем
страницы. По той же причине `--limit` больше не экономит обмены: он режет
построение записей, а не обход.

Тело ответа читается ограниченным ридером и обрывается на первом же куске,
который переводит сумму за предел, — а не скачивается целиком, чтобы потом
быть измеренным.

### Отпечатки и мониторинг


У записи их пять, и у каждого одна роль: `leadDigest` (содержимое подсказки
без момента наблюдения), `recordDigest` (канонические поля и `omissions`),
`semanticDigest` (основание мониторинга), `pageEvidence` (байты, сырой
отпечаток, момент, диагностика кодировки) и `observationDigest` (весь
снимок). Позиция в списке в `semanticDigest` не входит: перестановка карточек
сообщается один раз на направление через `orderDigest`, а не превращается в
сообщение об изменении каждого объекта.

### Baseline живого обхода и сопоставление с базой

| Команда | Что делает |
| --- | --- |
| `node scripts/poi-portals/verify-discovery-baseline.mjs <манифест>` | сверяет манифест baseline с gzip-артефактом, лежащим рядом в репозитории |
| `node scripts/poi-portals/match-discovery-to-airtable.mjs <отчёт\|.gz> <выгрузка> [<результат>]` | read-only раскладка корпуса обхода по исходам сопоставления с таблицей POI |

Baseline версионируется ЦЕЛИКОМ: манифест плюс gzip-артефакт (683 037 байт
против 6 507 108 распакованных). Контейнер собран вручную, чтобы в файл не
попали метаданные машины: `gzipSync` пишет в шапку байт операционной системы и
время. Воспроизводимость байт между средами НЕ обещается — тело потока пишет
`deflateRawSync`, и его вывод зависит от сборки zlib. Tracked-байты
неизменяемы, а доказывают их три отпечатка, проверяемые отдельно: сжатых байт,
распакованных байт и снимка. Манифест проверяется точно и до листа; путь
артефакта обязан быть каноническим и лежать прямо в каталоге baseline, и
разрешается он второй раз файловой системой. Отсутствие артефакта — порча
клона, а не «локально не скачан»: кода возврата «сверка не выполнялась» нет.

Сопоставление не ходит в сеть и не умеет писать в Airtable. Публичная граница
принимает БАЙТЫ выгрузки, сама проверяет контракт `poi-airtable-export/v1` и
сама считает отпечаток — подать чужой нечем. Каноническая пара база/таблица
берётся из `src/lib/airtable-schema.ts`. Проекция обязана доказать, что каждое
используемое поле запрошено. Сила свидетельства различается и не сглаживается:
`Source Key` — утверждение базы о себе, адрес страницы — совпадение источника,
имя — только кандидат для человека. Дубль ключа и ЛЮБОЙ непустой ключ, не
согласный с кандидатом по адресу, становятся названными конфликтами и связью не
становятся никогда; автоматическая связь обязана быть один-к-одному.

### Диагностический план модельной классификации

| Флаг | Что делает |
|---|---|
| `--model-plan` | локальный план: модель не вызывается, в базу ничего не пишется, ключи не нужны. Требует `--out` внутри `tmp/poi-model-plans/`; рядом с отчётом пишет исполняемый конверт `<имя>.envelope.json` |
| `--model-provider-profile <id>@<version>` | точный профиль из канонического реестра, только вместе с `--model-plan` |

`--model-provider-profile` **связывает локальный план v2 с профилем**. Это не
вызов модели: прогон по-прежнему обходит источники обычным адаптером, пишет
отчёт и ничего не отправляет провайдеру. Флаг несовместим с `--limit`:
ограничение корпуса не входит в план, и повторный запуск источников его не
воспроизведёт. Пара задаётся ровно как `id@version` — ближайшей версии,
отката и частичного совпадения нет.

Канонический профиль и таблица цены **объявлены** (`openai-responses-luna@1.0.0`,
модель `gpt-5.6-luna`), поэтому пара теперь может разрешиться. Что при этом
по-прежнему невозможно:

- `executionPermitted` остаётся `false`, пока policy источника запрещает
  обработку, — а сегодня её запрещают все двенадцать источников;
- разрешения владельца в репозитории нет;
- реальных журналов исполнения не существует.

С 10f-O исполнитель **вызывается** production-путём — но только через ворота,
см. следующий раздел. Ссылка на `model-executor.mjs` из production-исходников
теперь ровно одна, и набор недостижимости проверяет именно это: не отсутствие
пути, а его единственность.

Профиль объявляет модель наблюдаемым алиасом со сроком сверки каталога:
после **17 сентября 2026, 00:00 JST** флаг начнёт отказывать до первого
адаптера, пока владелец не пересверит каталог новым коммитом.

`--model-plan` несовместим с любым режимом записи.

### Production-исполнение модельного плана

| Флаг | Что делает |
|---|---|
| `--model-execute` | исполнить подписанный план: preflight, журнал, запрос провайдеру |
| `--model-plan-file <name>` | ИМЯ исполняемого конверта `<имя>.envelope.json` в `tmp/poi-model-plans/` — не путь и не отчёт |
| `--model-approval <name>` | ИМЯ файла разрешения в `tmp/poi-model-approvals/` — не путь |

Режим принимает **только эти три флага**. Список разрешённого, а не перечень
запрещённого: следующий флаг таблицы по умолчанию несовместим, и чтобы это
изменить, придётся написать это явно. `--write`, `--dry-write`,
`--base-snapshot`, `--model-plan`, `--limit`, `--existing`, `--monitor`,
`--out`, `--portal`, `--all` отвергаются до чтения файлов.

**Исполняемый артефакт — конверт, а не отчёт.** `--model-plan --out x.json`
пишет два файла: отчёт `x.json` — выгрузку данных источника с планом внутри —
и рядом конверт `x.envelope.json` (`poi-model-plan-envelope/v1`) ровно из трёх
полей: `contractVersion`, `planArtifactDigest` и `plan`. Отчёт полномочий не
несёт и исполняемым артефактом не является: читатель отвергает его по полю
`modelPlan` и называет конверт; голый план отвергается так же. В конверте нет
ни времени прогона, ни `dryRun`, ни списка порталов — их источник уже внутри
подписанного плана, и второй, внешней копии этих величин конверт не даёт.
Объявленный отпечаток пересчитывается из плана и обязан совпасть: конверт,
объявляющий один отпечаток и несущий план с другим, не исполняется.

**Пути нет ни у конверта, ни у разрешения — только имя.** Конверт читается из
разрешённого каталога, а план внутри него проходит тот же
`parseAndVerifyModelPlan`, что его построил; разрешение — только через
собственный store с фиксированным корнем. Разделители, `..`, ссылка наружу и
нестрочное `.json` отвергаются физической проверкой пути, а не сравнением
строк.

**Профиль и таблица цены выводятся из подписанного плана** и канонических
реестров, вторым пользовательским вводом они не принимаются. Отпечаток профиля
из реестра сверяется с отпечатком в плане: реестр мог измениться после подписи.

Порядок, в котором это исполняется, и есть предмет доказательства:

1. разбор аргументов и изоляция режима — до любого ввода-вывода;
2. чтение конверта по имени, его форма и отпечаток, собственная проверка
   плана внутри, привязка профиля и цены;
3. `runExecutionPreflight` — двенадцать ворот, включая policy источника на
   момент прогона, идентичность кода двумя чтениями, повторный запуск
   адаптеров и денежный потолок;
4. и только после принятых ворот — открытие журнала, чтение секрета и
   обращение к провайдеру.

При отказе любых ворот журнал не открывается, переменная окружения с секретом
не читается, провод не вызывается, а процесс получает **точный код возврата**
preflight или исполнителя — не единицу «что-то не так». Единица остаётся за
отказом до ворот, и перехват этого отказа fail-closed на любом брошенном
значении: `throw null`, символ, объект с бросающим getter'ом, отозванный Proxy
описываются общим `describeThrownSafely` типом, а не читаются напрямую.

Секрет читается ровно перед отправкой из отдельной переменной
`POI_MODEL_EXECUTION_OPENAI_API_KEY`, а не из общего `OPENAI_API_KEY`: тот
задан у владельца для черновиков POI, и чтение его здесь означало бы, что
настройка, сделанная для другого, открывает платный прогон сама собой. Ни
значение, ни его длина, ни производная от него не попадают в отчёт, журнал или
текст ошибки.

**Сегодня этот путь до провайдера не доходит.** Policy всех двенадцати
источников запрещает модельную обработку, разрешения владельца в репозитории
нет, переменная с секретом не задана — прогон честно останавливается на
воротах. Закрыто это воротами, а не отсутствием кода, и проверяется
исполнением: `tests/poi-model-entrypoint.mjs`.

### Запись

**В Airtable по умолчанию не уходит ничего.** Без флагов записи прогон только
считает и показывает. Локальный файл при этом создаётся: его пишет `--out`, и
это выгрузка данных источника, а не запись в базу — обращаться с ней нужно
соответственно.

| Флаг | Что делает |
|---|---|
| `--write` | записать корзину import через `ingestPoiBatch` |
| `--dry-write` | полный конвейер записи против живой базы, без создания записей |
| `--base-snapshot <file>` | то же против снимка базы из файла, без токена Airtable |
| `--max-place-lookups <n>` | потолок платных обращений к Google Places; обязателен для production-резолвера |

`--write` требует **отдельного разрешения владельца** на каждый прогон.
Порядок получения и что делать при сбое — в
[`runbook.md`](../../docs/poi-intake/runbook.md).

Записываются кандидаты из корзины import, у которых **собралось** русское имя.
Источников три, по убыванию надёжности: файл `--names` (владелец уже выбрал
форму — она переопределяет машинную), кана источника, английское название.
`--names` обязательным не является: собранного из каны или английского
достаточно.

Запись идёт через `ingestPoiBatch`, то есть через тот же гейт, что и остальные
пути приёма: канон → идемпотентность по `Source Key` → гейт дублей и родителя
→ черновик.

### Бюджет обращений к Google Places

Опознание места идёт через канонический `resolvePlace`, и каждое обращение к Google
Places **платное**. Порядок в `writeRun` устроен так, чтобы не платить зря:

1. проверяются контракт маршрута, покрытие файла имён и представимость категории —
   всё бесплатно и по всему пакету сразу;
2. создаётся хранилище и по каждой строке проверяется `Source Key`. Уже принятая
   строка к резолверу **не идёт**, но терминальный исход `already_ingested` получает
   штатно, от `ingestPoi`;
3. считается число НОВЫХ строк. Если оно больше `--max-place-lookups`, прогон
   останавливается **до первого запроса** — целиком, а не обрезкой хвоста;
4. только после этого идут обращения к Google.

`--max-place-lookups` принимает целое неотрицательное число, отвергает повтор флага,
пустое значение и мусор вроде `12abc` — всё до сети. Для резолвера, собранного из
`GOOGLE_PLACES_API_KEY`, лимит **обязателен**: платный прогон без объявленного потолка
не запускается. `--dry-write` и `--base-snapshot` бюджет не отменяют: они касаются
записи в Airtable, а не опознания места.

Отчёт различает четыре числа — объявленный лимит, фактически выполненные обращения,
пропущенные как уже принятые и отказанные до обращения (`report.write.placeBudget`).
Кэша ответов Google в этом контуре нет: retention-политика не утверждена.

Форма строки снимка для `--base-snapshot` — в
`scripts/poi-portals/lib/base-snapshot.mjs`.

### Чем ищется место и когда имя считается тем же

Запрос идёт **японским именем**, если оно есть: у японских открытых данных
английского названия нет вовсе — в замороженном корпусе Осаки английское имя
есть у нуля строк из двадцати, японское у всех. Пока ключом было только
английское название, портальный путь платил Google за гарантированный промах.
Английское имя остаётся запасным ключом для Telegram и источников без
японского. Язык запроса следует за ключом: `ja` для японского имени, `en` для
английского. Город и «Japan» дописываются только к латинскому запросу —
японскому они не помогают, а лишние латинские слова смещают выдачу.

Точка источника уходит **предпочтением** (`locationBias`, радиус 500 м), а не
ограничением: предпочтение смещает выдачу к нужному месту и не отсекает
правильный ответ чуть дальше. Принимается только полная конечная пара
координат — половина пары сместила бы поиск неизвестно куда.

Имя считается тем же по **множествам токенов**, а не по вхождению подстроки:
«Nara Park» и «Nara» — разные места, «Mt Fuji» и «Mount Fuji» — одно.
Межалфавитные пары не сравниваются вовсе: транслитерации у нас нет, а догадка
здесь запрещена. Японские имена сравниваются на равенство нормализованной
формы, поэтому «大阪城» не сходится с «大阪城公園».

**Префектура в записи — только от провайдера.** Прежде при ответе без
административной единицы наружу уходила наша же ожидаемая префектура под
видом ответа Google: проверить принадлежность направлению становилось нечем.
Ожидаемая префектура — условие проверки, а не данные.

Прошедших кандидатов может быть больше одного. Это не «нашли», а **не смогли
выбрать**: исход `ambiguous` не даёт ни Place ID, ни координат, иначе выбор
между двумя местами делала бы очередь выдачи.

Повреждённый ответ провайдера границу не покидает: тело не той формы,
`places` не массивом, брошенный `json()` и упавшая сеть дают именованный исход
(`malformedResponse`, `providerError`), а не исключение. Через путь Telegram
такое исключение прежде роняло весь приём — ни записи, ни отчёта.

### Приёмка на корпусе Осаки

**Офлайн** — `tests/poi-canary-osaka-offline.mjs`, входит в `npm test`. Двадцать
настоящих строк портала `bodik-osaka-tourism` и замороженные ответы Google
лежат в `tests/fixtures/poi-canary-osaka/` и привязаны отпечатками: подмена
корпуса меняет предмет приёмки. Сети, Airtable и денег в этом прогоне нет.

**Живой canary** — разовое наблюдение, а не режим работы. Прогон 02.09.2026
выполнен по отдельному разрешению владельца с жёстким потолком
`--max-place-lookups=20`, только на чтение, без единого обращения к Airtable
(хранилище — снимок в памяти) и без автоматического повтора. Наблюдалось:
20 обращений, границу места прошли 11 строк, записями в снимке стали 10, одна
прошла границу места и записью не стала (`ミライザ大阪城`; ветка приёма —
реконструкция: гейт дублей, музей Кайёдо в 12 м, в том же здании), 9 строк не
опознаны — 7 `notResolved`, 2 `ambiguous`.
Отчёт: `tmp/10f-n/live-canary-2026-09-02.json`. Расстояние между точкой
источника и точкой резолвера — от 1 до 205 м; **числового отказа по
расстоянию нет**: точка Google принята как достаточная, отдельного решения
владельца о пороге не было.

**Где кончается наблюдение.** Наблюдались агрегаты прогона: число обращений,
сколько строк прошло границу места, сколько стало записями, раскладка отказов и
Place ID с координатами СОЗДАННЫХ записей. Точка, Place ID и ветка приёма
двадцатой строки — той, что прошла границу и записью не стала, — в отчёте не
сохранены и **восстановлены реконструкцией** (`tmp/10f-n/final-canary-reconciliation.mjs`,
разбор — `tmp/10f-n/live-canary-2026-09-02-reconciliation.md`). Называть эту
реконструкцию живым наблюдением нельзя.

Этот прогон — состояние рабочего дерева на дату наблюдения, а не production:
коммита нет, расписания нет, и в живую базу ничего не писалось.

## Координаты и срок их хранения

`npm run backfill:coords` берёт координаты из Wikidata (CC0, хранить можно
бессрочно) и заодно проставляет `Wikidata QID` и `Name (JA)`.
`npm run backfill:coords-google` добирает остальное из Google Places.

**У координат из Google есть срок годности.** Условия Maps Platform разрешают
хранить `place_id` бессрочно, остальное содержимое — тридцать дней. Поэтому
рядом с координатой лежит `Google Place ID`, а `npm run refresh:coords`
перечитывает координаты по нему. Не запускать этот прогон — значит хранить
чужие данные дольше разрешённого и называть это иначе.

`Name (JA)` здесь важнее координат: имена на латинице у нас и у портала
расходятся всегда, японские — почти никогда, и сверка по ним надёжнее.

## Лицензии источников

**Источник с `licence.commercial !== true` пропускается автоматически.**
Проприетарные порталы лежат в реестре как проверенные, но в прогон не
берутся, пока не решён вопрос прав.

## Добавление портала

Только запись в `registry.mjs`. Поля `verified.at` и `licence` обязательны:
непроверенный источник в реестр не попадает.

Если источник — CSV в стандарте `自治体標準オープンデータセット`, адаптер
`opendata-csv` подхватит его без правок кода: колонки читаются через таблицу
алиасов с нормализацией ширины символов. Проверено на двух несовпадающих
схемах (Осака 58 колонок, Киото 32).

Для нового класса источников — новый адаптер в `lib/` и регистрация
в `ADAPTERS` внутри `collect-pois.mjs`.

Таблиц адаптеров две, и путать их нельзя. В `ADAPTERS` живут те, кто
производит КАНДИДАТОВ в POI: их результат идёт в оценку, дедуп, очереди и
запись. В `DISCOVERY_ADAPTERS` — те, кто производит discovery-записи с
неподтверждёнными подсказками; в конвейер кандидатов они не попадают ни одним
путём.


## Что в отчёте

- `totals.autoImportable` — сколько прошло все четыре условия автоимпорта
- `totals.needsLlmCategory` — очередь на ступень 1 каскада
- `totals.volatileFieldsUnverified` — записи, чьи часы и цены публиковать нельзя
- `rejectReasons` — причины отбраковки со счётчиками
- `aiCost` — оценка стоимости прогона по фактическому корпусу
- `samples` — примеры решений, числом из `--samples`
- `all` — полный список решений по каждой записи, не только примеры

У discovery-портала отчёт другой: `mode: 'discovery'`, `meta` со счётчиками
прогона и `discovery` с записями, порядком объектов по направлениям и списком
отказов. Полей `writable`, `queues` и `all` у него нет — кандидатов он не
производит.


Последнее важно: на вопрос «почему эта точка не прошла» надо уметь отвечать
без перезапуска прогона.
