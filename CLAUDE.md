## 1. Project identity

JumboInJapan is a Russian-language private guide and Japan travel-planning website.

The product should feel like:

- a personal guide service,
- calm and competent,
- route/logistics aware,
- grounded in local Japan context,
- useful for real travelers, not just SEO traffic.

Do not turn the site into a generic travel blog, city directory, or anonymous travel portal.

## 2. Current architecture baseline

Treat this as the current working model unless the code proves otherwise.

- Framework: Next.js App Router.
- UI: React, Tailwind CSS 4, componentized layout under `src/components`.
- Content: mostly Russian public-facing copy in `src/app`, `src/data`, and page-level modules.
- SEO: Next metadata, canonical URLs, OpenGraph, schema.org JSON-LD.
- Analytics: Vercel Analytics.
- Config: `next.config.ts` includes redirects and `withWorkflow(nextConfig)`.
- Data pipeline: Japan Travel event ingestion through `scripts/import-japantravel-events.mjs` and `src/lib/japantravel-*` modules.
- External storage: Airtable is the canonical storage layer for imported resources/events.
- Images: files live ONLY in `public/`; the authoritative image path lives in exactly ONE place per surface (stop photos & multi-day heroes → Airtable; static-page heroes, cards, OG → code). Canon, naming rules, and the change process: `docs/photo-storage.md`. Validate with `npm run check:images` before any photo-touching commit.
- Типографика: русский текст типографируется НА РЕНДЕРЕ — `typoDeep(props)` из `src/lib/typography.ts` в отображающих компонентах. Неразрывные пробелы, многоточия и дефис-тире в исходниках руками не расставляются. Подробности и границы — ниже, раздел «Типографика».

Important package scripts:

```bash
npm run dev
npm run build
npm run lint
npm run check:images          # целостность ссылок на фото (код+Airtable+public/)
npm run check:typography      # грубые ошибки русской типографики в исходниках
```

Note: `npm run lint` runs `eslint .` directly (Next.js 16 removed the `next lint` subcommand — if you see `Invalid project directory provided`, that's the old command resurfacing; `eslint.config.mjs` ignores `.next/**`, `next-env.d.ts`, `node_modules/**`, `public/**`).

## 6. Coding rules

### General

- Prefer TypeScript clarity over cleverness.
- Reuse existing utilities/components before adding new ones.
- Keep page-level content readable.
- Avoid unnecessary dependencies.
- Avoid broad formatting churn.
- Do not rename public states, fields, or routes unless required.
- Do not commit secrets, tokens, `.env.local`, logs with credentials, or private API output.

### React / Next.js

- Prefer server components unless client behavior is required.
- Add `'use client'` only when necessary.
- Keep metadata close to the page when page-specific.
- Use `next/image` for local/public images where appropriate.
- Keep alt text meaningful for real users and SEO.
- Do not use `dangerouslySetInnerHTML` except for controlled JSON-LD or already-established patterns.

### Styling

- Use existing Tailwind/CSS variable patterns.
- Preserve visual rhythm between nearby pages.
- Check mobile behavior for any layout change.
- Avoid decorative effects that reduce readability.
- Do not introduce a new design system inside one task.

### Вёрстка согласуется со скиллом `impeccable` (решение владельца, 2026-07-31)

Любая правка, меняющая вид публичной страницы — сетка, выравнивание, отступы, кегли, порядок блоков, новая секция, — проходит через скилл `impeccable`, а не делается на глаз.

**Почему.** Хук скилла уже подключён (`PostToolUse` + `Stop` в `.claude/settings.local.json`) и ловит детерминированное: кегли мимо шкалы, хардкод цветов, произвольные значения. Но «заголовки крепятся криво» он поймать не может — это суждение, а не правило. Именно такие вещи владелец и замечает на проде.

**Порядок работы:**

1. **Вызвать скилл явно.** Он живёт в `~/.claude/skills/impeccable` и сам по себе НЕ срабатывает — только инструментом Skill или `/impeccable <команда>`. Подкоманды: `layout` (сетка, ритм, выравнивание), `typeset` (иерархия и типографика), `critique` (разбор с оценками), `polish` (вычитка перед отгрузкой), `adapt` (узкие и широкие экраны).
2. **Диагноз замером, а не взглядом.** Прежде чем двигать блоки, снять фактические координаты в браузере (`playwright-core` + `channel: "chrome"`, дев-сервер `site`): левые и правые края колонок, верх и низ соседних блоков. Расхождение рельс в 37 px и несшитый низ в 56 px — это числа, а не впечатление; на глаз они читаются просто как «криво».
3. **Перед коммитом прогнать детектор:** `node ~/.claude/skills/impeccable/scripts/detect.mjs --json <файлы>` — пустой массив значит чисто.
4. **Показать владельцу картинку, а не код** (см. правило визуалов ниже по тексту раздела).

**Канон проекта старше скилла.** При конфликте побеждают правила этого файла: шкала кеглей из `globals.css`, лимиты длины из `src/lib/copy-limits.ts`, антиква только на дисплейных ролях, канон формулировок транспорта. Скилл предлагает — канон решает.

### Adversarial pass — обязательный прогон перед коммитом (2026-07-10)

Песочница не собирает приложение (tsc/eslint only), поведенческие баги доезжают до прода. Серия факапов 10 июля имела один корень: фича отгружалась по счастливому пути. Перед коммитом любой фичи ответить на 5 вопросов:

1. **Существующие данные:** как фича поведёт себя на записях, созданных до неё? (rename прилёта работал только для generated-items — старые manual молчали)
2. **Конкурирующие источники состояния:** у любого нового хранилища (localStorage, кэш, вторая вкладка) должна быть политика конфликтов с timestamp «кто новее» (черновик-кэш без неё показал пустой тур поверх сохранённого; «Сохранить» затёрло бы базу)
3. **Время и пояс:** владелец в Японии (UTC+9); даты — чистый UTC насквозь, пример прогнать под TZ=Asia/Tokyo (18 окт рендерилось как «17 окт»)
4. **Идемпотентность генераторов:** ввод может уже содержать то, что генератор добавляет (slug `classic-japan-7-days-7-days`)
5. **Разрушающие записи:** каким состоянием «Сохранить» может перезаписать базу? Guard от «пустое поверх полного»

Если сценарий проверяем только на проде — явно написать владельцу, что именно проверить.

## 7. Verification expectations

Run the strongest relevant verification available for the change.

For most code changes:

```bash
npm run lint
npm run build
```

При изменении русского текста (страницы, копирайт, данные) добавить:

```bash
npm run check:typography
npm run check:copy
npm run test:typography
```

There is no dedicated `npm run typecheck` script. Use `npx tsc --noEmit` directly — it works fine against the existing `tsconfig.json` and should be run whenever `.ts`/`.tsx` files change.

For UI/page changes:

- Run build.
- Manually inspect affected routes if a browser/dev server is available.
- Check mobile and desktop layout when practical.
- Confirm metadata/canonical/schema changes if touched.

For importer/pipeline changes:

Run at least a dry run, for example:

```bash
npm run check:images          # целостность ссылок на фото (код+Airtable+public/)
npm run sync:photo-fallback   # регенерация src/data/route-stop-photos.generated.json
npm run import:japantravel-events -- --pages 1 --limit 5 --dry-run
```

If changing maintenance behavior:

### Проверка привязывается к тем же байтам, что и исполнение (2026-08-20)

Число тестов, число убитых мутаций и слово «зелёный» ничего не значат без указания, НА ЧЁМ они получены.
Трижды за этап 10c один и тот же вердикт приходил по копии, отставшей от доставки: правка уже лежала на диске
владельца, а проверяющий читал старое дерево.

Требование — не «где запущено», а «на чём». Прогон годится на любой площадке — рабочее дерево, контейнер,
CI, — если совпадают три вещи: HEAD, состояние рабочего дерева относительно него и `sha256` файлов, о которых
идёт утверждение. Идентификатор байтов — только хеш и HEAD; `mtime` показывает, откуда взялось расхождение, но
сам ничего не доказывает.

В отчёте поэтому указываются HEAD, путь и `sha256` ключевых файлов. Расхождение чисел — повод сверить байты, а
не переписывать код заново.

### Мутационная проверка — ещё и детектор мёртвого кода (2026-08-20)

Выжившая мутация означает одно из двух: теста нет — или проверять нечего. Второе бывает реже, но встречается:
guard, ставший избыточным после усиления соседних инвариантов, — это мёртвый код, и он завышает видимую
площадь проверок.

Критерий, что с ним делать, и разбор двух случаев из этапа 10c — в `/jj-db-dev` §6. Здесь важен только
принцип: выжившая мутация требует решения, а не автоматического дописывания теста.

### Смена текущей версии формата оголяет замороженную (2026-08-24)

Пока формат был текущим, его закрытые наборы задевал каждый тест. В день, когда текущей становится следующая
версия, прежняя перестаёт задеваться вовсе — и проверка, которая её читает, остаётся без единого испытания.
Измерено на этапе 10d-B: с приходом `v3` мутация, опустошавшая `cardRejectionCodes` у `v2`, пережила оба
набора; сам код не менялся, изменилось только то, что по нему больше никто не ходит.

Поэтому у каждой замороженной версии обязан быть СВОЙ прогон её правил, а не косвенное покрытие через
текущую. Практически это значит: приведение сегодняшнего объекта к форме прошлой версии (поля убраны,
отпечатки пересчитаны прошлыми доменами) и прогон по ней. Проверять этого не требуется — это делает мутация:
опустошите набор замороженной версии, и она обязана умереть.

### Недостижимая проверка делается достижимой параметром, а не удаляется (2026-08-24)

Guard, который невозможно провалить на замороженном литерале, — по критерию §6 `/jj-db-dev` мёртвый код. Но
между «удалить» и «оставить как есть» есть третье: сделать вход параметром и подать синтетический
контрпример. Так поступили со сверкой, требующей, чтобы два формата снимка, ссылающиеся на один формат
записи, не разошлись в её правилах: на `VERSION_POLICY` расхождению взяться неоткуда, а на паре подставных
политик — вполне. Guard остался, стал испытуемым и получил свою мутацию.

Правило простое: сначала спросить, достижим ли отказ хоть каким входом. Если да — сделать вход достижимым.
Если нет ни при каком — удалять с выводом.

### Смена модели исполнения оголяет операционных потребителей (2026-08-24)

Контракт можно перестроить безупречно и всё равно оставить систему в противоречии: потребители, написанные под
прежнюю модель, продолжают считать по её формулам и молча принимают невозможное. Измерено на 10d-B: обход стал
графом, а офлайн-приёмка осталась двухуровневой — и приняла снимок, объявлявший 259 обменов там, где физически
требовалось 1322. Она же сама вычисляла базу 1322 и не сравнивала её ни с чем.

Поэтому после смены модели исполнения проверяются НЕ ТОЛЬКО контракт и обход, но каждый потребитель, у которого
есть собственная арифметика: приёмка, монитор, отчёты, бюджеты. Вопрос к каждому один — какое утверждение о мире
он делает и осталось ли оно верным. Три типовых исхода: пересчитать по новой модели; объявить потребителя
применимым только к прежним версиям и отказывать именованным кодом; удалить, если утверждение перестало иметь
смысл. Молчаливое «оно и так работает» здесь — самый дорогой вариант.

### Инвариант ставится там, где он верен для всех входов формата (2026-08-24)

Соблазн — починить конкретного потребителя. Правильнее спросить, не является ли нарушенное утверждение
свойством самого формата. Нижняя граница числа обменов выводится из состава снимка и потому живёт в контракте,
а не в приёмке: там она действует на каждый снимок `v3`, а не только на тот, что попал в canary. И наоборот —
к замороженным версиям её применять нельзя, потому что модель исполнения у них была другой; версия инварианта
объявляется полем политики, а не угадывается по наличию соседнего поля.

### Граница, считающая только успехи, неполна (2026-08-24, R2)

Инвариант «состав требует не меньше N» естественно пишется по тому, что получилось: свидетельства, записи,
найденные объекты. Но ресурс тратится и на попытку, которая кончилась отказом. Аудит R2 предъявил два снимка,
которые первая редакция границы пропускала: цель, отвергнутая с `statusDenied`, объявляла 4 обмена при минимуме
5, отвергнутый узел графа — 3 при минимуме 4. Правило общее: считая ресурс, потраченный на попытку, слагаемые
берут из ВСЕХ её исходов, а не из одних удачных.

Что именно стоило ресурса — измеряется на границе, а не выводится из смысла имени кода. Отказы делятся на «до
обмена» и «после», и делит их одно: успел ли вызов дойти до места, где растёт счётчик. Ответ читается в самом
`html-fetch`, а не угадывается. Из двух списков перечисляется тот, чей пропуск ШУМЕН: закрыт список досетевых
кодов, «после обмена» — его дополнение, поэтому забытый код поднимет границу и отвергнет законный снимок, а не
пропустит подделку. И проверяются ОБЕ ветви: регрессия только на ту, ради которой классификация заведена,
оставляет вторую невидимой, а мутацию «всегда истина» — живой.

### Классификация снимается с пути потребителя, а не с функции (2026-08-25, R3)

Предыдущая доктрина была верной наполовину и потому опасной: классификацию сняли с настоящей границы —
но с НИЗКОУРОВНЕВОЙ функции, а не с пути, которым к ней приходит потребитель. `canonicalDiscoveryUrl`
бросает `urlNotCanonical` до запроса, и это правда; но `fetchHtmlPage` зовёт ту же функцию второй раз — для
`Location` уже полученного 3xx. Один код, две стадии. Настоящий обход дал 7 обменов, снимок с объявленными
6 контракт принимал, и граница, только что «достроенная», оставалась обходимой одним редиректом.

Правило: смотреть не «где эта функция бросает», а «какие вызовы этой функции ДОСТИЖИМЫ на пути к записи,
которую я классифицирую». Если достижим больше чем один — глобальной таблицы по коду не существует, и
классификация обязана стать контекстной: свой список у каждого канала, обоснование у каждого пункта.
И проверять её надо ТЕМ ЖЕ расчётом, которым пользуется потребитель: отдельно экспортированная функция
переживает мутацию, закрепляющую неверную классификацию, а расчёт снимка — нет.

Где остаётся неопределённость, её называют, а не прячут.

### Названный остаток надо ПОСЧИТАТЬ, а не оценить на глаз (2026-08-25, R4)

Назвать остаток вслух — половина дела; вторая половина в том, что названная величина обязана быть
посчитанной. R3 честно записал: «`networkBudgetExhausted` бывает и на шаге редиректа, утаить можно не больше
одного обмена». Рассуждение шло от «после исчерпания каждый следующий вызов падает без сети» — и упустило,
что ОДНА цель успевает истратить до `maxRedirects` обменов прежде, чем упереться в потолок. Настоящий обход
при бюджете 4 потратил 4 обмена и объявил 2; состав снимка это позволял. Ошиблись не в направлении, а в
арифметике — и записанная оценка сделала дыру невидимой убедительнее, чем молчание.

Практика: остаток либо выводится как формула от величин, которые можно предъявить, либо предъявляется
исполняемым контрпримером на максимум. «Не больше N» без вывода — это гипотеза, а в документе она выглядит
как измерение.

И второй вывод, важнее первого: остаток чаще закрывается не там, где обнаружен. Классификацию отказов
уточнять было бессмысленно — код честно неопределим. Закрыл его СНИМОК, начавший нести собственные потолки:
величина, которой не хватало для проверки, была не в правиле, а в контексте прогона. Прежде чем считать
дыру неизбежной, стоит спросить, чего инварианту не хватает, — и нельзя ли это записать в артефакт.

### Диапазон нового поля берётся у production API, а не у своего примера (2026-08-25, R5)

Добавляя поле, легко записать в его проверку тот диапазон, в котором оно встречалось при отладке. Так
`maxRedirects` получил минимум «не меньше 1» — все фикстуры шли с двойкой. Но ноль — законный режим
production API «за редиректами не ходить», и валидатор начал отвергать снимки ОБЫЧНОГО обхода. Хуже того,
рядом стояло обоснование, звучавшее убедительно и бывшее ложным: якобы при нуле снимок не отличит исчерпание
бюджета от досетевого отказа. Инварианты при нуле работают дословно так же.

Правило: границы нового поля берутся у того кода, который это значение производит, и подтверждаются прогоном
на каждом краю — здесь хватило одного обхода с нулём. И обоснование ограничения пишется ПОСЛЕ того, как оно
проверено, а не заодно с ним: правдоподобный комментарий рядом с лишней проверкой переживает не одну ревизию
и защищает её от пересмотра.

### Проверка, молчащая на НЕДОСТАЮЩЕМ поле, не проверка (2026-08-25, 10d-C R1)

Сверка baseline читала манифест по принципу «что нашли, то и сравнили»: удалённый `snapshotDigest` или
удалённый счётчик давали ноль расхождений, то есть ЗЕЛЁНЫЙ отчёт. Отсутствие поля — не «нечего сравнивать»,
а несовпадение формата, и молчать о нём опаснее, чем о неверном значении: неверное значение когда-нибудь
заметят глазами, отсутствующее — нет.

Правило: валидатор формата точен и версионирован. Недостающее И лишнее поле на любом уровне отвергаются с
указанием пути; развитие формата идёт через новую версию или явный мигратор, а не через «сравним то, что
совпало». То же и о входах чужого происхождения: выгрузка из базы проверяется контрактом ДО раскладки по
исходам, иначе обсуждается состав того, что выгрузкой не является.

### Противоречивое свидетельство отравляет ВСЕ свои утверждения (2026-08-25, 10d-C R1)

Запись базы, у которой `Source Key` указывает на один объект, а `Website` — на другой, не «связана с первым
и заодно со вторым»: она утверждает о себе две несовместимые вещи. Первая правка сняла связь только у
названного ключом — и второй объект молча связался с той же записью по адресу. Считать такую запись
ненайденной тоже нельзя: это спрятало бы дефект базы за словом «новый».

Правило: противоречивые свидетельства вычисляются ДО раскладки, выбывают из всех указателей разом и
становятся НАЗВАННЫМ исходом. Автоматическая связь обязана быть один-к-одному, и это проверяется сторожем, а
не улаживается выбором первого претендента.

### Довод «такого входа не бывает» проверяется мутацией, а не рассуждением (2026-08-25, 10d-C R1)

Сторож связи один-к-одному был снабжён доводом: после отравления противоречивых записей два претендента на
одну строку невозможны, поэтому сторож — тропа для будущей правки. Мутация «сторож снят» ВЫЖИЛА, и это был не
эквивалентный мутант, а недостающий вход: два объекта обхода на одной странице не противоречивы ни в чём, но
оба тянулись к одной записи. Довод был неверен, и его правдоподобие защищало дыру.

Правило: выживший мутант у сторожа — это гипотеза «состояние недостижимо», предъявленная к доказательству, а
не к пересказу. Либо строится вход, на котором сторож срабатывает (тогда сторож остаётся и получает прямую
регрессию, а причина закрывается поимённо выше), либо недостижимость доказывается — и тогда мутация
объявляется эквивалентной ПИСЬМЕННО. Третьего — «оставим как есть, оно же разумно» — нет.

_Продолжение (R3)._ Тот вход существовал только потому, что граница принимала снимок БЕЗ контракта. Как
только она стала звать полный `assertDiscoverySnapshot`, «два объекта на одной странице» стало
непредставимым: контракт требует, чтобы `sourceKey` выводился из адреса. Обе ветви, добавленные в R1, стали
мёртвым кодом — и удалены, а не оставлены «на всякий случай»: сторож, который нечем убить, держит в матрице
строку, лгущую о покрытии. Утверждение о результате осталось отдельной экспортируемой функцией, и она
проверяется прямым вызовом.

### Точность проверки кончается там, где кончается тип (2026-08-25, 10d-C R2)

«Объект», «массив», «непустая строка» — это не проверка, а её обещание. Валидатор манифеста baseline
отвергал недостающие и лишние поля на каждом уровне и всё равно принимал `scope: {}`,
`recordVersions: [123]`, `incompleteReasons: [123]`, лишнее поле внутри `networkPolicy` и путь
`../../outside.json.gz`: до листьев он не доходил, а путь читал как «строку». Внутри правильной формы
пряталось произвольное содержимое.

Правило: у каждого листа объявлена ОБЛАСТЬ ЗНАЧЕНИЙ — перечень, синтаксис отпечатка, числовой диапазон,
каноничность и принадлежность пути. Там, где область задаёт версия формата, она берётся из той же политики,
которой пользуется производственная проверка, а не переписывается вторым списком. И проверяется публичный
валидатор ПРЯМО: сторож, испытанный только через агрегат, живёт ровно до дня, когда агрегат начнёт падать
по соседней причине — а «упало» и «упало из-за этого» разные утверждения.

### Полномочие не берётся у вызывающего (2026-08-25, 10d-C R2)

Три границы подряд спрашивали доказательство у того, кого проверяли. Тождество таблицы — параметр
`expected`, и подделка проходила, если вызывающий объявлял её ожидаемой. Отпечаток выгрузки — аргумент, и
строка `not-a-digest` попадала в отчёт как доказательство привязки. Полнота выгрузки — её собственная
проекция, и `fields: ['poiId']` объявлял бы все 1140 объектов несопоставленными.

Правило: то, что граница УДОСТОВЕРЯЕТ, вычисляется внутри неё. Каноническая идентичность — из общего модуля
схемы, отпечаток — из поданных БАЙТ (поэтому публичный вход принимает байты, а не разобранный объект),
достаточность входа — из списка того, чем пользуется сам код. Значение, которое вызывающий может объявить,
не удостоверяет ничего; параметр, позволяющий его объявить, — это не гибкость, а дыра с документацией.

### Незаданный вопрос выглядит как отрицательный ответ (2026-08-25, 10d-C R2)

Выгрузка с проекцией из одного поля исправна: строка без `Source Key` и `Website` — законное состояние базы.
Поэтому «не найдено 1140» на ней означало бы не «база их не знает», а «мы не спрашивали», и отличить одно от
другого по результату нельзя. Проекция — часть входа, а не деталь запроса: она обязана ДОКАЗАТЬ, что каждое
используемое поле было запрошено. Пустое значение в отдельной строке при этом остаётся законным — это ответ,
а не молчание.

### Обещание, которое нельзя проверить у себя, не пишут (2026-08-25, 10d-C R2)

Артефакт baseline объявлялся «детерминированным по построению»: фиксированная шапка gzip убирает имя, время
и код ОС, значит файл одинаков на любой машине. Первая половина верна, вывод — нет: тело потока пишет
`deflateRawSync`, и его вывод зависит от сборки zlib. На машине разработки пересборка совпадала побайтово, у
аудитора дала 714 522 байта против 683 037 — и обещание рухнуло ровно там, где его нельзя было проверить.

Правило: свойство, для проверки которого нужна среда, которой у вас нет, в документ не пишут — пишут то, что
проверяется здесь. Здесь это три отпечатка: сжатого файла, распакованного отчёта и снимка. Артефакт при этом
объявляется НЕИЗМЕНЯЕМЫМ: его не пересобирают и с пересобранным не сравнивают.

### Зелёная матрица мутаций — утверждение о входах, а не о коде (2026-08-25, 10d-C R2)

187 из 187 мутаций были убиты, и в тот же день аудит нашёл шесть fail-open границ. Противоречия нет: мутация
проверяет, отличит ли НАБОР испорченный код от исправного, — и молчит о поведении, для которого во входах
нет ни одного примера. Ни один тест не подавал `scope: {}` и не подменял проекцию, поэтому и убивать было
нечего.

Правило: процент убитых мутаций читается как «покрытие ТЕХ входов, что есть», и рядом с ним всегда стоит
второй вопрос — какие входы формат допускает, а набор не предъявляет. Отвечает на него не матрица, а
перебор областей значений по схеме и чужой злой взгляд. И новая мутация обязана убиваться СВОИМ
контрпримером: мутант, падающий у соседа, скрывает, что его собственная дыра не проверена.

### Нормализация — это утверждение о равенстве (2026-08-25, 10d-C R3)

`pageIdentity` опускала регистр целиком — и адрес базы `/e/E1.html` автоматически связывался со снимком
`/e/e1.html`. В HTTP путь регистрозависим: это разные ресурсы, и «привести к одному виду» здесь означало
объявить равным то, что не равно. Ложная канонизация тем и опасна, что выглядит как аккуратность и попадает
в отчёт готовым фактом.

Правило: нормализуют ровно те различия, равенство которых гарантирует спецификация, — схему, регистр имени
хоста, точный `www.`, оговорённый хвостовой слэш. Всё, что зависит от источника — регистр пути, точечные
сегменты, процентное кодирование, — либо сохраняется как есть, либо ЛИШАЕТ вход идентичности целиком. Третий
путь, «раскроем псевдоним и сравним», — это решение за источник, какие его адреса одинаковы.

### Публичная граница не бывает слабее того, кто её зовёт (2026-08-25, 10d-C R3)

Полный контракт снимка проверял скрипт, а экспортируемая граница — сокращённый заменитель «то, чем
пользуется раскладка». Он видел синтаксис отпечатка и не видел его соответствия содержимому: подделанная
запись живого снимка со СТАРЫМ `snapshotDigest` проходила, и отпечаток публиковался в отчёте как привязка.
Сокращённая проверка на границе — это обещание, данное вместо проверки.

Правило: если у входа есть производственный контракт, публичная граница зовёт ЕГО. «Проверим то, чем
пользуемся» годится для внутренней функции, но не для экспортируемой: снаружи её позовут не так, как звали
вы. И тогда фикстуры набора обязаны стать настоящими — набор, подающий объект, которого производство не
допускает, проверяет поведение, которого не бывает.

### Чужой разбор чинит вход раньше, чем вы его проверите (2026-08-25, 10d-C R4)

`pageIdentity` уже отвергала запрос, фрагмент, порт и точечные сегменты — но делала это ПОСЛЕ `new URL`, а
разбор WHATWG к тому моменту уже заменил обратные слэши прямыми, отбросил лишние слэши перед authority и
схлопнул `..`. Проверялся результат чужой догадки о том, что имел в виду источник:
`https://www.japan-guide.com\e/e3003.html` и `https:////www.japan-guide.com/e/e3003.html` на живой паре
входов автоматически связались с настоящей страницей.

Правило: если вход надо ОТВЕРГАТЬ по написанию, разбирайте его сами и до всякой библиотеки. Библиотечный
разбор существует, чтобы приводить к норме, — он по определению стирает ровно те различия, из-за которых вы
собирались отказать. Строгое собственное выражение вдобавок дешевле: оно и есть спецификация того, что вы
согласны считать адресом.

### Объявленная поддержка формата — это обещание, которое кто-то проверит (2026-08-25, 10d-C R4)

Валидатор baseline брал версию снимка из общей таблицы форматов и потому «поддерживал» `v1` и `v2`. Описать
их модуль не мог вовсе — `describeDiscoveryBaseline` читает `nestedCollectionEvidence`, которого у `v1` нет,
и падает. Хуже того, на этой ложной поддержке стояла проверка семейства ключа, а её «убивала» фикстура с
манифестом-химерой: метка `v1` при составе `v3`. Мутация считалась убитой состоянием, которого не бывает.

Правило: поддерживаемые версии перечисляются ЯВНО и ровно те, что модуль умеет обрабатывать целиком;
расширение — новая версия формата или мигратор, а не строка в списке. И проверка, живущая только за счёт
невозможного входа, снимается вместе с ним: покрытие, доказанное химерой, — не покрытие.

### Метка на упаковке — не то же самое, что содержимое (2026-08-25, 10d-C R5)

Версия формата проверялась там, где она ОБЪЯВЛЕНА, — в манифесте, — и нигде больше. Аудит упаковал настоящий
снимок `v1` каноническим gzip, пересчитал все три отпечатка и оставил манифесту заявление `v3`: байты
сошлись, производственный контракт снимок принял (он законный, только другой версии), и сверка дошла до
описания, которого для `v1` не существует. Ложного зелёного не было — было сырое падение вместо названного
отказа.

Правило: отпечаток доказывает ЦЕЛОСТНОСТЬ, а не пригодность. Если код работает только с одним форматом,
фактическая версия распакованного содержимого сверяется отдельно — после контракта и до первого чтения полей,
специфичных для формата. И та же проверка ставится на публичную функцию, которая эти поля читает: снаружи её
позовут напрямую.

### Строгость входа кончается на первом `String(x)` (2026-08-25, 10d-C R5)

`pageIdentity` была переписана под строгий лексический разбор — и начиналась с `String(url ?? '').trim()`.
Две необъявленные нормализации подряд: объект `URL` приводился к строке уже ПОЧИНЕННЫМ (он для того и
существует), а внешние пробелы молча срезались. Производственный путь таких значений не подавал, но контракт
функции обещал строгость, которой у неё не было.

Правило: у строгой функции строг и приём. Примитивный тип проверяется явно, приведение и подрезка не
делаются вовсе — если вход не той формы, ответ «не знаю», а не «сейчас поправим». Дырой это становится ровно
тогда, когда рядом появляется второй вызывающий, который об умолчаниях не знал.

Подробности для слоя данных — в `/jj-db-dev`; здесь только то, что верно для любой правки.

## 8. How to report work

Every implementation response should include:

```md
Summary:
- ...

Changed files:
- ...

Verification:
- Ran: ...
- Not run: ...

Risks / notes:
- ...

Suggested next step:
```

каких байтах получен результат (путь, `sha256`, время изменения), и команду, которой другая сторона
воспроизведёт это у себя. Перезапись поверх уже верного кода — лишний риск, а не вежливость.

- Interactive `git rebase` can fail on this mount (missing `.git/rebase-merge/message` mid-rebase, a write-related quirk of the mount, not a real conflict). Prefer `git merge origin/main --no-edit` over rebase when reconciling a diverged branch here — it's a single atomic operation and doesn't depend on writing per-commit state files.

### КАНОН длины текста: у каждой роли есть предел (2026-07-30)

**Обязательно для всех, кто пишет или компилирует тексты сайта — включая агентов-копирайтеров.** Машиночитаемый источник правды: `src/lib/copy-limits.ts`. Проверка: `npm run check:copy`.

Числа не назначены на глаз: замерена фактическая ёмкость строки на мобильном (390 px — узкое место, десктоп заведомо шире) в настоящем контейнере каждой роли. «Комфортно» — столько знаков, сколько ложится в комфортное число строк; «предел» — на строку больше, дальше блок ломается.

**Главное правило: длинный заголовок не лечится уменьшением кегля.** Кегль — часть иерархии; подгонять его под текст значит разрушать иерархию ради одного заголовка. Лечится текст: длинное уходит в лид под заголовком.

Где это работает само:
- **Админка** — `CopyLengthHint` / `CopyLengthNotice` под полями в Route Texts и Конструкторе: счётчик становится жёлтым за комфортом и красным за пределом, с объяснением, что именно сломается.
- **Вёрстка** — заголовки карточек ограничены `line-clamp-2`: перелёт деградирует многоточием, а не рвёт сетку. Это страховка, а не разрешение писать длинно.
- **Проверка** — `npm run check:copy` проходит по коду (роль определяется тегом: h1/h2/h3) и по публичным полям Airtable. Падает только на перелётах; «длинновато» не блокирует.

Не проверяются намеренно: строки программы тура (Day Items, Route Days) — они переносятся свободно и сетку не держат. Лимиты существуют для блоков фиксированной формы, а не для любого текста.

### Типографика: типографер на рендере (2026-07-30, аудит `docs/typography-audit-2026-07-29.md`)

Подключено в 24 отображающих компонентах через `typoDeep(props)`, в копирайт-константах страниц и `src/data`, а также там, где компонент забирает данные сам (журнал, события, SEO-поля маршрутов).

**Правила, которые нельзя нарушать:**

1. **Типографер стоит на границе показа, а не на границе чтения данных.** Логика обязана видеть сырой текст: `tour-pricing` ищет подстроку «частный транспорт», `working-hours` парсит часы, фильтры сравнивают строки. Не переносить `typoDeep` в слой Airtable. Единственное исключение — `getMultiDayRouteSeoFields` (там всё поля-витрины), оно подписано в коде.
2. **В клиентских компонентах — только через `useMemo(() => typoDeep(props), [props])`.** `typoDeep` создаёт новые объекты; без мемоизации они уходят в зависимости хуков, и эффект с `setState` на `[stops]` в `IntercityRouteTimeline` даёт бесконечный цикл.
3. **Не расширять типографер правилами, требующими понимания смысла.** Числовой диапазон неотличим от японского адреса `Асакуса, 1-32-11`, десятичная точка — от даты `18.07`, границы цитаты регуляркой не вычисляются. Это правится в данных (`scripts/fix-airtable-typography.mjs`, dry-run по умолчанию) и ловится через `npm run check:typography`.
4. **PDF не типографируем.** Причина одна: pdfkit ломает строку по `\s`, куда U+00A0 попадает, — то есть перенос всё равно случится, а смысл неразрывного пробела теряется. Глифов это не касается: проверено, U+00A0, тире и многоточие в PT Sans и PT Serif есть; отсутствует именно U+2009, из-за которого в прошлый раз печатались квадраты. `/p/<token>` и печатное превью идут через `PrintProgramDocument` и типографируются, PDF — нет.
5. **`metadata` не трогаем** — в однострочном обрезаемом `<title>` неразрывные пробелы не видны, а SEO-строки без выгоды лучше не менять.

**Антиква только на h1/h2** (решение владельца 2026-07-30). h3 — гротеск Geist Medium: это заголовки карточек, шагов и FAQ, то есть подчинённый уровень, и антиква на подписи в 18–20 px читается как блог, а не как редакционная уверенность.

**Микротипографика в базовом слое:** висячая пунктуация (`hanging-punctuation`, пока только Safari), `text-wrap: pretty` на абзацах против висячих слов, табличные цифры в метках и подписях, подчёркивание ссылок ниже базовой линии. Всё это прогрессивные улучшения — там, где браузер не поддерживает, просто ничего не происходит.

**Границы в `SKIP_KEYS`** (`type`, `mode`, `status`, `slug`, `href`, …) — ключи логики. `name`, `alt`, `value` намеренно НЕ в списке: это видимый текст. Латинские значения типографер и так возвращает как есть.

### КАНОН транслитерации географических названий (владелец, 2026-07-14)

По умолчанию — система Поливанова (Дзуйходэн, Этиго-Цумари, Мацусима). НО устоявшиеся поисковые написания имеют приоритет — решение владельца в пользу SEO-практики. Текущие исключения: **«Хаконе»** (НЕ «Хаконэ») — везде: код, Airtable, метаданные, включая производные (Хаконе Дзиндзя, Мотохаконе, Хаконемати). Унификация проведена 2026-07-14 (код + все таблицы Airtable). Новые исключения добавлять **только** в `POLIVANOV_EXCEPTIONS` (`src/lib/polivanov.ts`) — оттуда правило расходится само.

**Как решается спор о написании (владелец, 10.08.2026).** Счёт по русской Википедии: `insource:"форма"` для ОБЕИХ форм, с одним и тем же фильтром на японский контекст. Симметрия обязательна — асимметричный замер дал «Кобе» ×5,3 вместо настоящих ×3,7. Регулярным выражением не мерить: оно ловит подстроку и приписывает «Кобе» ещё и Кобеляки (3540 вместо 113).

Замер решает только там, где корпус толстый: Токио ×430, Иокогама ×14,5, Кобе ×3,7, Хакодате ×2,2. Где корпус тонкий — Хаконе 27:23, Сендай 110:109 — решает владелец, и это записывается как решение, а не выдаётся за измерение. Подмена здесь реальна: Википедия мерит корпус энциклопедии, а канон сайта обоснован ПОИСКОМ, и у «Хаконе» счёт даёт ничью при однозначном решении владельца от 14.07.2026.

Google для замера не годится: русские имена есть лишь у 21% нашей базы, и среди них озеро Акан подписано по-сербски, а Сирахигэ — через «ши», вопреки канону.

**Правило теперь исполняется, а не пересказывается (10.08.2026).** Три года оно жило прозой здесь, в промпте исследователя и таблицей исключений в коде — и не стерегло ни один путь записи: агенты через транслитератор не ходят, они пишут имя сами. Замер показал 58 вхождений «Хаконэ» в POI и ещё 144 в маршрутах, включая утверждённые описания и SEO-заголовки, то есть текст, уехавший на сайт. Теперь `canonicalText()` чинит написание на входе в канон, а список запрещённых форм не ведётся руками, а **выводится**: для каждого исключения считается, что дал бы чистый Поливанов, и расхождение с каноном и есть запрещённая форма. Добавили строку в `POLIVANOV_EXCEPTIONS` — запрет появился сам. Замена идёт подстрокой, поэтому производные (Мотохаконе, Хаконемати) чинятся вместе с корнем.

### КАНОН: японские топонимы не склоняются (владелец, 2026-08-01)

«Я не люблю склонять японские топонимы за редкими исключениями» — решение владельца. По умолчанию названия остаются в исходной форме во всех падежах: «от Гинза до Сибуя», «в Сибуя», «с Гинза», «у статуи Хатико в Сибуя», «переехала на Тоёсу».

Исключения — устоявшиеся написания, которые уже склоняются в русском повсеместно и режут глаз в неизменяемом виде: Токио (не склоняется само по себе), Киото, Осака («в Осаке» допустимо, если так уже написано на сайте). Новые исключения добавлять сюда по решению владельца.

**Проверено на корпусе (10.08.2026).** Правило не объявлено, а измерено: владелец просмотрел 188 живых фраз базы в виде «было → стало» и вернул НОЛЬ. Его формулировка: несклоняемый вариант работает во всех случаях, склоняемый — нестабильно. База приведена (316 замен в 112 записях), соблюдение стережёт `npm run check:canon`. Список защищённых топонимов — `INDECLINABLE_TOPONYMS` в `src/lib/polivanov.ts`; падежные формы оттуда выводятся, а не перечисляются.

Правило распространяется на публичные тексты, FAQ и тексты в Airtable. Оно НЕ переопределяет канон транслитерации (Поливанов + устоявшиеся поисковые написания, см. выше) — это отдельный вопрос: как писать, а не как склонять.

### КАНОН формулировок видов транспорта (владелец, 2026-07-11)

В любом публичном тексте и в UI конструктора используются ТОЛЬКО эти термины: **Самостоятельно / Общественный транспорт / Частный транспорт / Заказной транспорт / ЖД / Авиа**. Другие формулировки не вводить. ЗАПРЕЩЕНЫ (юридические соображения): «автомобиль с гидом», «машина с гидом», «гид с машиной», «гид-водитель» — этот формат публично называется «частный транспорт», без расшифровки, кто за рулём. «С гидом» как отдельная переменная сопровождения (чекбокс) — допустимо; «без гида» = «самостоятельно». Термин «синкансэн» в лейблах транспорта заменён на «ЖД».

### Транспортная доктрина (фундаментальное бизнес-правило владельца, 2026-07-06)

Любой публичный текст (страницы, FAQ, метаданные) обязан подавать передвижение так:

- **Внутри города** (Токио, Киото): общественный транспорт уместен, может быть частью опыта.
- **Большие переезды между регионами**: синкансэны и суперэкспрессы — да, комплиментарно, обязательная часть тура и логистики.
- **Вне мегаполисов / в глубинке**: автомобиль с гидом — основной формат (двери-в-двери от отеля, свой темп, вещи в багажнике, остановки по пути).
- **VIP**: лимузин-сервис — упоминать как опцию, когда уместно.
- **Локальные электрички/автобусы между городами**: только справочно, с маркером «для самостоятельных поездок». Никогда — как формат тура с гидом для индивидуалов (так ездят разве что сборные группы).

Нарушение = переписывание. Эталон правильной подачи — FAQ Хаконэ (Airtable Routes.FAQ, живой на /intercity/hakone). Расширенная версия с примерами «было → стало» живёт в Cowork-скилле `jumboinjapan-faq-writer`; суть продублирована здесь, потому что Claude Code скиллы Cowork не видит.

### КАНОН: продолжительность тура не выносится в тексты и документы (владелец, 2026-07-18)

Число дней программы — переменный и опциональный параметр под конкретного клиента, а не свойство тура. Поэтому:

- НЕ выводить продолжительность («N дней», «N-дневный») в распечатки (PDF-обложка, печатное превью, публичная страница `/p/<token>`), в генерируемые описания (fallback meta description, подписи карточек) и в новые публичные тексты о турах конструктора.
- НЕ зашивать число дней в автогенерируемый slug (`-19-days` в URL врал бы после изменения программы; легаси-хвосты `-N-days` у существующих slug'ов не трогать — это постоянная идентичность записи).
- Допустимо: нумерация дней внутри программы («ДЕНЬ 1», даты), machine-readable `duration` в schema.org JSON-LD, внутренние админ-поверхности (карточка клиента, расчёт стоимости, шапка билдера) и осознанные диапазоны в кураторском копирайте статических модельных туров («7–8 дней», «От 4 дней»).

Реализация первой волны: коммиты `a047011` (документы и описания) и далее (slug). При написании нового кода/копирайта — соблюдать по умолчанию.

### Канон транспорта и тона (2026-07-18, решения владельца)

Классификация: **Общественный транспорт** = метро/ЖД/автобусы + такси + Uber Black Van; **Заказной транспорт** = лимузин-сервисы (MK Taxi, Hinomaru Limousine и аналоги); **Частный транспорт** = транспорт по договорённости с гидом (без указания гида как водителя). Публичные ярлыки карточек — только канонические термины; такси/лимузин/бренды — только внутри описаний.

Подача: три опции сквозные; карточки одинаковые для всех туров одного ТИПА, не отдельного тура. Типы: Токио (day-one, day-two, hidden-spots) / Выездные экскурсии (все intercity + Такао и Митакэ) / Многодневные. Карточка передаёт уровень комфорта в контексте типа тура, без логистических деталей (ветки, линии метро, пересадки — запрещены). Выездные: частный — наиболее выгодно, общественный — деликатно пессимизирован, заказной — оптимизирован без люкс-акцента (без ощущения расслоения).

Тон: повелительное наклонение к клиентам строго запрещено («идите», «попробуйте», «возьмите» — просторечие). Регистр — люксовый консьерж: деликатно передавать ощущение, по-деловому, без приторности. Кнопки-инфинитивы («Обсудить маршрут») допустимы. Slug заказного формата: `/city-tour/charter` (бывш. `/limousine`, 301 в next.config.ts).

### КАНОН: закрытый POI в программу не ставится (владелец, 2026-08-10)

Поле **Operating Status** у POI: `Работает` | `Сезонный` | `Закрыт временно` | `Закрыт навсегда` | `Не проверено`. Решение принимает `checkProgrammeUsable()` в `src/lib/poi-canon.ts` — это ЕДИНСТВЕННОЕ место, где правило записано; в агентах и промптах его дублировать нельзя, иначе разойдётся.

- Ставить точку в день тура при статусе `Закрыт временно` / `Закрыт навсегда` — запрещено.
- `Сезонный` — НЕ разновидность закрытого. Google не различает межсезонье и закрытие и отдаёт сад слив в Судзуке (POI-000005) как `CLOSED_TEMPORARILY` одиннадцать месяцев в году. Автопрогон `operatingStatusFromGoogle()` сезонность не затирает; ставить сезонную точку можно, сверив даты тура с окном в Working Hours.
- `Не проверено` не блокирует, но обязывает сверить состояние перед выдачей гостю.
- **«Работает» не ставится исследованием.** Бот приёма (`RESEARCH_SYSTEM_PROMPT`) заполняет статус только при подтверждённой находке о закрытии или сезонности; «Работает» приходит из `businessStatus` Google, потому что это единственный статус, действующий без замечаний, и он обязан быть проверяемым. `parseResearchJson` подрезает «Работает» из ответа модели, даже если та его написала.
- Завести закрытую точку в базу МОЖНО и нужно: `applyCanon` даёт по ней `warn`, а не `error`. Запрет на запись означал бы, что база не помнит о закрытии, и коллектор заведёт объект заново как незнакомый.

### БАЗА — ОСНОВАНИЕ ПРОЕКТА (владелец, 10.08.2026)

«База данных лежит в основе всего проекта. Она должна быть безупречна с точки зрения технического исполнения и полезности содержания» — решение владельца после двух дней, ушедших на разбор ошибок приёма поштучно.

Вывод из этих двух дней: **ошибки находились случайно и по одной, потому что эталон нигде не был записан.** Пустое описание, текст в неверном поле, имя без английской пары, выдуманный текст, кафе вместо холмов — каждая находка была отклонением от нормы, которую никто не сформулировал.

Эталон записан в `docs/poi-standard.md`, мерка к нему — `npm run poi:score`. Мерка НЕ падает: она показывает расстояние до цели, а не поломку. Падают `check:canon` и `check:poi` — там нарушения.

**Классов записей три, и мерить их одной меркой нельзя.** Обычная, родительская (держит связку, координат нет намеренно), служебная. Первая попытка посчитать «записи без описания» дала 29 и оказалась бессмысленной: шесть из них — зоны Этиго-Цумари, у которых описания и не должно быть. Мерка, не различающая классы, ругает исправное и молчит про сломанное.

Замер на 10.08.2026: обычные 86%, родительские 97%, служебные 91%.

За один день нашлись ТРИ канона, записанных прозой и не стерегущих ничего: написание топонимов (58 вхождений «Хаконэ» в POI и 144 в маршрутах, включая утверждённые описания и SEO-заголовки), склонение (128 мест), тождество place_id. - **Серверные предохранители сохранения Конструктора** (`saveMultiDayBuilderRoute`, `src/lib/multi-day-builder-storage.ts`). Урок инцидента: клиентские guard'ы не защищают базу — прод может крутить старый клиент. Теперь сервер сам отклоняет разрушающие записи (HTTP 409 + код):
  - `SHRINK_BLOCKED` — входящая программа ≤2 блоков или меньше половины существующей (при существующих ≥5): похоже на случайную перезапись пустым состоянием. Override: повторное «Сохранить» в течение 15 с (клиент шлёт `saveOptions.allowShrink`).
  - `DEMOTE_BLOCKED` — попытка увести Published-маршрут в другой статус побочным эффектом сохранения. Override аналогично (`allowDemote`).
  - `SYNC_CONFLICT` — optimistic concurrency по `Last Builder Sync`: клиент шлёт штамп, который загрузил; расхождение = базу менял кто-то ещё; override НЕТ, только перезагрузка маршрута. Сервер возвращает новый штамп (`builderSync`) в ответе сохранения, клиент обновляет его в состоянии.
  - `SLUG_TAKEN` — сохранение с изменённым slug (переименование) в slug, занятый другой программой; override НЕТ.
  - **Идентичность и переименование**: slug — ключ upsert'а. У сохранённого маршрута slug НЕ регенерируется из названия/числа дней (это плодило программы-дубли); slug редактируется явным полем в Параметрах, клиент шлёт `saveOptions.previousSlug`, сервер патчит ту же запись Routes (rename, не создание) и подчищает детей под старым slug после успешной записи новых. Смена slug опубликованного тура меняет публичный URL без редиректа — предупреждение в UI.
  - **Автобэкап**: перед каждой перезаписью существующего маршрута полный снапшот программы уходит в Routes.'Program Backup' (`fld1Bvnjvbe1CDtCV`, JSON `{backedUpAt, route}`). Один уровень глубины — два подтверждённых ошибочных сохранения подряд затирают и бэкап. Ошибка бэкапа сохранение не блокирует (логируется).
  - Никогда не ослаблять эти предохранители «чтобы не мешали» — сначала разбираться, почему они сработали.
