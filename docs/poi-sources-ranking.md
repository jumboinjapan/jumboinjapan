# Источники POI: реестр, ранжирование и модель весов

**Дата:** 6 августа 2026
**Список источников:** зафиксирован владельцем, восемь позиций
**Статус:** первый прогон выполнен, веса расставлены

## 1. Решение, которое требует вашего подтверждения

**`en.japantravel.com` исключён из прогона.**

Их `robots.txt` поимённо блокирует `ClaudeBot`, `Claude-Web`, `Claude-SearchBot`, `anthropic-ai`, `GPTBot`, `ChatGPT-User`, `OAI-SearchBot`, `Google-Extended`, `PerplexityBot` — и отдельно `Scrapy`. Комментарий в файле их словами: «AI / LLM training crawlers — blocked due to load and zero SEO benefit».

Отдельного пункта про AI в их Terms of Service нет — документ датирован 23 июля 2018 года и с тех пор не обновлялся. То есть позиция выражена только технически, но выражена недвусмысленно и поимённо.

Обойти её можно единственным способом — подменив User-Agent. Это сознательная выдача себя за другого, и делать этого я не буду. В реестре источник помечен `enabled: false`, `blockedReason: 'robots-ai-optout'`.

**Что это значит для вас практически.** Ваш действующий `scripts/import-japantravel-events.mjs` ходит именно туда. Это решение старше нашего разговора, и оно ваше. Два факта в помощь: их ToS содержит фразу «Abstracting with credit to JT and our URL is permitted and encouraged» — реферирование со ссылкой они прямо поощряют; и там же «we expect to be compensated for any reuse» — коммерческое использование выведено в платную лицензию. Контакт для переговоров есть на сайте.

## 2. Главная техническая находка

**Шесть источников из восьми не публикуют никакого машиночитаемого сигнала свежести.** Замерено, не предположено:

| Источник | sitemap lastmod | JSON-LD dateModified | HTTP Last-Modified | Итог |
|---|---|---|---|---|
| japan-guide.com | ✗ нет sitemap | ✗ | ✗ | **нет сигнала** |
| japan.travel (JNTO) | ✗ таймаут | ✗ | ✗ | **нет сигнала** |
| visit-hokkaido.jp | ✗ нет sitemap | ✗ | ✗ | **нет сигнала** |
| shikoku-tourism.com | ✗ нет sitemap и robots | ✗ | ✗ | **нет сигнала** |
| en.japantravel.com | ✗ нет sitemap | ✗ | — | **нет сигнала** |
| jtb.co.jp | ✗ | ✗ | только на ассетах | **нет сигнала** |
| japanstartshere.com | ✓ | ✓ | — | **полный сигнал** |
| kyushujourneys.com | ✓ 100% из 51 URL | ✗ | — | **есть сигнал** |

**Следствие:** требование «свежее доминирует над старым» нельзя выполнить, доверяя заявленным датам — у большинства источников их нет. Свежесть приходится **измерять самим**: снимать отпечаток содержания при каждом прогоне и смотреть, что реально изменилось между прогонами.

Отсюда две шкалы в модели:

- **declared** — что источник о себе заявил. Может врать: CMS обновляет `lastmod` при любой правке шаблона.
- **measured** — что мы увидели своими глазами между прогонами.

**measured сильнее declared.** При расхождении берётся худшее из двух — сайт, который пишет в sitemap сегодняшнюю дату, не меняя ни слова в содержании, получает возраст по содержанию, а не по заявлению.

На первом прогоне measured отсутствует — это не ошибка, а честное «пока не знаем». Свежесть измеряется временем, а не одним запросом.

## 3. Модель весов

Требование «свежее доминирует» верно **не для всех фактов**. Координаты храма Тодайдзи и его история не меняются — там должен побеждать авторитетный источник, даже если его страница не трогалась три года. Часы работы и цена билета устаревают за месяцы — там свежая запись блога полезнее старой страницы национальной турорганизации.

Поэтому вес считается **отдельно для двух классов полей**:

| Класс | Поля | Что доминирует |
|---|---|---|
| **stable** | имя, координаты, адрес, категория, история | **авторитет** |
| **volatile** | часы, цена, статус работы, доступ, сезонность, сайт, телефон | **свежесть** |

```
w = authority^aExp × freshness^fExp

stable:    aExp = 1,0   fExp = 0,3
volatile:  aExp = 0,5   fExp = 1,5
```

Множитель свежести по возрасту факта: ≤90 дней → 1,00 · ≤365 → 0,70 · ≤730 → 0,40 · старше или неизвестно → **0,15**.

Неизвестная свежесть штрафуется так же, как двухлетняя давность. Это намеренно: молчание источника о своей актуальности — не нейтральный факт.

Шкала авторитета (ставится руками в реестре, не вычисляется машиной — это ответственность владельца):

| Значение | Кто |
|---|---|
| 1,00 | первоисточник — официальный сайт самого объекта |
| 0,90 | национальная или префектурная турорганизация |
| 0,85 | энциклопедический справочник с редакцией |
| 0,60 | коммерческий туроператор |
| 0,50 | UGC-платформа |
| 0,40 | частный блог одного автора |

**Проверка модели на крайних случаях** (`node scripts/poi-portals/lib/weights.mjs`):

| Случай | Свежий блог (0,40 / 10 дней) | Старый DMO (0,90 / 1200 дней) | Кто побеждает |
|---|---|---|---|
| волатильное поле | **0,6325** | 0,0551 | блог, в 11 раз |
| стабильное поле | 0,4000 | **0,5094** | DMO |

Ровно требуемое поведение.

### Две ошибки, которые прогон поймал сам

Первый запуск дал ложные показания, и это стоит зафиксировать, потому что такие вещи молча портят веса:

1. **JTB измерился по CSS-файлу.** Шаблон ссылок `/leisure/` поймал `/leisure/wroot/css/base.css`, и возраст источника посчитался по дате вёрстки — 573 дня. После фильтра ассетов JTB честно показывает «неизвестна».
2. **Kyushu Journeys измерился по пустой странице.** В выборку попали `/terms-and-conditions/` (59 символов, страница физически пуста) и `/privacy-policy/`. У них свежий `lastmod`, потому что CMS трогает их при каждой перекатке. Свежесть завышалась.

Исправлено: свежесть замеряется только по содержательным страницам — не ассеты, не служебные разделы, минимум 1500 символов текста.

### Проверка второго прогона

Механизм измеренного дрейфа проверен на подготовленном снимке 60-дневной давности, где 3 из 5 страниц Kyushu Journeys помечены как изменившиеся:

```
ИЗМЕРЕННЫЙ ДРЕЙФ: compared 5, changed 3, changeRate 0.6,
                  daysBetween 60, impliedAgeDays 100
```

Источник **заявлял** возраст 0 дней (sitemap сегодняшний), **измерение** дало 100 дней. Модель взяла худшее, и волатильный вес упал с **0,7746 до 0,4537**.

Это и есть главный смысл конструкции: сайт, который обновляет `lastmod` без изменения содержания, автоматически теряет вес со второго прогона.

## 5. Разрешение конфликтов на уровне поля

Когда источники дают разные значения одного поля, побеждает наибольший вес. Но победа — не всё: важнее, что видно **почему**.

| Случай | Победитель | Согласие | Расхождение | Человек |
|---|---|---|---|---|
| часы: свежий блог vs JNTO трёхлетней давности | japanstartshere | 0,92 | **да** | **да** |
| координаты: те же двое | jnto-japan-travel | 0,56 | да | нет |
| цена: три источника согласны | bodik-osaka | 1,00 | нет | нет |
| часы: единственный источник | bodik-osaka | 1,00 | нет | нет |

**Важный нюанс, который пришлось развести отдельно.** В первом случае взвешенное согласие вышло 0,92 — просто потому, что у возражающего источника почти нет веса. Формально «согласие высокое», фактически источники прямо противоречат друг другу.

Смешивать это нельзя. По волатильным полям человек вызывается на **любое расхождение**, а не только на низкое взвешенное согласие: цена ошибки здесь — клиент у закрытых ворот. Модель при этом всё равно считает победителя, так что человек **подтверждает готовый ответ, а не ищет с нуля**.

По стабильным полям расхождение человека не требует — там разница в шестом знаке координат не стоит внимания.

## 6. Роли источников: они не взаимозаменяемы

Восемь зафиксированных источников — это три разных инструмента, и мешать их в один рейтинг «лучше/хуже» было бы ошибкой:

| Роль | Источники | Что берём | Чему НЕ верим |
|---|---|---|---|
| **discovery** | japan-guide | какие объекты вообще существуют, редакторская оценка «стоит ли ехать» | часам работы (нет сигнала свежести) |
| **verify** | JNTO, visit-hokkaido, shikoku-tourism, открытые данные | официальные названия, адреса, базовые факты | ничему волатильному без сверки |
| **signal** | japanstartshere, kyushujourneys, JTB | что сейчас на слуху, что продаётся, сезонность | фактам об объектах вообще |

`japan-guide` в роли discovery особенно ценен: их страница `/e/e623a.html` — вход в справочник на 226 направлений, и у них есть собственный рейтинг объектов, которого нет больше нигде. Именно на нём стоит строить приоритет обхода.

`kyushujourneys` — **прямой конкурент**: лицензированный туроператор по Кюсю (合同会社Starbright Concepts, Travel Agent No. 2-873), тот же профиль, что у вас. Всего 51 страница, как справочник бесполезен. Ценность одна — видеть, что конкурент собирает в маршруты. Отмечен в реестре флагом `competitorRisk` (см. следующий раздел).

`jtb.co.jp` — витрина бронирования, не справочник. По соотношению «риск / польза» худший из восьми: сервер отвечает 5,4 секунды, фактов об объектах не даёт, но показывает, что крупнейшее японское турагентство продаёт прямо сейчас.

## 7. Правовой контур

Проверено по условиям использования каждого источника.

**Ни один из восьми не разрешает копирование своего описательного текста.** Это не блокирует задачу — вы и так пишете свои тексты — но задаёт жёсткое правило конвейера:

> Описание источника используется как **сырьё для извлечения фактов** и в базе **не сохраняется**. Сохраняются факты и ссылка на источник.

**Отдельно и важно:** перевод чужого описания на русский — это **производное произведение** (著作権法 ст. 27, право на перевод и переработку), а не свой текст. Граница проходит так: писать от фактов — да; писать, глядя в исходный абзац, — нет. Это ровно та дисциплина, которая уже описана в `CLAUDE.md` для ваших копирайтерских скиллов.

Что говорят источники:

- **japan-guide:** «No part of this web site may be reproduced without the written permission». Коммерческим считают в том числе любой сайт с рекламой. Короткие цитаты разрешены без запроса.
- **JNTO:** самая жёсткая формулировка — среди охраняемых компонентов прямо названы «databases», запрещено даже «stored for private use». Заявленное шире того, что даёт закон (факты не охраняются; ст. 12の2 требует творческой структуры), но расхождение — вопрос к юристу. Плюс `/*/travel-directory/*` закрыт в robots — это как раз каталог объектов.
- **shikoku-tourism:** самая дружелюбная — «著作権法上、認められる場合を除き», прямая отсылка к статутным исключениям без попытки расширить охрану договором. Отдельно: **прямое исключение для турфирм** по фотографиям — «旅行会社様が四国の旅行商品造成を目的としてご使用になる場合は、その使用を妨げるものではありません». Применимость к иностранному оператору — вопрос к юристу. Подсудность: 高松地方裁判所.
- **visit-hokkaido:** 無断使用・転載禁止, охрана заявлена на «文書・画像» — на выражение, не на факты. robots разрешает всё явно.
- **japanstartshere, kyushujourneys, jtb:** страницы условий фактически не существует (у Kyushu она есть, но физически пуста; у JTB общесайтового 利用規約 нет вовсе — только членское). Действует авторское право по умолчанию.

**Два риска вне авторского права, которые важнее копирайтных:**

1. **Нагрузка.** Дело 岡崎市立中央図書館 (Librahack, 2010): человека задержали по 偽計業務妨害 при частоте **1 запрос в секунду** — потому что на другой стороне оказалась хрупкая система. Прокуратура прекратила дело, экспертиза AIST установила, что неисправна была библиотечная система, а не краулер. Урок прямой: строго последовательный обход, пауза 2 секунды, честный User-Agent с контактом. В коде это зашито и прокомментировано.
2. **Конкурент.** Дело 翼システム (Токийский окружной суд, 2001–2002): база данных истца была признана **не** охраняемой авторским правом, но суд присудил возмещение по ст. 709 ГК Японии (деликт), потому что копирующий вышел на конкурирующий рынок. Для `kyushujourneys` это ровно та фактура. Внутреннее использование без перепродажи данных отличается от обстоятельств дела, но граница проходит здесь.

**Самое сильное снижение риска, которое видно из всего материала:** для часов работы, адреса и доступа канонический источник — **официальный сайт самого объекта** (храма, музея, парка), а не агрегатор. Это одновременно точнее (агрегаторы устаревают — что таблица весов и показывает) и почти полностью выводит вопрос из-под чужих условий использования. Восемь зафиксированных источников лучше использовать для **обнаружения** объектов, а сверку вести по первоисточнику. В шкале авторитета под это уже зарезервировано значение 1,00.

Вопросы, где нужен юрист, а не я: граница ст. 30の4 (информационный анализ) для конвейера, сохраняющего чужой текст ради последующего извлечения фактов; применимость 翼システム к вашей базе; объём исключения Сикоку для иностранного оператора; статус существующего импортёра japantravel.

## 8. Что добавилось в код

```
scripts/poi-portals/
  registry.mjs             ← переписан: 8 зафиксированных источников
                             + роль, авторитет, robots, свежесть, лицензия
  profile-sources.mjs      ← НОВОЕ: первый прогон, профилирование, ранжирование
  lib/weights.mjs          ← НОВОЕ: модель весов + разрешение конфликтов
  lib/freshness.mjs        ← НОВОЕ: robots, заявленная и измеренная свежесть
  lib/opendata-csv.mjs       без изменений
  lib/scoring.mjs            без изменений
  lib/dedupe.mjs             без изменений
  lib/enrich.mjs             без изменений
```

Запуск:

```bash
# первый прогон — заявленная свежесть, ранжирование
node scripts/poi-portals/profile-sources.mjs --out tmp/sources-t1.json --samples 5

# второй прогон через месяц — включается измеренная свежесть
node scripts/poi-portals/profile-sources.mjs --previous tmp/sources-t1.json --out tmp/sources-t2.json

# самопроверка модели весов
node scripts/poi-portals/lib/weights.mjs
```

Прогон занимает около 5 минут — это следствие паузы в 2 секунды между запросами, и сокращать её не нужно.

## 9. Что делать дальше

1. **Повторить прогон через 3–4 недели** с `--previous`. Только тогда включится измеренная свежесть, и веса станут основанными на фактах, а не на заявлениях. Это единственный шаг, который нельзя ускорить.
2. **Решить по `en.japantravel.com`** — оставить исключённым или начать переговоры о лицензии.
3. **Проставить авторитет руками.** Сейчас значения выставлены по типу источника. Вы знаете эти сайты лучше — если japan-guide в ваших глазах точнее JNTO, это правится одним числом в реестре.
4. **Добавить первоисточники объектов** (сайты храмов и музеев) с авторитетом 1,00 — по волатильным полям они должны перебивать все восемь.
5. Дальше — шаг 1 дорожной карты из `docs/poi-portal-collector.md`: поля происхождения и координат в схеме POI. Без них писать в базу по-прежнему нельзя.
