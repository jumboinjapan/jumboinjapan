# ADR-0001. Таксономия POI v1

**Статус:** одобрен по направлению владельцем 11.08.2026. **К реализации не принят** — сначала реестр и тесты, порядок в разделе 13.
**Дата:** 11.08.2026, редакция 2 (после ревью владельца)
**Контекст:** разметка 132 объектов Осаки остановлена до принятия схемы — размеченный набор закрепил бы модель, которую мы собираемся менять.

---

## 1. Проблема

Одно поле `POI Category (RU)` отвечает сразу на пять вопросов:

| Вопрос | Пример значения |
|---|---|
| Что это за сущность? | Буддийский храм |
| Пускать ли в POI вообще? | Ресторан, Японский отель |
| В какую таблицу направить? | Ресторан → ресурсы, не POI |
| Какова туристическая функция? | Смотровая площадка |
| Как показывать в продукте? | Знаковый вид |

Отсюда список, где рядом стоят храм, ресторан, отель, транспортный узел, СПА и «Знаковый вид».

### Расхождение уже произошло — измерено 11.08.2026

Источников правды не один, а **четыре**, и они расходятся:

| Источник | Значений | «Знаковый вид» |
|---|---|---|
| `src/lib/poi-canon.ts` → `POI_CATEGORIES_RU` | 18 | есть |
| `scripts/poi-portals/lib/enrich.mjs` → промпт классификатора | 17 | нет |
| `scripts/poi-portals/lib/airtable-store.mjs` → `CATEGORY_RU_TO_EN` | 17 | нет |
| опции самого поля в Airtable | **20** | есть |

Живая база отвечает четвёртым списком, и в нём есть значения, которых нет ни в одном модуле: **«Ландшафтный сад» (7 записей), «Историческая локация» (7), «Парк» (6), «Городская достопримечательность» (3)**.

Ещё по 466 записям: **136 (29 %) без категории вовсе**, у **67** проставлено две и больше.

## 2. Решение: четыре поля вместо одного

Первая редакция смешивала в `catalog_target` адрес назначения, вид сущности и исход приёма. Разведено:

| Поле | Отвечает на вопрос | Значения | Кто присваивает |
|---|---|---|---|
| `entity_kind` | Что найдено | см. §3 | классификатор предлагает |
| `intake_disposition` | Что делать с находкой | `route` · `exclude` · `needs_review` | **детерминированная политика** |
| `catalog_target` | В какую базу | `poi` · `hotel` · `restaurant` · `event` · `experience` · `null` | **детерминированная политика** |
| `poi_primary_type` | Что это за POI | 19 типов, §4 | классификатор предлагает, человек утверждает |

Плюс два независимых слоя: `facets` (§6) и `badges` (§7), и отношения `relations` (`part_of`, `experience_at`, `view_of`, `depart_from`, `branch_of`) — согласованы в хендоффе, здесь не переопределяются.

**Почему маршрут не выводится из `poi_primary_type`.** Все 19 типов по определению относятся к POI: политике не из чего выбирать. Маршрут определяет `entity_kind`, который умеет сказать «это отель» и «это автовокзал».

`poi_primary_type` заполняется **только** при `catalog_target = poi`. В остальных случаях он `null`.

**Ключевое правило.** Модель классифицирует сущность. Маршрут выбирает политика: «очень известный ресторан» не становится POI оттого, что агент так решил.

Схема согласуется с внешними моделями: Schema.org допускает `TouristAttraction` как **дополнительный** тип к основному, а не вместо него; Overture разводит основной тип, иерархию и альтернативные категории. Иерархия и синонимы хранятся отдельно от кодов — обычный concept scheme в духе SKOS.

## 4. `poi_primary_type` — 19 листовых типов

Машинный код **неизменен**. Подписи RU/EN меняются **только версионируемо** (§5).

| Группа | Код | RU | EN |
|---|---|---|---|
| религия | `shinto_shrine` | Синтоистское святилище | Shinto Shrine |
| | `buddhist_temple` | Буддийский храм | Buddhist Temple |
| | `religious_site_other` | Другой религиозный объект | Religious Site |
| культура | `museum` | Музей | Museum |
| | `art_venue` | Галерея / арт-пространство | Art Venue |
| | `performing_arts_venue` | Театр / культурная площадка | Performing Arts Venue |
| наследие | `historic_site` | Историческое место | Historic Site |
| | `architectural_landmark` | Архитектурный объект | Architectural Landmark |
| | `castle_fortification` | Замок / фортификация | Castle |
| | `monument_public_art` | Памятник / публичное искусство | Monument |
| природа | `park_garden` | Сад / парк | Park & Garden |
| | `natural_landmark` | Природная достопримечательность | Natural Landmark |
| | `viewpoint` | Смотровая точка | Viewpoint |
| город | `tourist_district` | Туристический район | Tourist District |
| | `market` | Рынок | Market |
| | `shopping_street` | Торговая улица / квартал | Shopping Street |
| досуг | `amusement_park` | Парк развлечений | Amusement Park |
| | `zoo_aquarium` | Зоопарк / аквариум | Zoo & Aquarium |
| купание | `public_onsen` | Общественный онсэн / купальня | Public Onsen |
| резерв | `other_tourist_poi` | Прочий туристический объект | Other |

`other_tourist_poi` — **только ручное решение с обязательной заметкой**, автоимпорт с ним запрещён.

Неизвестный код → `needs_review`. Агентам запрещено добавлять типы автоматически.

**Тип — слабый сигнал дедупликации, но не доказательство идентичности.** Совпадение типа повышает вес пары в матчере; расхождение типа не опровергает дубль (один и тот же объект люди классифицируют по-разному). Тождество по-прежнему устанавливают идентификаторы и расстояние.

## 5. Коды и подписи: разный режим изменения

| Что | Режим |
|---|---|
| код (`buddhist_temple`) | **неизменен навсегда** |
| подпись RU/EN | меняется **только с новой версией реестра** и записью в `deprecated`/`renamed` |

Свободная правка подписей запрещена: отчёты и eval-фикстуры ссылаются на код, и если подпись под тем же кодом начнёт означать другое, старые наборы молча изменят смысл. Смена подписи — событие с версией, а не редактура строки.

## 6. `facets` v1 — только то, у чего нет своего поля

`hot_spring` (природный источник) · `onsen` (есть онсэн) · `spa` (есть СПА) · `night_view`

Из первой редакции **убраны**: `free_entry` (это билетная политика), `seasonal_bloom` (для этого есть `Season Window`), `indoor` (характеристика доступности). Facet не должен дублировать структурированное поле — иначе появляется второе место, где одно и то же может расходиться.

Facet — проверяемое по источнику свойство. На допуск не влияет и тип не заменяет.

---

## 7. `badges` — редакционный слой

`Знаковый вид` · `Выбор Jumbo` · `Сезонное место`

1. Бейдж **не тип и не facet**. Кинкакудзи — `buddhist_temple` + «Знаковый вид»; Shibuya Sky — `viewpoint` + тот же бейдж; красивый мост — `architectural_landmark` + тот же бейдж.
2. **Intake бейджи не присваивает.** Максимум — предлагает `badge_candidate` с обоснованием.
3. Присваивает редактор или отдельное правило публикации.
4. Не влияет на допуск, дедупликацию, маршрутизацию и тип.
5. Хранится в отдельном поле `POI Badges`.

«Сезонное место» как бейдж не подменяет `Season Window`: первое — решение показывать, второе — факт о работе объекта.

## 10. Решения владельца по спорным случаям

### 10.1. Каталог инфраструктуры не создаём

Два автовокзала не оправдывают подсистему. Запись выглядит так:

```text
entity_kind        = transport_infrastructure
intake_disposition = exclude
catalog_target     = null
exclude_reason     = infrastructure_not_catalogued
```

Появится конкретный потребитель — построение маршрутов, трансферы, места встречи — каталог заводится отдельным ADR.

### 10.2. Рыболовный пирс — место, а не впечатление

У него нет отдельного поставщика, расписания сеанса и брони, значит это не `experience`:

```text
catalog_target   = poi
poi_primary_type = other_tourist_poi
note             = recreational fishing facility
```

Автоимпорт запрещён. Наберётся несколько таких объектов — обоснованно добавим `outdoor_recreation_site`.

### 10.3. `滝見小路` — не торговая улица

Основная функция не розничная торговля. Если пространство само входит в маршрут:

```text
catalog_target   = poi
poi_primary_type = tourist_district
relation         = part_of Umeda Sky Building
```

Отдельные рестораны остаются в ресторанном каталоге. Если туристической ценности у самого пространства нет — записи не нужно.

### 10.4. Синонимы — по явной карте, спорное вручную

| Старое значение | Записей | Решение |
|---|---|---|
| Ландшафтный сад | 7 | автоматически → `park_garden` |
| Парк | 6 | автоматически → `park_garden` |
| Историческая локация | 7 | автоматически → `historic_site` |
| **Городская достопримечательность** | **3** | **только вручную** |

Последнее слишком расплывчато: под ним может скрываться район, мост, памятник или смотровая площадка.

Миграция обязана начинаться с **read-only прогона** в формате `recordId → old → proposed → mode → reason`. Запись — только после проверки прогона человеком.

### 10.5. Порядок: сначала реестр

XLSX, собранный до реестра, немедленно стал бы **пятым** источником правды.

## 11. Единый машинный реестр

`config/poi-taxonomy.v1.json` — единственный источник, из которого строятся проверки Intake, промпт классификатора, выпадающие списки XLSX, переводы RU/EN и сверка опций Airtable.

```jsonc
{
  "version": "poi-taxonomy/v1",
  "entityKinds": [
    { "code": "tourist_poi", "disposition": "route", "catalogTarget": "poi" },
    { "code": "transport_infrastructure", "disposition": "exclude",
      "catalogTarget": null, "excludeReason": "infrastructure_not_catalogued" }
  ],
  "poiPrimaryTypes": [
    { "code": "buddhist_temple", "group": "religion",
      "labels": { "ru": "Буддийский храм", "en": "Buddhist Temple" },
      "hints": { "ru": ["храм"] },
      "include": ["действующий или музеефицированный буддийский храм"],
      "exclude": ["ресторан или магазин с названием храма в адресе"] }
  ],
  "facets": [{ "code": "hot_spring", "labels": { "ru": "Природный источник", "en": "Hot Spring" } }],
  "badges": [{ "code": "iconic_view", "labels": { "ru": "Знаковый вид", "en": "Iconic View" },
               "assignedBy": "editor" }],
  "deprecated": [
    { "value": "Ландшафтный сад", "mapsTo": "park_garden", "mode": "auto" },
    { "value": "Городская достопримечательность", "mapsTo": null, "mode": "manual" }
  ]
}
```

Поле называется `hints`, а не `synonyms`, и это не косметика: «храм» по-русски применяют и к синтоистскому святилищу. Точным соответствием такой термин быть не может — он подсказка классификатору и не более.

`include` / `exclude` пойдут в промпт вместо голого списка названий — из-за него ресторан `松阪牛焼肉M 法善寺横丁店` стал буддийским храмом по фрагменту `法善寺` в адресе.

## 12. Миграция «Знакового вида»

Измерено на живой базе: **16 записей**.

| Случай | Записей | Что делать |
|---|---|---|
| Есть и другая категория | 11 | перенести бейдж, тип остаётся |
| **«Знаковый вид» — единственная категория** | **5** | тип назначить вручную: `POI-000534`, `POI-000535`, `POI-000536`, `POI-000537`, `POI-000546` |

Пяти записям после переноса не останется ни одного типа, поэтому порядок жёсткий:

1. Завести поле `POI Badges`.
2. Перенести значение у всех 16.
3. Назначить тип пятерым вручную.
4. Только затем убрать опцию из поля категорий.

Отдельным долгом: **136 записей без категории** и **20 опций в Airtable против 18 в каноне**.

## 13. Порядок работ

1. Исправить ADR — **сделано, эта редакция**.
2. Создать `config/poi-taxonomy.v1.json` и JSON Schema к нему.
3. Тесты: уникальность кодов, допустимость целей маршрута, полнота переводов, корректность `deprecated`-карты.
4. Генерировать из реестра промпт классификатора, проверки Intake, списки XLSX и сверку опций Airtable.
5. Пересобрать XLSX.
6. Разметить Осаку.
7. **Только по размеченной выборке** менять правила классификатора.

---

## 14. Чего эта ADR не делает

Не меняет код, пороги классификатора и Intake. Не трогает существующие записи. Не описывает внутренние таксономии каталогов отелей, ресторанов, событий и впечатлений — только границу, по которой записи туда уходят.
