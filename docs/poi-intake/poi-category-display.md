# Единый показ типов POI

Исправление 11.09.2026. Текущий реестр `poi-taxonomy/v5` остаётся единственным источником
кодов, подписей, фасетов и бейджей. Поля Airtable и правила классификации не менялись.

## Почему появились дубли

Экран POI строил фильтр из всех значений старого `POI Category (RU)`.
Читатель не передавал `POI Type`, хотя новый Intake уже записывал его. В старом
поле соседствовали синонимы, общие слова, отметки вида и объекты других каталогов.

## Чтение

`src/lib/poi-category.ts` обслуживает `airtable.ts` (админка и карточки программ)
и `multi-day-builder-data.ts` (подбор POI в конструкторе и остановках).

1. При заполненном `POI Type` проверяются четыре поля таксономии существующей
   `taxonomyRecordFields`. Валидный тип имеет приоритет над старой категорией.
   Неизвестный код, версия, источник или фасет требуют проверки; старое значение
   не маскирует повреждённый новый тип.
2. Без нового типа используются точные соответствия из `legacyCategoryMigrations`,
   совпадения с текущими подписями и обратное чтение существующего
   `legacy-airtable-category-bridge.mjs`. Отдельного списка синонимов нет.
   Несколько синонимов одного типа дают один тип; несколько разных типов
   требуют уточнения. Общие категории не превращаются в семантическую догадку.
3. «Знаковый вид» и другие известные бейджи показываются отдельно, без назначения
   типа. Особенности читаются из канонических фасетов. Прежние категории сохраняются
   в модели чтения и остаются доступны поиску админки.
4. Фильтр использует коды и показывает число карточек каждого типа. Все неразобранные
   карточки доступны через «Тип требует уточнения», их причина видна в карточке.
   В публичных карточках служебная претензия к типу не показывается.

Перенос точных соответствий происходит при чтении. `origin: legacy` означает
отображение по прежней категории, а не новую классификацию фактов. Поля базы,
исходные категории, Type Source, опубликованные тексты и связи не перезаписываются.
Это позволяет исправить интерфейс сразу, сохранив данные для отдельного разбора.
Дальнейшее исправление Draft/Todo выполняется существующим draft-revision;
массовая миграция и опубликованные записи требуют собственного состава и проверки.

## Сверка базы

Команда только читает. Полный список соответствий, причин и исходных категорий
остаётся локальным файлом. Уже существующий файл отчёта не перезаписывается.

```bash
npm run poi:categories -- --live --out tmp/poi-categories-report.json
npm run poi:categories -- --fixture tmp/poi-snapshot.json --out tmp/poi-categories-offline.json
```

Фикстура — массив `{recordId, fields}`. Живая ветвь загружает `.env.local` и
постранично читает только необходимые поля POI; служебные записи исключены.
В отчёте: `counts.canonical`, `counts.legacy`, `counts.review`, все `rows`,
`requests`, `writes: 0`. Сумма трёх исходов равна `total`.

Снимок 11.09.2026: **734 POI**, из них 274 с каноническим типом, 171 с точным
legacy-соответствием, 289 требуют уточнения. 11 служебных блоков в этот состав
не входят. Среди 289 есть 124 записи без прежней категории; остальные имеют
неоднозначные или конфликтующие значения. Это датированный результат,
актуальные числа определяет команда, а не эта таблица.
Артефакт: `tmp/poi-category-fix-2026-09-11/live-report.json`, восемь GET, ноль записей.

## Проверка

`tests/poi-category.mjs` проверяет каждый тип и точное соответствие, приоритет
канонического типа, конфликт нескольких категорий, повреждённые поля, отдельный
бейдж, сохранение всех строк, реальное чтение админки и конструктора на подменённом
HTTP, CLI на фикстуре и живую ветвь с подменённым GET. Набор входит в `npm test`.
Семантическую правильность 289 неопределённых карточек тест не доказывает.

## Туристический транспорт — 12.09.2026

По решению владельца добавлен тип `tourist_transport`: «Туристический транспорт».
Канатные дороги, туристические подъёмники и именованные прогулочные линии
с точкой посадки относятся сюда. Обычные станции и причалы без самостоятельной
туристической функции не переводятся сюда автоматически. Услуга без названной
локации остаётся в каталоге услуг. Агент оценивает предмет всей карточки;
новую категорию принимает существующий reviewed Intake.

Старые файлы v1/v2 неизменны. `storedTaxonomy` в единственном loader выбирает
текущую или предыдущую версию для чтения сохранённых карточек.
`storedTaxonomyRecord` проверяет старые коды по их собственной версии;
новый транспорт нельзя объявить записанным под v2. `taxonomyRecordFields`
принимает для новых записей только текущую версию. Массового обновления
карточек нет. Удаление поддержки v2 потребует отдельной миграции.

Инасаяма: владелец согласился учитывать Ropeway и Slope Car отдельно.
На официальном сайте 12.09.2026 Ropeway работает, Slope Car закрыт на ремонт.
Закрытие не относится ко всему парку или обоим подъёмникам.
Общий переход к многослойной матрице остаётся отдельным этапом.

Опция живой схемы добавляется через настройки существующего поля POI Type;
старый CLI создания четырёх полей не умеет расширять их опции. Снимок до
операции и область изменения — `tmp/poi-tourist-transport-2026-09-12/`.
12.09.2026 опция добавлена через интерфейс Airtable. Независимое чтение схемы
подтвердило ровно одно добавление: все прежние опции и остальные поля неизменны
(`schema-before.json`, `schema-after.json`, `schema-proof.json`). Первоначальная
ошибка инструмента доступа не подтверждала блокировку Мака; операция завершена
через прямое управление Chrome.
Записи POI этой операцией не меняются.

## Торговое пространство и транспортная инфраструктура — 12.09.2026

Владелец принял оба предложенных названия. В `poi-taxonomy/v4` добавлены:

- `shopping_complex` — «Торговое пространство»: торговые комплексы, аутлеты, именованные площадки с магазинами, сувенирами и едой. Применить к Pier 7, аутлету Сэндай и Michi-no-Eki Shiretoko Rausu.
- `transport_hub` — «Транспортная инфраструктура»: пассажирские пристани, станции и терминалы, используемые при построении маршрута. Применить к Нитода и Одомари, дочерним POI Тасиродзима.

Решения о регистрации этих мест уже приняты: повторных вопросов не нужно.
Канатки, туристические подъёмники и прогулочные суда остаются `tourist_transport`.
Грузовая и служебная инфраструктура не становится POI автоматически. Старый
`entityKind: transport_infrastructure` по-прежнему исключает нерелевантные
объекты; одобренная точка маршрута поступает как `tourist_poi` с типом
`transport_hub` через существующий reviewed Intake. Отдельный магазин
не превращается автоматически в торговый комплекс.

Текущая запись требует v5; сохранённые карточки v2/v3/v4 читаются по своей версии.
Прежние файлы реестра неизменны. Новые коды нельзя заявить под старой версией.
В живое поле POI Type добавлены ровно две опции; старые опции и остальные поля
не менялись. Доказательство: `tmp/poi-categories-v4-2026-09-12/schema-proof.json`.
Это снятие ограничений справочника, а не отчёт о создании оставшихся POI.

## Общественное пространство — 12.09.2026

Владелец выбрал этот тип для стадиона Mizuho PayPay Dome. Код `public_space`
добавлен в реестр v5; прежний v4 сохранён для чтения существующих карточек.
Подпись и фильтры используют общий loader, отдельного словаря для стадиона нет.
Тип описывает общественную или событийную площадку и не обещает свободный вход:
билет, афиша и ограничения сохраняются в фактах и примечаниях конкретного POI.
Парки, музеи и туристический транспорт сохраняют свои типы. Старой точной
категории Airtable нет — приблизительное legacy-значение не записывается.
В живую схему добавлен только `public_space`; прежние настройки сохранены.
Доказательство: `tmp/jg-last-four-2026-09-12/schema-verification.json`.
