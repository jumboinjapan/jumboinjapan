# Единый показ типов POI

Исправление 11.09.2026. Реестр `poi-taxonomy/v2` остаётся единственным источником
кодов, подписей, фасетов и бейджей. Поля Airtable и правила классификации не менялись.

## Почему появились дубли

Экран POI строил фильтр из всех значений старого `POI Category (RU)`.
Читатель не передавал `POI Type`, хотя новый Intake уже записывал его. В старом
поле соседствовали синонимы, общие слова, отметки вида и объекты других каталогов.

## Чтение

`src/lib/poi-category.ts` обслуживает `airtable.ts` (админка и карточки программ)
и `multi-day-builder-data.ts` (подбор POI в конструкторе и остановках).

1. При заполненном `POI Type` проверяются четыре поля таксономии существующей
   `taxonomyRecordFields`. Валидный тип имеет приоритет над старой категорией.
   Неизвестный код, версия, источник или фасет требуют проверки; старое значение
   не маскирует повреждённый новый тип.
2. Без нового типа используются точные соответствия из `legacyCategoryMigrations`,
   совпадения с текущими подписями и обратное чтение существующего
   `legacy-airtable-category-bridge.mjs`. Отдельного списка синонимов нет.
   Несколько синонимов одного типа дают один тип; несколько разных типов
   требуют уточнения. Общие категории не превращаются в семантическую догадку.
3. «Знаковый вид» и другие известные бейджи показываются отдельно, без назначения
   типа. Особенности читаются из канонических фасетов. Прежние категории сохраняются
   в модели чтения и остаются доступны поиску админки.
4. Фильтр использует коды и показывает число карточек каждого типа. Все неразобранные
   карточки доступны через «Тип требует уточнения», их причина видна в карточке.
   В публичных карточках служебная претензия к типу не показывается.

Перенос точных соответствий происходит при чтении. `origin: legacy` означает
отображение по прежней категории, а не новую классификацию фактов. Поля базы,
исходные категории, Type Source, опубликованные тексты и связи не перезаписываются.
Это позволяет исправить интерфейс сразу, сохранив данные для отдельного разбора.
Дальнейшее исправление Draft/Todo выполняется существующим draft-revision;
массовая миграция и опубликованные записи требуют собственного состава и проверки.

## Сверка базы

Команда только читает. Полный список соответствий, причин и исходных категорий
остаётся локальным файлом. Уже существующий файл отчёта не перезаписывается.

```bash
npm run poi:categories -- --live --out tmp/poi-categories-report.json
npm run poi:categories -- --fixture tmp/poi-snapshot.json --out tmp/poi-categories-offline.json
```

Фикстура — массив `{recordId, fields}`. Живая ветвь загружает `.env.local` и
постранично читает только необходимые поля POI; служебные записи исключены.
В отчёте: `counts.canonical`, `counts.legacy`, `counts.review`, все `rows`,
`requests`, `writes: 0`. Сумма трёх исходов равна `total`.

Снимок 11.09.2026: **734 POI**, из них 274 с каноническим типом, 171 с точным
legacy-соответствием, 289 требуют уточнения. 11 служебных блоков в этот состав
не входят. Среди 289 есть 124 записи без прежней категории; остальные имеют
неоднозначные или конфликтующие значения. Это датированный результат,
актуальные числа определяет команда, а не эта таблица.
Артефакт: `tmp/poi-category-fix-2026-09-11/live-report.json`, восемь GET, ноль записей.

## Проверка

`tests/poi-category.mjs` проверяет каждый тип и точное соответствие, приоритет
канонического типа, конфликт нескольких категорий, повреждённые поля, отдельный
бейдж, сохранение всех строк, реальное чтение админки и конструктора на подменённом
HTTP, CLI на фикстуре и живую ветвь с подменённым GET. Набор входит в `npm test`.
Семантическую правильность 289 неопределённых карточек тест не доказывает.
