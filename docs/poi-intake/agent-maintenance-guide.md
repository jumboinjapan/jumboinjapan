# POI Intake — карта аудита и безопасных изменений для моделей

Этот документ — маршрут для модели, которая впервые видит подсистему POI. Он не заменяет
код, тесты, решения владельца или runbook. Его задача — показать, **где лежит истина,
какие границы нельзя обходить и чем доказывать каждое изменение**.

Под «моделью» здесь понимается любой исполнитель: Codex, Claude Code, OpenClaw или другой
агент. Название инструмента не даёт дополнительных полномочий.

## 1. Первые десять минут

До чтения задачи и первой правки:

1. Прочитать корневой `AGENTS.md` и guardrail своего инструмента. Если отдельного guardrail
   нет, обязательны этот документ и `docs/poi-intake/change-policy.md`; брать инструкции
   другого инструмента и считать их своими нельзя.
2. Выполнить `git --no-optional-locks status --short --branch` и
   `git --no-optional-locks rev-parse --show-toplevel`. Сохранить список уже изменённых и
   неотслеживаемых файлов. Они принадлежат владельцу, пока не доказано обратное.
3. Прочитать `docs/poi-intake/README.md`, затем раздел этого документа для нужного вида
   изменения, соответствующие разделы `change-policy.md` и `runbook.md`.
4. Найти owning code path и всех потребителей через `rg`. Комментарий, название теста,
   старый handoff и отчёт другого агента не доказывают поведение production-кода.
5. Записать контракт изменения: область, нецели, предотвращаемая ошибка, источник истины,
   терминальные исходы, поведение после частичного сбоя и необходимое доказательство.
6. Для дефекта сначала получить различающий контрпример на прежних байтах, затем менять
   код. Копию для разрушительных мутаций держать вне рабочего дерева.

Запрещено начинать с живого запуска, «попробовать, что получится», или подгонять текущий
baseline под новое поведение без решения, какое поведение считается правильным.

Код описывает механизм, но не может сам выдать полномочие владельца. Файл решения,
контрольная сумма и статический импорт **не доказывают авторство**: решение становится
полномочным только после owner review, описанного в `change-policy.md`.

`tmp/`, логи прежней сессии, pasted report, чат и архивные аудиты — улики или история,
но не текущая истина. Если нужный локальный артефакт отсутствует, это пишут как
`not verified`, а не восстанавливают его содержание по пересказу.

## 3. Текущее состояние системы

- Airtable Intake Core принят: **30/30 критериев, 10 из 10 вех приняты**.
- Это принятие не доказывает готовность всех порталов. Japan Guide discovery работает, но
  Japan Guide Portal Intake Adapter не завершён: нет проекции `discovery record → PoiCandidate`.
- Принятие Intake Core не разрешает массовый импорт. Канареечные записи были ограничены
  отдельными разрешениями владельца; массовый корпус Осаки не исполнялся.
- Последние подтверждённые parser-owned создания: `POI-000577`, `POI-000578` и
  `POI-000579`. Для `POI-000579` владелец выбрал `representativePoint`; Google Place ID
  не назначался.
- Регулярный cron обхода порталов не включён. Запуски коллектора остаются ручными.
- Production-путь модельного исполнителя существует, но платный прогон закрыт policy
  источников и требует отдельного точного разрешения владельца.
- Создание парсером защищено манифестом, pre-write gate, одноразовым разрешением,
  журналом намерения и независимым перечитыванием результата.
- Обновление существующих записей парсером (пилот автообновлений, SC‑005,
  `pilot-completion-ledger.md`) имеет ядро той же строгости — карточка, разрешение, журнал
  `observe → update → outcome`, исход чтением по `recordId`, — но production‑потребителя у
  границы нет; пилот в режиме «только отчёт», PATCH существующих записей не разрешён.
- Открытые работы после завершения — не «недоделанный парсер»: миграция legacy-политик,
  потребители таксономии, classification eval, массовый импорт, журнал редакторских
  обновлений, guard удаления и эксплуатационный cron. Их зависимости ведутся в DAG.

Числа живой базы быстро устаревают. Документ может хранить доказанный исторический переход,
но текущий размер таблицы, состав очереди или число legacy-записей получают только новым
read-only чтением с отдельным разрешением.

## 4. Production-поток портального приёма

```text
registry.mjs
  → Source/Discovery Adapter (сырые байты + стабильный Source Key)
  → Portal Intake Adapter
  → канонический PoiCandidate
  → Airtable Intake Core
  → evaluate/classification
  → matcher и batch dedupe
  → report + run-manifest/v2
  → preWriteGate(reference)
  → poi-write-approval/v2 + долговечная одноразовая отметка
  → owner coordinate decision ИЛИ resolvePlace
  → ingestPoiBatch → ingestPoi
  → createAirtablePoiStore, обёрнутый withVerifiedWrites
  → POST create [и только при коллизии номера внутренний PATCH rename]
  → независимые readFreshBySourceKey + readFreshByPoiId
  → verified outcome в poi-write-journal/v1
```

Основные разделения:

- Source/Discovery Adapter отвечает за тождество строки источника; позиция `row-N`
  тождеством не считается;
- Portal Intake Adapter только проецирует проверенную source/discovery-запись в общий
  кандидат и не владеет taxonomy, matcher, resolver или writer;
- классификатор предлагает тип и маршрут, но не выдаёт полномочие владельца;
- matcher policy решает дедуп и abstention; отчёт не вправе пересчитать решение по-своему;
- `preWriteGate` сравнивает фактические входы, код, зависимости и реестры до store и
  резолвера;
- write approval разрешает только поимённые `Source Key` и ограничивает create и rename;
- координатное решение владельца применяется только к совпавшему `subject` и до резолвера;
- `ingestPoi` — общая create-граница; портальный writer не должен заводить параллельный путь;
- HTTP-ответ writer'а — заявление, не доказательство. Успех устанавливает база после
  независимых чтений;
- неизвестный исход останавливает хвост. Автоматического повтора, отката или удаления нет.

Telegram использует ту же create-границу `ingestPoi`, но не получает полномочия портального
write approval автоматически. Ручной ввод Airtable остаётся внешним путём и распознаётся по
отсутствию Intake-маркеров.

не переписывают задним числом.

## 6. Полномочия разделены

Ни одно из разрешений не включает другое:

| Полномочие | Что разрешает | Чего не разрешает |
|---|---|---|
| Ответ владельца о типе, координате или политике | предметное решение | сеть, запись, commit или push |
| Разрешение на credentialed read | названное чтение и названные поля | POST, PATCH, DELETE |
| Execution card / write approval | точный набор эффектов в указанный срок | другой файл, другой digest, повтор или расширение набора |
| Просьба commit | запись указанного diff в Git | push |
| Просьба push | отправку уже проверенного коммита | новые production-эффекты |

Для L3 разрешение обязано назвать точный артефакт и digest, цели, потолок POST/PATCH/DELETE
и платных обращений, частичный сбой, восстановление и финальную проверку. «Принято» или
предметный ответ не заменяют разрешение на исполнение.

Одноразовую отметку использованного разрешения и write-журнал не удаляют, не переносят и
не создают заново. Они доказывают потребление полномочия и фактический префикс эффектов.

## 7. Инварианты, которые нельзя ослаблять

1. Любой неизвестный, конфликтный или повреждённый вход даёт именованный fail-closed исход.
2. Каждый входной кандидат попадает ровно в один терминальный исход; полная очередь остаётся
   в отчёте, stdout может показывать только образец.
3. Входной файл читается один раз; gate и writer используют те же проверенные байты.
4. Состав кода выводится из графа импортов и проверяется до адаптеров и перед gate.
5. Реестры читаются только каноническими loader'ами. Локальный список, fallback JSON-reader
   или тестовый канал решения запрещены.
6. Машинный путь не может выбрать `human` и не может создать owner decision.
7. Без выводимой `Coordinate Policy` запись не создаётся; refresh не затирает
   `representativePoint` и `notApplicable`.
8. До первого эффекта существуют применимый reference, `PASS` gate, разрешение и его
   долговечная одноразовая отметка.
9. Намерение записывается до эффекта, результат подтверждается чтением после эффекта.
10. Первый `unknown`, `mismatch`, `ambiguous` или иной неподтверждённый исход останавливает
    оставшийся хвост; повтор и компенсирующий delete не выполняются автоматически.
11. В отчёте сохраняются доказанный префикс, отказ, `recoveryRequired` и применённое
    разрешение — в том числе когда разрешение не допускает ни одной строки.
12. Новый writer, PATCH или DELETE сначала появляется в реестре писателей и получает свой
    контракт, отрицательные проверки и способ восстановления.

## 8. Маршруты изменений

| Что меняется | Сначала читать | Минимальное доказательство |
|---|---|---|
| Новый портал или discovery → candidate | `portal-adapter-architecture.md`, `portal-adapter-rollout-plan.md`, `registry.mjs`, source adapter, runbook § 2 | сырые байты; неоднозначные заголовки; стабильный ключ; коллизии; закон сохранения; всерсионная проекция в `PoiCandidate`; ноль прямых writer/resolver; offline fixture; сквозной dry run; canary по точному approval |
| Классификация или маршрут | taxonomy loader, `classification-contract.mjs`, ADR-0001 | исчерпывающая матрица допустимых состояний; запрет `human`; отсутствие второго списка; версия реестра при семантической правке |
| Matcher или dedupe | `src/lib/poi-matching.ts`, eval-фикстура, change-policy § 23 | порядок кандидатов; близкие тёзки; part–whole; отсутствие координат; owner-примеры; новая версия и baseline при семантической правке; мутации порогов и обходов |
| Отчёт, счётчик или очередь | `collect-pois.mjs`, `classification-contract.mjs` | каждый исход непустой на фикстуре; закон сохранения; равенство множеств по `Source Key`; полный артефакт и stdout-sample различены |
| Манифест или pre-write gate | `run-manifest.mjs`, `code-graph.mjs` | каждая ось дрейфа независимо; старый/чужой формат; подмена между двумя чтениями; ноль store/resolver до отказа |
| Координаты и place resolver | coordinate policy/decision/refresh, `poi-portal-place.ts` | совпадение subject; все три политики; половина пары; неоднозначное место; refresh-race; итоговое чтение; ноль платных вызовов у owner decision |
| Таксономия или живая схема | ADR-0001, taxonomy loader, `poi-taxonomy-airtable.ts`, schema chain | новая immutable-версия при семантике; exhaustive routing; read-only preflight; точная L3-card; независимый witness; без повторного исполнения |
| Create writer, журнал или reconciliation | writers registry, runbook § 5б и § 9 | намерение до эффекта; независимые чтения; ошибка после POST; внутренний PATCH; оборванный журнал; hostile thrown values; остановка хвоста; поздняя сверка без эффектов |
| Update, migration или delete | writers registry, canonicalization, DAG 2.8/2.9 | свежая карточка `recordId + old → proposed`; все old до серии и перед каждой строкой; backup; журнал; входящие ссылки; ручное восстановление; отдельное L3-разрешение |
| Модельный план или транспорт | runbook § 2а, model plan/approval/preflight/execution modules | отсутствие сети до полного preflight; точная стоимость; outbound bytes digest; неопределённый dispatch; ownership/takeover; reconciliation без автоматического повтора |
| Только документация | owning code и `package.json` | каждая операционная фраза прослежена до кода; команды существуют; статусы не смешивают завершение парсера и post-completion debt; `check:docs` и doc tests |

Если изменение затрагивает несколько строк, берут объединение доказательств, а не выбирают
самую удобную строку.

## 9. Протокол аудита

Аудитор не принимает отчёт автора как доказательство. Для каждого сильного утверждения:

```text
Утверждение:
Owning code path:
Команда или тест:
Контрпример:
Наблюдаемый результат:
Что не доказано:
```

Порядок:

1. Зафиксировать HEAD, diff и исходные байты.
2. Проверить реальный production-вызов, а не только библиотечную функцию.
3. Воспроизвести найденный дефект на прежних байтах.
4. После правки прогнать тот же контрпример и положительный контроль.
5. Для критического guard сделать жизнеспособную мутацию. Убийством считается только
   именованное утверждение, а не import error, timeout или соседний guard.
6. Проверить пустой набор, второй кандидат, конфликт, частичный сбой и враждебное брошенное
   значение там, где они применимы.
7. Перечитать сохранённый артефакт и финальный diff. Лог процесса не доказывает запись на диск.
8. Отдельно перечислить неисполненное и границу доказанного.

## 10. Проверки и сеть

Состав `npm test` и `npm run verify` берётся только из `package.json`.

Минимальный офлайн-финиш для изменения POI:

```bash
AIRTABLE_TOKEN= AIRTABLE_BASE_ID= npm test
npm run typecheck
npm run lint
npm run check:docs
npm run check:claims
npm run check:typography
git --no-optional-locks diff --check
```

Пустые `AIRTABLE_TOKEN=` и `AIRTABLE_BASE_ID=` перед `npm test` обязательны, если эти
переменные могли быть экспортированы в shell (см. строку `test` в таблице ниже). Это
переопределение только для одной команды; файл `.env.local` при этом не трогается.

Перед `npm run verify` нужно определить, подхватит ли checkout `.env.local`. Несколько
стадий сами загружают этот файл и при наличии токена делают read-only запросы к Airtable.
Поэтому полный `verify` — не гарантированно офлайн-команда. По решению владельца от
07.09.2026 (`pilot-owner-decisions-2026-09-06.md` § III) read-only стадии `verify` запускают
без отдельного разрешения: только GET, без `--write`/`--apply`, лог в `tmp/`, в отчёте названы
факт живого чтения и стадии, прочитавшие базу. Прочее чтение с ключами — по-прежнему по
отдельному разрешению. Если полный `verify` не выполнен (например, из-за лимита времени
оболочки), запускают офлайн-набор выше и честно перечисляют пропущенные стадии; офлайн-набор
за полный `verify` не выдаётся. Нельзя переименовывать, редактировать или временно убирать
`.env.local`, чтобы добиться «офлайн»-прогона.

Проверяйте не только `verify`, но и каждую отдельно выбранную стадию. Число запросов
нигде не фиксировано: стадии читают таблицы постранично (`pageSize=100`, `offset`), и
количество GET зависит от объёма данных, а не от числа таблиц.

| Стадия | Фактическая сеть и безопасный выбор |
|---|---|
| `check:canon` | `scripts/check-canon.mjs` сам читает `.env.local` / `.env`; с токеном постранично читает пять таблиц (POI, маршруты, дни, пункты дня, остановки). Офлайн-режима нет — без разрешения пропустить |
| `check:polivanov` | `scripts/check-polivanov.mjs` через `loadEnvConfig` читает окружение; по умолчанию с токеном постранично читает POI. `--fixture tests/fixtures/poi-names.json` исключает сеть, но не чтение env-файлов. Исключение из правила «ключ есть, сети нет — отказ»: при ошибке сети с ключом стадия сама переходит на снимок, пишет об этом в stdout и завершается с кодом 0 |
| `check:copy` | `scripts/check-copy-length.mjs:124` сам читает `.env.local`; с токеном читает схему базы и записи полей копирайта. `--code` исключает сеть и чтение `.env.local`; проверяет только код и локальную документацию лимитов |
| `check:poi` | `scripts/check-poi-integrity.mjs:28` через `loadEnvConfig` читает окружение; с токеном `loadLive` (строка 707) читает схему, POI и остановки постранично. Офлайн только с явной фикстурой `--fixture <дамп>`; без ключа и без фикстуры стадия пропускается |
| `check:images` | `scripts/check-image-refs.mjs` сам читает `.env.local`; по умолчанию постранично читает маршруты и остановки. `--no-airtable` исключает сеть, но не чтение env-файла |
| `build` | `next build` сам загружает `.env.local`; ISR-страницы и `generateStaticParams` при пререндере читают живой Airtable. Офлайн-флага нет — `build` не входит в офлайн-набор |
| `test` | условно сетевая. Тест `tests/multiday-locale-invariants.mjs` сам `.env.local` не загружает, но при ЭКСПОРТИРОВАННЫХ в shell непустых `AIRTABLE_TOKEN` и `AIRTABLE_BASE_ID` (строка 160) настоящим `fetch` читает Meta API, маршруты и для каждого маршрута `Route Days`, `Day Items`, `Transport Segments` постранично; без них печатает именованный пропуск. Другие сюиты используют фиктивные токены с фикстурами или явно обнуляют переменные; дочерние CLI некоторых из них (например, fixture-прогон `check-poi-integrity` из `tests/poi-integrity.mjs`) вызывают env-loader, то есть читают `.env.local`, но работают с явно выбранными фикстурами и сеть не трогают. Стадии без сети: `lint`, `typecheck`, `check:typography`, `check:docs`, `check:claims`,
`check:admin-tokens` — они читают только рабочее дерево. `check:docs` сверяет состав и
порядок команд CI, но не их окружение: какие шаги получают секреты, видно только в самом
`verify.yml`.

Нулевое число write-эффектов не делает такой прогон офлайн. Если стадия уже прочитала
живую базу, это нужно назвать в отчёте, не повторять её без разрешения и не обозначать
результат как «сеть: 0». Само наличие ключа не разрешает его использование.

Сухая запись в Airtable и сухой Google — разные понятия: `--dry-write` запрещает эффект в
Airtable, но не обязан отменять place resolver. Любой потенциально платный resolver получает
явный потолок и отдельное разрешение.

## 11. Локальные артефакты и восстановление

- `tmp/` игнорируется Git. Ссылка на него в документе не делает артефакт доступным другой
  машине или аудитору после очистки.
- Evidence, необходимое для будущего аудита, либо входит в Git без секретов и персональных
  данных, либо в отчёте прямо названо локальным и невоспроизводимым без этой машины.
- Used-marker разрешения и write-журнал — операционное состояние, а не мусор. Их не чистят
  общим скриптом и не пересоздают ради повторного запуска.
- После неопределённого эффекта сначала выполняют read-only reconciliation по существующему
  журналу. Повторный writer запрещён, пока чтение не установило исход и владелец не выдал
  отдельную recovery-card на точный неприменённый хвост.
- Git-lock и `tmp_obj_*` под `.git` не относятся к `tmp/` проекта. Их не удаляют из среды,
  которая уже показала неспособность убрать собственный Git-файл.

## 12. Как поддерживать документацию

Изменение механизма и изменение его канонического статуса входят в один коммит.

- `README.md` хранит только текущую картину и ссылки.
- `change-policy.md` хранит устойчивые правила, а не хронологию.
- `runbook.md` хранит исполняемые команды, ветки отказа и восстановление.
- `poi-writers-registry.md` меняется при каждом новом POST/PATCH/DELETE к POI.
- `parser-completion-ledger.md` — доказательство завершения 30/30; новые долги не меняют
  знаменатель задним числом.
- `portal-adapter-architecture.md` — граница Airtable Intake Core и портальных адаптеров.
- `portal-adapter-rollout-plan.md` — экономичная очерёдность подключения Japan Guide; статус шага
  меняется только вместе с его доказательством.
- `poi-completion-dag.md` — post-completion backlog и зависимости, а не статус готовности
  парсера.
- ADR объясняет решение. ADR‑0002 сохраняется только потому, что его классы отношений
  являются источником для matching‑фикстуры; operational‑статус из него не берут.
- Исторические документы сохраняются в рабочем дереве только при живой ссылке из тестового
  доказательства. Отменённые handoff, аудиты и roadmap удалены и доступны через Git‑историю по
  `retired-index.md` (путь, SHA‑256, коммит); новое удаление входит в индекс тем же коммитом.
  Возвращение любого из этих файлов — включая `scripts/poi-score.mjs` — останавливает `check:docs`;
  сама npm-команда `poi:score` guard'ом не проверяется, её нет в `package.json`.

Не копировать в прозу полный список CLI-флагов, полей, enum или тестов: сослаться на
канонический код и объяснить смысл. Когда точное совпадение документа и кода важно,
добавить исполняемый guard.

## 13. Изоляция области

POI Intake не содержит конфигурацию мониторинга гостиниц. Будущая гостиничная система может
использовать похожие идеи — manifest, gate, одноразовое разрешение, журнал и reconciliation, —
но должна иметь другие базы, таблицы, настройки, реестры, артефакты и документацию. Нельзя
переиспользовать POI-разрешение или POI-конфигурацию как полномочие гостиничного процесса.

В POI-коде остаётся только защитное знание о классе `accommodation`: такие строки должны
получить `routedElsewhere`, а не стать POI. Это не подключение гостиничной системы. Импорт её
таблиц, данных, компонентов, маршрутов или проверок в `scripts/poi-portals/`, `src/lib/poi-*`
и `config/poi-*` запрещён и механически проверяется `check:docs`.

## 14. Форма передачи работы

```md
Сводка:
- результат и текущий статус;

Контракт изменения:
- область, нецели, источник истины, терминальные исходы;

Изменённые файлы:
- точный список и зачем каждый изменён;

Доказательство:
- контрпример до;
- результат после;
- целевые тесты и мутации;
- широкие офлайн-гейты;

Живые эффекты:
- сеть, Airtable GET/POST/PATCH/DELETE, Google/model, созданные отметки и журналы;

Не проверено:
- точный список;

Риски и восстановление:
- частичный эффект, recoveryRequired, команда read-only сверки;

Git:
- HEAD, staged scope, commit, push или явное «не выполнялись»;

Следующий допустимый шаг:
- действие, которое не расширяет полномочия.
```
