# POI перед сборкой маршрута

Решение владельца от 23.09.2026: маршрут из внешней ссылки собирается только
после регистрации и подготовки всех входящих локаций. Прочитанная статья,
название остановки, фотография или заполненный override не заменяют POI.

## Обязательный порядок для агента

1. Прочитать источник целиком и определить основные локации блоков маршрута.
   Уточнение владельца от 23.09.2026: в блоке Такао основной POI — ступа
   Буссяри; Отоко-дзака и Онна-дзака описываются в теле текста как варианты
   подхода. Не смешивать три названия в идентичности одного POI и не
   создавать три остановки только потому, что статья упоминает три места.
2. Найти существующие карточки и проверить тождество, не создавать дубли.
3. Недостающие места зарегистрировать через штатный Intake с источниками,
   досье и RU/EN-текстами по [общему процессу](cross-portal-operations.md).
   Новый POI остаётся Draft/Todo до предусмотренной редакторской приёмки.
   Нельзя автоматически повышать статус или копировать Draft в Approved,
   чтобы пройти проверку маршрута.
4. Независимо перечитать созданные POI. Сохранять состав маршрута в
   декларативном плане `route-intake-plan/v1` по формату ниже. Одна основная
   локация на блок; подходы и ориентиры — в `context`. Повторное посещение
   использует тот же `placeKey`, а не вторую карточку места.
5. Выполнить сборку по свежей базе:

   ```sh
   npm run --silent route:assemble -- --input /absolute/plan.json > /absolute/new-report.json
   ```

   Команда делает только GET. Код 0 и `status: ready` — все связи разрешены;
   код 1 и `blocked` — есть очередь подготовки; код 2 и `error` — неверный
   вход или ошибка чтения. При блокировке нет `steps`, `dayItems` и `preflight`:
   нельзя записать только готовую часть, незаметно потеряв остальные места.
   После Intake и редакторской приёмки повторить ту же команду с тем же планом.
   Не вводить подстановки ID по названиям или слагам маршрутов в коде.
6. Сохранять через штатные серверные писатели. Они повторяют проверку перед
   записью. Прямые POST/PATCH к Airtable из разовых импортных скриптов запрещены:
   они обходят серверный допуск. У внешних владельцев токена технически остаётся
   такой доступ; документация и аудит не являются ограничением прав Airtable.
7. После записи перечитать порядок, связи и тексты; выполнить `npm run check:poi`
   и проверить страницу на постоянном превью. Успех регистрации POI, сохранение
   маршрута и публикация — три отдельных результата.

## Декларативный план из внешнего источника

```json
{
  "version": 1,
  "routeSlug": "intercity/example",
  "places": [
    {
      "key": "main-temple",
      "label": "Основное святилище из статьи",
      "source": {
        "kind": "manual-import",
        "id": "example-source",
        "externalKey": "main-temple",
        "url": "https://example.org/main-temple"
      }
    }
  ],
  "steps": [
    {
      "key": "visit-temple",
      "kind": "poi",
      "placeKey": "main-temple",
      "context": "К святилищу ведут два подхода; они описываются здесь."
    },
    { "key": "meeting", "kind": "note", "text": "Встреча с гидом" }
  ]
}
```

Это условный пример структуры, не готовые данные для Intake. `source` должен
совпадать с источником карточки в штатном `ingestPoi`: ключ строится общей
функцией `buildSourceKey`, без отдельного реестра соответствий. Для уже
проверенного существующего объекта вместо `source` допустимо поле
`"poiId": "POI-000001"`. ID в данных плана — выбор карточки, а не условие в коде.
Оба способа одновременно запрещены. `label` помогает исследователю, но не
участвует в автоматическом сопоставлении и не подменяет каноническое имя.

Сборщик `scripts/lib/route-intake-plan.mjs` проверяет весь план до чтений:
версию, поля, уникальность ключей, ссылки, отсутствие неиспользованных мест.
Разные селекторы, разрешившиеся в один POI, требуют объединения `placeKey`.
Последовательность `steps` сохраняется, включая заметки и повторные посещения.

Если источник ещё не связан с карточкой, `registrationQueue` содержит место
и его ключ источника. Это очередь штатного Intake, **не приказ создать дубль**.
Intake сначала выполняет исследование и поиск существующего объекта. Если
совпадение найдено у карточки с другим источником, исследователь проверяет
тождество и выбирает её `poiId` в плане. Не переписывать её Source Key ради
сборки. Неоднозначные совпадения требуют решения, а не выбора первой строки.
Новая карточка Draft не допускается, пока её публичное описание не принято
по действующим редакторским правилам. Сборщик не создаёт и не публикует POI.

При успехе `steps` содержит реальные POI ID и канонические названия,
`dayItems` — элементы конструктора с отдельным `poiId`, `preflight` — вход
для существующей дополнительной проверки:

```sh
npm run route:preflight -- --input /absolute/preflight.json --report /absolute/report.json
```

Сохранять `dayItems` внутри выбранного дня через штатный писатель конструктора.
Для дневного тура переносить `steps` в Route Stops через штатную админку:
одна основная локация на строку, тот же порядок, `context` как текст блока.
Ответ сборщика не является разрешением на публикацию и не заменяет повторный
серверный допуск. Нельзя исполнять его через прямой Airtable POST/PATCH.
Чтение статьи и отделение самостоятельных посещений от контекста остаются
работой исследователя: алгоритм не делит названия по запятым или союзам.

## Импорт существующего макета дня

Конструктор запрашивает `GET /api/admin/route-stops/stops?routeSlug=…&forTemplate=1`.
Сервер читает все страницы остановок, исключает Helper/Inactive/Archived и
проверяет оставшиеся связи свежим `preflightRoutePois`. Ошибка блокирует
замену дня. `route-day-template.ts` переносит явный `poiId`; отсутствие связи
нельзя компенсировать `STOP ID`, названием или текстом override. Это относится
к новому импорту макетов; чтение старых уже сохранённых данных не меняется.

## Что именно проверяет код

Единый контракт: `src/lib/route-poi-readiness.ts`.
У каждой локации должен быть корректный `POI-000000`, ровно одна существующая
карточка с этим ID, русское название и непустой текст в `Description Approved (RU)`
или историческом `Description (RU)` — именно их читает сайт. Один Draft-текст
пока не проходит: сайт его не показывает. Технический допуск не удостоверяет
историческую точность, источники, перевод или редакторское утверждение.
Для явно зарегистрированных `Is System` сервисных POI требуются ID и имя;
описание услуги необязательно. Флаг `Is Helper` у остановки не отменяет связь.

`POST/PATCH /api/admin/route-stops/stops` проверяет новые/изменяемые активные
остановки. PATCH проверяет весь присланный пакет **до первой записи**, включая
вторую и последующие десятки. Удаление и деактивация некорректной старой строки
доступны для исправления. Перестановка меняет только порядок, новых связей не
создаёт. Создание пустой оболочки маршрута Draft остаётся доступно.

`saveMultiDayBuilderRoute` проверяет все элементы типа `poi` независимо от
`sourceMode`, а также все прочие элементы с POI-ссылкой — до записи маршрута,
дней и удаления старых элементов. Заметки, транспортные переходы, прилёт/вылет
и служебные блоки не становятся POI автоматически. Нельзя переименовывать
локацию в `note`, чтобы обойти Intake.

Нет общей транзакции Airtable: успешный preflight не исключает изменение POI
другим писателем после проверки или частичный сетевой сбой при сохранении.
При таком сбое обязательны перечитывание и сверка, не слепой повтор.

## Старые данные и контроль

`check:poi` считает отсутствие связи ошибкой, а не предупреждением. Тот же
контракт проверяет активные Route Stops и POI-ссылки Day Items (включая ручные).
Inactive/Archived остановки не требуют восстановления. Фикстуры без текстовых
полей не выдаются за проверку готовности описаний.

Старые неверные остановки не скрываются из публичной программы и не удаляются
автоматически: это замаскировало бы пропуск. Аудит выдаёт список для исправления.
Исправление существующих данных требует отдельного ограниченного плана и
штатного Intake; введение проверки само по себе не создаёт недостающие POI.

Регрессии: `npm run test:route-poi-readiness`. Проверяются настоящие обработчики
админки и писатель конструктора с подменённым транспортом; никакой живой записи
в тестах. Потеря POI, пустой текст, неоднозначный ID, ошибка сети и дефект в 11-й
строке должны давать ноль записей.

## Исправление прежних связей — 24.09.2026

Долг из 33 ошибок закрыт; [результаты и границы](route-poi-debt-closure-2026-09-24.md).
Конструктор хранит `poiId` отдельно от `internalNotes`. Редактирование заметки
не меняет связь. Разбор старой строки `POI ID: …` остаётся совместимостью для
объекта без собственного `poiId`; явно пустое значение не подменяется заметкой.

`PATCH /api/admin/multi-day/poi-links` — ограниченное исправление существующих
Day Items через админскую авторизацию. Не пересобирает дни, не удаляет строки,
не меняет порядок. Проверяет весь пакет и прежние поля до первой записи,
повторяет проверку строки непосредственно перед PATCH и перечитывает итог.
При сбое возвращает подтверждённые `applied`, `failedId`, `uncertainId`, `phase`
и `recoveryRequired`; после возможного эффекта инвалидирует кеш маршрутов.
Долговечного серверного журнала у endpoint нет: пакетное исполнение требует
внешнего журнала с fsync и независимой сверки. Слепой повтор запрещён.

Регрессия `test:route-poi-readiness` выполняет настоящий путь загрузки и
сохранения конструктора после изменения заметки. `test:day-item-poi-repair`
проверяет сохранность полей, drift, допуск POI и отказ после частичного эффекта.

## Проверки алгоритма

`npm run test:route-intake` проверяет строгий вход до чтений, неоднозначные
идентичности, пустые описания, настоящий Intake в памяти, повторную сборку
после регистрации и приёмки, повторные посещения и отсутствие частичного
результата. Регрессии макетов выполняют настоящий GET и конвертер; отказ на
второй странице и отказ чтения POI не допускают импорт. Проверка с отключённым
ограничением доказывает, что возврат запасной связи через STOP ID ломает тест.
