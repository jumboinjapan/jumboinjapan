# POI перед сборкой маршрута

Решение владельца от 23.09.2026: маршрут из внешней ссылки собирается только
после регистрации и подготовки всех входящих локаций. Прочитанная статья,
название остановки, фотография или заполненный override не заменяют POI.

## Обязательный порядок для агента

1. Прочитать источник целиком и выделить отдельные места. Составной заголовок
   вроде «Отоко-дзака, ступа Буссяри и Онна-дзака» — три кандидата, а не один POI.
2. Найти существующие карточки и проверить тождество, не создавать дубли.
3. Недостающие места зарегистрировать через штатный Intake с источниками,
   досье и RU/EN-текстами по [общему процессу](cross-portal-operations.md).
   Новый POI остаётся Draft/Todo до предусмотренной редакторской приёмки.
   Нельзя автоматически повышать статус или копировать Draft в Approved,
   чтобы пройти проверку маршрута.
4. Независимо перечитать созданные POI. Подготовить план соответствий:
   исходная локация → POI ID → остановка/день → порядок. Каждый отдельный POI
   должен быть представлен явно. Пока таблица Route Stops хранит один POI ID,
   несколько самостоятельных объектов сохраняются отдельными остановками;
   объединять их заголовком, теряя связи, нельзя.
5. Проверить полный план перед записью:

   ```sh
   npm run route:preflight -- --input /absolute/plan.json --report /absolute/report.json
   ```

   ```json
   {
     "version": 1,
     "routeSlug": "city-tour/takao",
     "stops": [
       { "key": "01: место из источника", "poiId": "POI-000001" }
     ]
   }
   ```

   Ключи в примере условные. Команда делает только свежие GET к Airtable.
   Код 0 и `status: ready` подтверждают техническую готовность проверенного
   состава; код 1 — неподготовленные POI, код 2 — ошибка чтения/входа.
   При кодах 1/2 остановить сборку, сохранить список недостающих мест и
   продолжить подготовку POI. Не пропускать места ради успешного результата.
6. Сохранять через штатные серверные писатели. Они повторяют проверку перед
   записью. Прямые POST/PATCH к Airtable из разовых импортных скриптов запрещены:
   они обходят серверный допуск. У внешних владельцев токена технически остаётся
   такой доступ; документация и аудит не являются ограничением прав Airtable.
7. После записи перечитать порядок, связи и тексты; выполнить `npm run check:poi`
   и проверить страницу на постоянном превью. Успех регистрации POI, сохранение
   маршрута и публикация — три отдельных результата.

## Что именно проверяет код

Единый контракт: `src/lib/route-poi-readiness.ts`.
У каждой локации должен быть корректный `POI-000000`, ровно одна существующая
карточка с этим ID, русское название и непустой текст в `Description Approved (RU)`
или историческом `Description (RU)` — именно их читает сайт. Один Draft-текст
пока не проходит: сайт его не показывает. Технический допуск не удостоверяет
историческую точность, источники, перевод или редакторское утверждение.
Для явно зарегистрированных `Is System` сервисных POI требуются ID и имя;
описание услуги необязательно. Флаг `Is Helper` у остановки не отменяет связь.

`POST/PATCH /api/admin/route-stops/stops` проверяет новые/изменяемые активные
остановки. PATCH проверяет весь присланный пакет **до первой записи**, включая
вторую и последующие десятки. Удаление и деактивация некорректной старой строки
доступны для исправления. Перестановка меняет только порядок, новых связей не
создаёт. Создание пустой оболочки маршрута Draft остаётся доступно.

`saveMultiDayBuilderRoute` проверяет все элементы типа `poi` независимо от
`sourceMode`, а также все прочие элементы с POI-ссылкой — до записи маршрута,
дней и удаления старых элементов. Заметки, транспортные переходы, прилёт/вылет
и служебные блоки не становятся POI автоматически. Нельзя переименовывать
локацию в `note`, чтобы обойти Intake.

Нет общей транзакции Airtable: успешный preflight не исключает изменение POI
другим писателем после проверки или частичный сетевой сбой при сохранении.
При таком сбое обязательны перечитывание и сверка, не слепой повтор.

## Старые данные и контроль

`check:poi` считает отсутствие связи ошибкой, а не предупреждением. Тот же
контракт проверяет активные Route Stops и POI-ссылки Day Items (включая ручные).
Inactive/Archived остановки не требуют восстановления. Фикстуры без текстовых
полей не выдаются за проверку готовности описаний.

Старые неверные остановки не скрываются из публичной программы и не удаляются
автоматически: это замаскировало бы пропуск. Аудит выдаёт список для исправления.
Исправление существующих данных требует отдельного ограниченного плана и
штатного Intake; введение проверки само по себе не создаёт недостающие POI.

Регрессии: `npm run test:route-poi-readiness`. Проверяются настоящие обработчики
админки и писатель конструктора с подменённым транспортом; никакой живой записи
в тестах. Потеря POI, пустой текст, неоднозначный ID, ошибка сети и дефект в 11-й
строке должны давать ноль записей.
