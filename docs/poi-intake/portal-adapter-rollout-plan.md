# План завершения работающего парсера Japan Guide

Цель — довести Japan Guide до общего Airtable Intake Core, не разбирать 919 строк вручную,
не повторять уже готовые механизмы и не тратить платные запросы на объекты, которые будут
отброшены офлайн.

«Экономичный» означает одновременно:

- минимальную стоимость внешних API;
- минимальное число повторных обходов сайтов;
- отсутствие отдельного конвейера для каждого портала;
- маленькие обратимые этапы с измеримым результатом;
- ноль live-write до готовой проверяемой очереди.

## 0. Активный путь и результат для владельца

По решению владельца 08.09.2026 (`pilot-owner-decisions-2026-09-06.md` § V) этот план
ведёт к работающему парсеру japan-guide.com, а не к расширению общей архитектуры.
**JG‑1 принят аудитом Codex R2 08.09.2026. JG‑2 (JA‑3…JA‑5) принят аудитом Codex
09.09.2026.** Код JG‑3 и офлайн-канарейка приняты аудитом Codex 09.09.2026.
Живые JA‑4 и canary ещё не выполнены. Следующий шаг — проверенные имена,
опознание, свежий снимок базы и разрешение на конкретную canary; затем первая партия.
Журнал 10h-B принят; прежнее условие «Japan Guide после журнала 2.8» выполнено.
BODIK U3 принят 08.09.2026 как отчёт без записи и не является дополнительным условием
начала или завершения этих пакетов. U4/U5 не запускать вместо Japan Guide.

Ближайший рабочий результат: штатный ручной запуск Japan Guide собирает факты,
классифицирует и сопоставляет кандидатов, показывает полные очереди, а после точного
разрешения создаёт новые POI в живой базе как черновики через существующий writer.
Каждая запись проверяется независимо; владелец получает понятный полный отчёт о
созданных, пропущенных и требующих разбора объектах, причинах и ошибках.
Команда запуска, входы, места отчётов и восстановление описаны в runbook и проверены
на сквозном сценарии. Набор библиотек или офлайн-тесты сами по себе этим результатом не являются.

Canary ≤ 5 и первая партия ≤ 25 — промежуточные проверки, не изменение исходной цели
регулярной обработки более 100 новых POI за запуск. Масштаб подтверждается отдельным
разрешённым прогоном после малых партий; до него не заявлять готовность такого объёма.
Текущие разрешения на живые обращения и потолки этим решением не расширены.

Админка/крон, обновление существующих POI, отдельный копирайтер, миграции legacy и
следующие порталы остаются вне ближайшей поставки работающего парсера. PA‑1 — справочный
будущий этап, а не условие завершения Japan Guide. Список DAG не даёт агенту права
самостоятельно расширять задачу. Чинить только то, что нужно текущему пакету или
подтверждённому блокеру его сквозного сценария; остальное не задерживает поставку.

| Сетевые GET обхода | 1 293 |

Эти 919 строк — верхняя граница неизвестного множества, а не план создания. В нём есть
объекты вне продуктового каталога, части существующих объектов, ложные совпадения и записи,
для которых недостаточно географии.

Текущий снимок позволяет выполнять этапы 0–3 без нового обхода Japan Guide. Повторный обход
нужен только при изменении source contract, подтверждённом drift, либо перед production-
canary после длительной паузы.

## 2. Экономическая модель

| Ресурс | Правило бюджета |
|---|---|
| Japan Guide GET | один полный снимок на цикл разработки; fixtures и сохранённый снимок используются повторно |
| Airtable GET | один проекционный снимок на сопоставление; новый — перед canary и перед каждой разрешённой партией |
| Airtable POST/PATCH | 0 до owner approval; canary не более 5 create и 0 rename; первая партия не более 25 create |
| Google Places | только для кандидатов, прошедших офлайн-отсев и matching; отдельный `max-place-lookups` для каждого прогона |
| Модельная классификация | 0 по умолчанию; включается только для остатка, который не разобрали правила, и по отдельной source policy |
| Ручная работа | сначала 2 неоднозначности и малые очереди высокого риска; 919 строк по одной вручную не просматриваются |

Денежная стоимость не зашивается в документ: тарифы внешних API меняются. Перед платным
прогоном карточка бюджета фиксирует SKU, дату официального тарифа, валюту, максимум вызовов и
формулу `максимальная стоимость = потолок вызовов × действующий тариф`. Изменение тарифа не
требует правки адаптера, но требует нового расчёта карточки.

## 3. Порядок, который экономит деньги

```text
сохранённый discovery-снимок
  → офлайн-проекция кандидатов
  → офлайн-taxonomy и отсев
  → офлайн-сопоставление с Airtable snapshot
  → бесплатные официальные источники
  → ограниченный Google только для остатка
  → owner review малой очереди
  → canary
  → ограниченные партии
```

Нельзя менять этот порядок, вызывая Google или модель до taxonomy и дедупликации: платный
ответ для будущего `routedElsewhere` или уже существующего POI не создаёт ценности.

### JA-4. Ограниченное опознание места

Результат: координаты и Place ID только для кандидатов, переживших предыдущие этапы.

- Google вызывается через общий `resolvePlace`, без портальной копии.

- Неоднозначный ответ не выбирается автоматически.
- Перед запуском фиксируются действующий тариф и максимальная стоимость.
- Gate завершения: каждый вызов и каждый отказ учтены; превышение потолка останавливает

### JA-5. Owner review и артефакт решений

Результат: малый файл решений, содержащий только действительно неоднозначные строки.

- Владелец видит источник, имена, предполагаемый тип, географию, возможный дубль и причину

- Решение не выдаёт полномочие на сеть, запись или Git.
- Русское имя проходит отдельную проверку Поливанова и редакторскую сверку.
- Gate завершения: ни одно машинное решение не выдано за решение владельца.

### JA-6. Сквозной dry run

Результат: отчёт настоящего пути Japan Guide → Intake против свежего снимка Airtable.

- Airtable write: 0.
- Google/model: 0, если результаты JA-3/JA-4 подаются подписанными входами; иначе точные
  отдельные потолки.
- Отчёт содержит полные очереди, manifest и суммы исходов.
- Gate завершения: повтор на тех же байтах даёт тот же предметный результат; изменение
  источника, снимка базы, правил или кода видно отдельной осью drift.

### JA-7. Canary

Результат: не более 5 новых POI, выбранных из разных классов сложности.

- Отдельный эталон и `poi-write-approval/v2`.
- `maxCreates ≤ 5`, `maxRenames = 0`, `DELETE = 0`.
- После каждого эффекта — независимые чтения и журнал.
- Неуспешный исход останавливает хвост без автоматического повтора.
- Gate завершения: каждая созданная запись перечитана, в каноне и связана с источником.

### JA-8. Первая партия и эксплуатация

Результат: партия не более 25 create, затем решение о следующем потолке по фактическому
проценту отказов canary и первой партии.

- Каждая партия получает новый Airtable snapshot, reference report и одноразовое approval.
- Повторное использование разрешения запрещено.
- Cron не включается, пока первый пакет не сверен независимо.
- Размер следующей партии повышается только отдельным решением владельца; документ не
  устанавливает бессрочный максимум.

### PA-1. Подключение следующего портала

Результат: новый портал использует тот же контракт и Intake Core.

1. Выбрать семейство адаптера.
2. Переиспользовать `opendata-csv` или Japan Guide-подобную проекцию, если форма совпадает.
3. Добавить только source-specific fixtures, mapping и policy.
4. Повторить JA-2, JA-6 и JA-7 на новом портале.

Если для нового портала приходится копировать taxonomy, matcher, resolver, approval или
writer, архитектурная граница нарушена и работа останавливается до аудита.

## 5. Метрики экономичности

Каждый checkpoint сообщает:

- сколько входных записей обработано офлайн;
- сколько отброшено до Google и модели;
- сколько бесплатных GET и платных вызовов сделано;
- стоимость по SKU и тарифу на дату запуска;
- сколько вопросов осталось владельцу;
- сколько POST/PATCH/DELETE разрешено и фактически произошло;
- сколько результатов подтверждено независимым чтением;
- можно ли повторно использовать сохранённый снимок без нового обхода.

Полезная метрика этапа JA-2: `paidAvoidance = 1 − eligibleForPaidLookup / discoveryRecords`.
Она измеряет долю корпуса, которую система решила до платного шага. Метрика не может быть
целью, если ради неё правила начинают отклонять сомнительные объекты как уверенные.

## 6. Условия окончательного завершения Japan Guide

Japan Guide считается подключённым к Intake только одновременно при следующих фактах:

1. Полный discovery-снимок проходит версионный контракт.
2. Каждая discovery-запись получает ровно один исход Portal Intake Adapter.
3. Общие taxonomy, matcher и Coordinate Policy исполняются без портальных копий.
4. Сквозной dry run даёт полные очереди и ноль неучтённых строк.
5. Canary выполнена по точному approval и независимо перечитана.
6. Никакой текст Japan Guide не скопирован в каталог как авторское описание.
7. Штатный ручной запуск и восстановление документированы и воспроизведены; первая
   разрешённая партия создаёт черновики через существующий writer и независимо сверена.
8. Владелец получает полный отчёт по созданным, существующим, отклонённым и требующим
   разбора записям с причинами; ошибки и неприменённый хвост не скрываются.

Подключение другого портала не требуется для завершения Japan Guide. Готовность
регулярного объёма более 100 новых POI отмечается отдельно после его проверки.

До выполнения этих условий корректный статус: **«Airtable Intake Core принят; Japan Guide
discovery работает; Japan Guide Portal Intake Adapter не завершён»**.
