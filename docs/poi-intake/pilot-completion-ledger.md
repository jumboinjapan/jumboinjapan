# Пилот автообновлений (SC‑005): реестр приёмки

Это **вторая область** после Airtable Intake Core (`parser-completion-ledger.md`,
`poi-parser-v1`, 30/30). Решение владельца I‑1.1 от 06.09.2026: пилот автообновлений — новый
пакет со своими критериями и своей приёмкой; знаменатель парсера 30/30 он не меняет и его
полномочий не наследует. Решения OD01–OD04 из аудита «Астра» 06.09.2026 заменены строками
опросников I и II (`pilot-owner-decisions-2026-09-06.md`); здесь они переоформлены в
критерии. Форма реестра — та же, что у парсера: в каждой вехе ровно три критерия, источник
точных enum и поведения — код, реестр называет границу и исполняемое доказательство.

## 0. Место пилота в текущем приоритете

Основная задача — закончить парсер Japan Guide (`pilot-owner-decisions-2026-09-06.md`
§ V). U1–U3 приняты. U3 завершён только как отчёт BODIK без записи и не является
зависимостью Japan Guide. U4/U5 отложены из активного плана: следование номерам этого
реестра не является поручением продолжать их после U3. Критерии и знаменатель пилота
сохраняются для будущей работы; 9/15 не является оценкой
готовности адаптера Japan Guide.

## 1. Граница области

Пилот обновляет **существующие** записи POI по данным источника. Решениями владельца область
сужена до: поле — **только часы работы** (I‑2.2); записи — **только с `Source Key`** (I‑2.3;
legacy‑записи без ключа и сопоставленные матчером записи не обновляются); источник —
**только BODIK** (I‑2.4; Google Places — не источник обновлений); запуск — **только вручную**,
каждый прогон по отдельному разрешению (I‑4.1); при расхождении источника и базы по любому
другому полю — `needs_review`, человек решает (I‑4.4); частичный отказ серии — остановка с
сохранением доказанного префикса (I‑4.6). Правило поштучного, пополевого согласования
остаётся (I‑2.1). U1 и U2 приняты; пилот пока работает в режиме «только отчёт»:
писатель часов (U4) не подключён, живая серия требует отдельного разрешения.

Не входят в область: редакторские пути админки и крон координат на Vercel (журнал для них —
отдельный пакет, решение IV‑2 от 08.09.2026), удаление записей (DAG 2.9), миграция 444
legacy‑записей (после журнала, II‑6.3), статус «закрыто», координаты, имена и описания
(I‑2.2), автоматический стоп по месячному потолку Google (I‑4.2 — учётный предел).

Итог: **9/15 критериев, 3 из 5 вех приняты.** U1 и U2 приняты независимым аудитом
Codex 08.09.2026 (10h-B, R3); U3 — независимым аудитом Codex 08.09.2026 (10h-C).
Доказательство U3: `poi-hours-report` — 88 проверок; аудит закрыл потерю расхождения сайта,
когда значение было пустым только с одной стороны, и мутация прежнего условия убита
именованными утверждениями; непрерывный `npm run verify` на Node 22.23.0 — exit 0.
Живой отчёт BODIK не запускался. Производственного потребителя обновлений нет;
принятие U1–U3 не разрешает живой PATCH.

## 4. Как поддерживать реестр

Как у парсера (`parser-completion-ledger.md` § 4): критерий переходит в `ACCEPTED` только по
независимому аудиту с названным доказательством; переоткрытие — только production‑контрпримером;
знаменатель 15 меняется только решением владельца, записанным в
`pilot-owner-decisions-2026-09-06.md`. Текущий статус области — в `README.md` § 3; открытые
зависимости — в `poi-completion-dag.md` (узлы 2.8, 5.5).
