установлены её полномочия, потолок эффектов и способ проверки результата.

## 2. Что реализовано в Airtable Intake Core

- стабильный `Source Key`, который строит адаптер из идентификатора источника, а не позиции;
- строгие границы сырого входа, заголовков, names/existing/base-snapshot и закон сохранения;
- taxonomy v2 через один loader и один маршрут классификации;
- matcher policy с версией, отпечатком чисел и словарей, matching eval и owner-controls;
- единый `resolvePlace` для кодовых create-путей и терминальная неоднозначность вместо
  создания записи без опознанного места;
- `Coordinate Policy` для новых записей и реестр решений владельца для
  `representativePoint`/`notApplicable`;
- общий refresh-контракт, который не затирает решение владельца и проверяет PATCH чтением;
- `run-manifest/v2` и pre-write drift gate до store и resolver;
- `poi-write-approval/v2`: поимённый набор `Source Key`, потолки create/rename, привязка к
  эталону и долговечная одноразовая отметка;
- `poi-write-journal/v1`, независимые чтения результата, остановка хвоста и read-only
  reconciliation;
- guarded production entrypoint модельного исполнителя; платный путь закрыт policy источников
  и отсутствием отдельного разрешения на конкретный прогон;
- четыре поля taxonomy v2 в живой схеме Airtable, созданные одной принятой схемной карточкой.

Механизм и тест для каждого пункта перечислены в карте сопровождения. Точные enum, поля,
флаги и тестовые счётчики берут из кода, а не переписывают из этой страницы.

## 6. Production-поток

```text
source registry → Source/Discovery Adapter → Portal Intake Adapter → PoiCandidate
  → Airtable Intake Core: classification → matcher/dedupe → report + manifest
  → preWriteGate → write approval + used-marker
  → coordinate decision ИЛИ resolvePlace
  → ingestPoiBatch → ingestPoi
  → verified Airtable store → create/optional rename
  → independent reread → journal outcome → report/exit code
```

Отдельный discovery-поток Japan Guide производит evidence, а не кандидатов в Intake. Его
данные нельзя передать в create-путь без версионного Portal Intake Adapter и его
различающих тестов.

## 7. Защищённые границы

Обход любого пункта — регрессия:

1. Кодовое создание POI проходит через `ingestPoi`; новый прямой POST запрещён.
2. Реестр taxonomy читается только через канонический loader; второго JSON-reader нет.
3. Машинный путь не может объявить источник решения `human`.
4. Решение владельца о координатах не приходит через `deps`, `options` или поля запроса.
5. Gate и writer используют одно чтение каждого входного файла.
6. Live write не начинается без эталона, `PASS` gate, применимого одноразового разрешения и
   долговечной used-marker.
7. HTTP 2xx и тело ответа не доказывают эффект. `verified` требует независимых чтений базы.
8. Неопределённый исход останавливает хвост; повтор, rollback и delete автоматически не
   выполняются.
9. Каждый кандидат получает один терминальный исход, а полная очередь остаётся в отчёте.
10. Новый POST/PATCH/DELETE к POI сначала добавляется в реестр писателей и получает тест
    отказа, частичного эффекта и восстановления.

Полный набор правил — `change-policy.md`. Матрица изменений и аудита —
`agent-maintenance-guide.md`.

## 8. Сеть, живые данные и разрешения

Раздельные полномочия:

- предметное решение владельца;
- credentialed read;
- production write по точной карточке или approval;
- commit;
- push.

Одно не включает другое. `--dry-write` запрещает запись в Airtable, но не гарантирует ноль
обращений к Google Places. `npm run verify` тоже не гарантированно офлайн: стадии могут
подхватить `.env.local` и выполнить read-only запросы. Порядок безопасного запуска описан в
runbook и карте сопровождения.

Used-marker и журнал исполненного разрешения — операционное состояние. Их нельзя удалять,
переносить или пересоздавать ради повторного прогона.

## 9. Известные ограничения

- Airtable не даёт транзакцию для пакетного create; доказанный префикс может остаться.
- Автоматического rollback нет. Удаление опасно из-за входящих ссылок.
- Между независимыми чтениями остаётся окно без compare-and-swap; расхождение обнаруживается,
  но физически не исключается.
- Ручной ввод в Airtable может обойти create-границу; отсутствие Intake-маркеров делает это
  видимым.
- Редакторские update-пути не покрыты parser write-journal.
- Локальные артефакты в `tmp/` не доступны другой машине автоматически.
- Источник может сообщить неверные данные; manifest доказывает тождество входа, а не его
  истинность.
- Discovery-адаптер Japan Guide не строит `PoiCandidate`; без этой границы корпус
  Japan Guide не может пройти Airtable Intake Core.
