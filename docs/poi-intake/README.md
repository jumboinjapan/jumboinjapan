# POI Intake — каноническая точка входа

Этот файл отвечает на один вопрос: **что в подсистеме приёма POI работает сейчас, а что существует только на бумаге.** Если вы агент без исторического контекста — начните отсюда и не верьте другим документам про POI, пока не сверитесь с таблицей ниже.

Остальные документы по подсистеме описывают либо целевую архитектуру, либо состояние на свою дату. Ни один из них не переписывается при каждом изменении кода; этот — переписывается.

---

## 1. Зачем система

База POI — точки, из которых собираются маршруты и печатные программы. Всё остальное в проекте её только читает. Приём отвечает за то, чтобы в базу попадали записи, за которые не стыдно: с городом, координатами, непротиворечивой категорией и следом происхождения.

Источников поступления четыре: Telegram-бот владельца, коллектор с открытых японских порталов, админка и ручной ввод в интерфейсе Airtable. Первые три идут через код, последний — нет, и это известная дыра, а не недосмотр (см. §6).

---

## 2. Текущая стадия

Идёт перевод классификации на машинный реестр таксономии — по одному потребителю за коммит. Пройдены реестр, loader и портальный классификатор. Массовый импорт Осаки **не открыт**: до него нужно подключить оставшихся потребителей и мигрировать поля Airtable.

Активная версия таксономии: **`poi-taxonomy/v2`**
Файл: `config/poi-taxonomy.v2.json`
Digest (`raw-file-bytes/v1`): `sha256:11bb3fef98373bd0029d75a97db7bba4dade5f919b56b910bcac2633646d2a6b`

`config/poi-taxonomy.v1.json` остаётся в репозитории неизменным как историческая версия. Его digest `sha256:57b9c2b6d95d8b79b8bc24cd8db4ccac1156a889d208967441511c01643f2305` закреплён тестом: v1 больше не читается кодом, но обязан лежать побайтно тем же.

## 6. Защищённые границы

Обойти любую из них — регрессия, а не оптимизация.

1. **Создание записи POI кодом идёт только через `ingestPoi()`.** Прямой `POST` в таблицу POI из нового кода запрещён.
2. **Ручной ввод в интерфейсе Airtable этой границей не закрыт.** Так появились 24 пустые записи 10.08.2026. Закрыть кодом нельзя; сделать видимым — можно, запись без Intake-маркера отличима.
3. **Реестр таксономии читается только через `src/lib/poi-taxonomy.ts`.** Второй читатель JSON — это второй реестр.
4. **Локальных списков типов, подписей, фасетов и маршрутов не существует.** Проверяется тестом: строковые литералы модулей пересекаются со значениями реестра, пересечение обязано быть пустым.
5. **Источник классификации `human` машинным вызовом не имитируется.** В портальном классификаторе такого канала нет вовсе.
6. **Семантическое изменение реестра требует новой версии; любое изменение байтов меняет digest.**
7. **`--write` в коллекторе — только по явному решению владельца.**

Полный список правил для агентов: `docs/poi-intake/change-policy.md`.

## 7. Следующий разрешённый этап

**Жизненный цикл разрешения и журнал — коммит № 5.** Он вводит состояния разрешения во времени (действует, истекло, израсходовано) и журнал, по которому одноразовость исполнения становится проверяемой: один `approvalDigest` — один детерминированный `executionId`. Сейчас этой проверки нет, и повторный платный прогон по тому же разрешению кодом не блокируется.

Что уже готово к нему: контракт профиля при пустом реестре, идентификатор записи запроса и выборка кандидатов, механика исполняемого плана v2 с одним парсером на две версии, контракт разрешения владельца с потолками.

Чего по-прежнему нет и кодом не делается: выбор провайдера и модели, разрешённые источники, закреплённая таблица цен, финансовый потолок. `PROVIDER_PROFILES` пуст, `modelProcessing` у всех двенадцати источников запрещающая — поэтому production CLI исполняемый план не строит, а запрос отправить нечем. Реальный runtime-план v2 и approval создаются локально уже после owner-коммита, а не сейчас.

Что делать **до** него нельзя: трогать XLSX, Airtable, production Intake и правила классификации. Правила меняются только по eval-фикстуре, а её ещё нет (§8).

## 9. Открытые риски

Известные и непокрытые. Не дефекты конкретного коммита — свойства системы на сегодня.

| Риск | В чём | Что делать до того, как закроем |
|---|---|---|

## 10. Как проверить, что этот файл не устарел

```bash
git log -1 --format=%H -- docs/poi-intake/README.md   # чем этот файл в последний раз подтверждён
git log --oneline -1                                  # где HEAD
npm test                                              # состав наборов — в package.json
shasum -a 256 config/poi-taxonomy.v2.json
```

Границей актуальности служит коммит, содержащий текущую версию **самого этого файла**, а не поле внутри него. Поле `Last verified commit` убрано намеренно: коммит, обновляющий документ, не может содержать собственный hash, поэтому такая подпись всегда отстаёт ровно на один коммит и выглядит просроченной, даже когда документ верен.

Если между `git log -1 -- docs/poi-intake/README.md` и `HEAD` есть коммиты, менявшие подсистему POI, документ обязан быть обновлён — тем же коммитом, что и код.
