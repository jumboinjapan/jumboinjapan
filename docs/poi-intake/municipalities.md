# Муниципалитет и туристическое направление

Решение владельца 25.09.2026: новые муниципалитеты сохранять автоматически;
не добавлять каждый посёлок в фильтр направлений. Понятные туристические районы
Хоккайдо — следующий этап, их границы этим изменением не назначаются.

## Данные и приём

- `Municipality (JA)` — текстовое поле с муниципалитетом из японского адреса
  источника, например `中富良野町`. Это наблюдение адреса, а не отдельный POI
  или запись в справочнике туристических направлений. Префектура хранится рядом
  в существующих `Prefecture (EN/RU)`.
- `Site City` — туристическое направление. Известные соответствия сохраняются.
  Если муниципалитет разобран, префектура подтверждена, но направления нет,
  используется `unassigned-<prefecture.en в нижнем регистре>`. Для Хоккайдо
  интерфейс показывает «Хоккайдо — направление не назначено». Все такие
  муниципалитеты образуют один пункт фильтра, публичных страниц городов не создают.
- `POI Geography` — прежний территориальный охват крупных объектов и связи.
  Муниципалитет адреса не подменяет охват горы, острова или комплекса.

Общий контракт — `src/lib/poi-municipality.ts`, разбор и выбор направления —
`resolvePoiDestination` в `jp-address.ts`. Портальная подготовка
`japan-guide-record.mjs` передаёт адрес как `poi.sourceAddressJa`; `ingestPoi`
пишет поле в тот же POST. До чтения базы проверяются адрес, префектура точки,
направление, а для досье v2 — наличие адреса в исходных блоках доказательств.
Смысловую принадлежность адреса объекту подтверждает разбор источника;
поиск подстроки не заменяет эту проверку. Адрес и префектура не согласуются →
отказ, а не подстановка ближайшего города. Пустой или неразобранный адрес
не создаёт муниципалитет. Общая группа по префектуре не считается доказательством
«тот же город» при поиске дублей.

Это изменение не ослабляет опознание места, проверку координат, досье,
редактуру, дедупликацию, журнал записи и закрытие «Разбора POI». Отсутствие
направления само по себе больше не вопрос владельцу. Другие блокеры сохраняются.

Старый `resolveSiteCity` и ограничение регионов CSV-коллектора не изменены:
его список покрытия — отдельное правило выбора партии. Новые адаптеры каталога
используют `resolvePoiDestination`, а не пополняют `DESTINATIONS` каждым посёлком.
Старые карточки автоматически не переписываются; их муниципалитеты можно
дополнить отдельным проходом по сохранённым адресам после проверки источников.

## Поле в Airtable

`npm run poi:municipality-schema` читает схему и показывает план.
`npm run poi:municipality-schema -- --apply` создаёт **только** поле
`Municipality (JA)` типа `singleLineText`, если его нет. Данные POI команда не
пишет. Совпавшее поле → `present`, неправильный тип → отказ без изменения.
После одного POST результат устанавливается свежим GET; при потере ответа
POST не повторяется. Неподтверждённый исход → остановка, повтор начинают с
чтения схемы. Журнал — `tmp/poi-municipality-schema/*.ndjson`.

Intake проверяет поле в живой схеме. Хранилище в памяти распознаётся по тождеству
фабрики и внешних эффектов не имеет. В пакете адреса всех строк проверяются до
первого эффекта. Черновики, успешно принятые раньше, повторно не создаются.

Проверки: `tests/poi-municipality.mjs` — новые муниципалитеты, отсутствие
выдуманной географии, запись/повтор, конфликт до I/O, схема и восстановление;
`tests/poi-portal-draft-batch.mjs` — полный путь неизвестного муниципалитета
из исходной страницы до сохранённых полей, подмена адреса и журнал записи.
