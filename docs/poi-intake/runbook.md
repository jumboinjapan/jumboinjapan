# POI Intake — runbook

Как запустить сбор POI и ничего не сломать. Команды сверены с `package.json` и парсером аргументов `scripts/poi-portals/collect-pois.mjs`; флагов, которых там нет, здесь нет тоже.

---

## 1. Что можно запускать без риска

Эти команды ничего не пишут. Первые пять полностью локальны; `check:poi` может читать живую Airtable-базу, если найдёт ключи:

```bash
npm test                      # все наборы; состав — в package.json
npm run test:poi-classification   # только контракт классификации
npm run test:poi-taxonomy-loader  # только loader реестра
npm run typecheck
npm run lint
npm run check:poi             # read-only; с ключами читает Airtable, без ключей пропускает живую часть
```

`npm run verify` проходит без Airtable-ключей: живые проверки пропускают свою часть или используют фикстуру и говорят об этом вслух. Но «ключ не экспортирован в shell» не означает «ключа нет»: часть скриптов автоматически читает `.env.local` через Next, часть читает файл сама. Если файл с рабочими ключами лежит в корне, `npm run verify` выполняет credentialed read живой базы.

Перед полным `verify` нужно отдельно установить эффективный режим и получить разрешение на живое чтение Airtable. Разрешение на Git, commit или push его не включает. Без разрешения запускаются офлайн-ветви и фикстуры по отдельности, а полный `verify` отмечается как не выполненный. Переименовывать или править `.env.local` ради офлайн-прогона нельзя.

## 2. Сбор с портала

```bash
npm run poi:collect -- --portal bodik-osaka-tourism --out tmp/osaka.json
```

Что происходит: коллектор идёт в сеть за выгруженным датасетом портала, прогоняет кандидатов через оценку качества и классификацию правилами, раскладывает по терминальным исходам и пишет полный отчёт в `--out`. **В Airtable не пишется ничего** — без флагов записи путь `writeRun` вообще не вызывается.

### Флаги

| Флаг | Что делает | Нужна сеть | Пишет в Airtable |
|---|---|---|---|
| `--portal <id>` | один портал | да | нет |
| `--all` | все объявленные порталы | да | нет |
| `--limit <n>` | взять первые n кандидатов | да | нет |
| `--out <file>` | полный отчёт в файл | — | нет |
| `--samples <n>` | сколько примеров в каждой выборке, по умолчанию 8 | — | нет |
| `--existing <file>` | сверка с выгрузкой базы из файла | — | нет |
| `--names <file>` | файл русских имён | — | нет |
| `--monitor <file>` | сравнение с прошлым прогоном | — | нет |
| `--base-snapshot <file>` | **включает** путь записи против снимка базы в файле | да, за порталом | **нет**, снимок вместо базы |
| `--dry-write` | **включает** путь записи против живой базы без создания записей | да | нет, но читает Airtable |
| `--write` | **создаёт записи** | да | **да** |

Важное про два последних: `--base-snapshot` и `--dry-write` включают `args.write` внутри — то есть путь записи исполняется, но до создания записи дело не доходит. `--base-snapshot` предпочтительнее: он не требует токенов на чтение живой базы.

### Форма снимка базы

Файл — массив строк. Каждая строка **объявляет** все девять полей; значение может быть `null` почти у всех.

| Поле | Значение | Зачем гейту |
|---|---|---|
| `poiId` | строка формы `POI-000000`, уникальная | тождество записи |
| `recordId` | `null` или непустая строка, уникальная | идентификатор записи в Airtable |
| `nameRu` | непустая строка | сравнение имён |
| `nameEn` | `null` или непустая строка | то же |
| `siteCity` | `null` или непустая строка | различение «тот же город» |
| `lat`, `lon` | `null` или числа в пределах ±90 / ±180, только парой | сравнение расстояния |
| `placeId` | `null` или непустая строка | **подготовлено, портальным путём не исполняется** — см. ниже |
| `sourceKey` | `null` или непустая строка, уникальная | идемпотентность приёма |

Объявление обязательно, даже когда значения нет. Выгрузка, в которой поля нет вовсе, — файл другого формата: приняв её, прогон выдал бы «ключей источника нет ни у кого» за факт о базе, хотя это факт о файле.

Что отвергается отдельно, потому что выглядит заполненным и пусто по сути:

- пробельная строка вместо `null` в любом идентификаторе — отсутствие пишется как `null`;
- половина координаты: гейт молча перестал бы сравнивать расстояние;
- координата, равная нулю. Живое хранилище (`src/lib/poi-matching.ts`, `toPoiLike`) считает ноль отсутствием координаты — нулевая широта это точка в Атлантике. Снимок обязан говорить то же самое тем же способом, иначе счётчик `withCoords` соврёт;
- `poiId` произвольной формы: по нему же хранилище выдаёт следующий номер.

Состав полей и проверка определены в одном месте — `scripts/poi-portals/lib/base-snapshot.mjs`, функция `assertSnapshotRows`. Через неё проходит и файл, и любые строки, отданные хранилищу напрямую: обойти проверку, передав строки мимо файла, нельзя. Файл читается и проверяется **до обращения к порталу**: неверный снимок роняет прогон до первой сетевой загрузки. При загрузке в stderr печатаются счётчики покрытия — сколько записей несут ключ источника, координаты, город и `place_id`.

### Что `--base-snapshot` действительно исполняет

Исполняются: preflight маршрута, покрытие файла имён, legacy-мост, канон, **идемпотентность по `Source Key`**, гейт дублей по именам и координатам, накопление принятых записей внутри пакета — повтор того же ключа во второй строке пакета даёт `already_ingested`.

Не исполняется:

- **гейт «один `place_id` — один POI»**. Проверка в `src/lib/poi-ingest.ts` сравнивает `request.poi.resolved.placeId` с полем существующих записей и работает — но коллектор `resolved` не наполняет: доверенный `resolvePlace` к портальному пути не подключён. Поэтому одинаковый `place_id` у кандидата и у записи снимка сегодня даёт `created`. Поле в формате снимка есть и лежит готовым; обещать проверку по нему нельзя до подключения резолвера;
- запись в Airtable. Записи «создаются» только в памяти процесса и исчезают вместе с ним. Снимок — объект фабрики `createMemoryPoiStore` (`src/lib/poi-memory-store.ts`); writer узнаёт его по тождеству фабрики, а не по объявлению, поэтому объект с эффектным `create` эту ветку не откроет;
- проверка того, что база не изменилась с момента снятия снимка;
- всё, что зависит от полей, которых в снимке нет.

Ограничение, которое надо помнить: если ни у одной записи снимка нет `sourceKey`, ветка `already_ingested` не сработает ни разу — не потому что повторов нет, а потому что сравнивать не с чем. Коллектор говорит об этом отдельной строкой в stderr.

Штатного экспортёра снимка нужной формы пока нет: снимок готовится отдельно, и это отдельная задача — у локального файла с координатами есть вопрос срока хранения, который решает владелец.

## 2а. `--model-plan` — локальный план модельной классификации

```bash
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism \
  --model-plan --out tmp/poi-model-plans/osaka-$(date +%Y%m%dT%H%M%S).json
```

Дата **и время** в имени — не украшение: план никогда не перезаписывается, и имя с одной только датой разрешило бы ровно один прогон в сутки, а второй закончился бы отказом.

**Что делает.** Обходит портал обычным адаптером, раскладывает кандидатов по девяти исходам, как всегда, и добавляет в отчёт `report.modelPlan` — какие кандидаты ушли бы в модель, какой отпечаток у их входа и какой политикой это запрещено.

**Чего не делает.** Не вызывает модельного провайдера, не создаёт `store`, не вызывает `writeRun` и `ingestPoiBatch`, не требует ключей провайдера. Несовместим с `--write`, `--dry-write` и `--base-snapshot`: проверка стоит в глобальном преflight и падает до первого адаптера.

**Требования.**

- `--out` обязателен, обязан лежать в `tmp/poi-model-plans/` и **обязан оканчиваться на `.json`**: уборка по сроку ищет `*.json`, и файл с другим именем пережил бы свой срок незамеченным. Каталог в Git не входит. Оканчиваться на `.envelope.json` `--out` не может: это имя зарезервировано за исполняемым конвертом, который тот же прогон пишет рядом с отчётом (`x.json` → `x.envelope.json`), и занятое имя конверта останавливает прогон до адаптера так же, как занятое имя отчёта.
- Путь обязан быть свободен. Занятое имя — отказ, и отказ этот случается **до обращения к порталу**, а не в конце прогона. Финальная запись всё равно идёт эксклюзивно: проверка закрывает долгое ожидание, флаг записи — гонку между проверкой и записью.
- Отслеживаемое рабочее дерево должно быть чистым: план связывается с идентичностью кода, и одним отпечатком нельзя описать два разных состояния. Untracked-файлы значения не имеют.
- План строится только по очереди `awaitingClassification`. `qualityRejected`, разобранное правилами и всё остальное в него не попадает.

**Что в `report.modelPlan`.** Только идентификаторы, версии, отпечатки и счётчики: `planDigest`, `policyDigest` по каждому порталу, `candidateInputDigest` и `sourceKey` по каждому ключу, точные числа байтов канонического представления, промпта и схемы, приблизительная оценка токенов с версией спецификации. Значений полей источника — названий, описаний, адресов — в этом поддереве нет ни одного, и это закреплено тестом.

**Но файл `--out` — это не план.** План лежит внутри полного отчёта, а полный отчёт несёт `portals[].all`, `portals[].writable` и все очереди: японские названия, координаты, часы работы, сайты, адреса и причины отсева. **Весь файл целиком** — выгрузка данных источника, и обращаться с ним нужно как с выгрузкой, а не как с отпечатком.

Отсюда: файл нельзя добавлять в Git (`tmp/` в `.gitignore`, и выводить отчёт куда-либо ещё режим не даёт), нельзя пересылать как «просто план», и срок жизни в семь суток из `deleteAfter` относится **ко всему файлу**, а не к одному его полю.

**Исполняемый артефакт — конверт `<имя>.envelope.json` рядом.** В нём только версия конверта, отпечаток артефакта плана и сам план — те же отпечатки и счётчики, без единого значения полей источника. Именно его имя передаётся в `--model-plan-file`; отчёт читатель исполнения отвергает. Срок у конверта тот же — `plan.deleteAfter` внутри него, — и убирается он вместе с отчётом, поимённо.

**Чего в плане нет и почему.** `estimatedCostUpperBound`, `networkRequestCount`, `batchJobCount` и `billableTokens` равны `null` в плане v1: сколько задач уложится в один запрос и сколько это стоит, решает транспорт провайдера, а в диагностическом плане провайдер не выбран. В плане v2, собранном с `--model-provider-profile`, провайдер назван, но денежный итог по-прежнему считает preflight, а не план.

**Срок жизни и уборка.** Автоматического удаления нет.

**Авторитетная граница удаления — `modelPlan.deleteAfter` внутри самого файла.** Она записана при построении плана и от файловой системы не зависит.

Команда ниже — **поиск кандидатов**, а не проверка срока: `-mmin` смотрит на mtime, а mtime не тождествен `deleteAfter`. Копирование, распаковка архива или случайный `touch` сдвинут mtime вперёд, и просроченный файл в выдачу не попадёт; наоборот, свежий план, восстановленный из резервной копии со старым mtime, попадёт в неё зря.

```bash
find tmp/poi-model-plans -type f -name '*.json' -mmin +10080 -print
```

`10080` минут — семь суток, тот же порядок, что и в `deleteAfter`, но совпадение приблизительное.

Дальше по каждому кандидату смотрят его собственный срок:

```bash
node -e "const r=require('./'+process.argv[1]); console.log(process.argv[1], r.modelPlan?.deleteAfter ?? 'плана нет')" \
  tmp/poi-model-plans/<имя-файла>.json
```

И удаляют **поимённо те пути, у которых `deleteAfter` действительно прошёл**:

```bash
rm tmp/poi-model-plans/<имя-файла>.json tmp/poi-model-plans/<имя-файла>.envelope.json
```

**Массового `find … -delete` здесь нет намеренно.** `find` отбирает по mtime и про `deleteAfter` не знает ничего: в его выдачу попадает и ложноположительное — план, чей mtime состарился при копировании или восстановлении из резервной копии, хотя срок ещё не вышел. Предупредить о ложноположительных в тексте и тут же удалить их одной командой — значит написать предупреждение впустую.

Если ручная сверка станет обузой, нужен отдельный инструмент, читающий `modelPlan.deleteAfter` и покрытый тестами. Пока такого инструмента нет, удаление идёт поимённо. Утверждённый план можно удалять сразу после утверждения, не дожидаясь срока.

**Прогноз каскада — не стоимость запроса.** `portals[].aiCost` считает шире очереди: в него входит всё, что «не reject и не разобрано правилом», включая кандидатов со слабым качеством, которые до очереди не доходят. Это отдельная диагностика, и стоимостью планируемых запросов она не является.

### Журнал исполнения принадлежит эпохе

Ниже плана лежит журнал модельного исполнения, и продолжить его нельзя просто
потому, что файл на месте. Журнал — цепочка сегментов
`journal.<поколение>.e<N>.jsonl`; захват эпохи есть создание её файла, и он
одноразов. Поколение — часть грамматики, а не украшение имени: новые журналы
пишутся поколением `g2`, где каждой отправке обязана предшествовать
синхронизированная запись `prepared` с отпечатком и длиной исходящих байтов.
Журналы `g1` читаются прежней грамматикой и продолжаются тем поколением,
которое стоит в именах их сегментов, — выбрать поколение параметром нельзя.

Что это значит на практике, когда путь исполнения станет достижимым:

- прежний владелец либо освободил эпоху записью `released`, либо нет; во
  втором случае продолжать нельзя без решения владельца
  `poi-model-takeover/v1`, связанного отпечатками с точным хвостом и со всеми
  незавершёнными сегментами;
- незавершённый или оборванный сегмент **не пропускается автоматически**:
  «файл пустой» не доказывает, что его создатель мёртв;
- записи, появившиеся за границей перехвата, дают `journalForked` — отдельный
  код возврата, никаких счётчиков и никакой дозаписи; разбирать вручную;
- журнал прежнего формата (`journal.jsonl`) читается и сохраняет свой итог, но
  дозаписи не принимает;
- сегменты разных поколений в одном каталоге исполнения — повреждение: часть
  эпох читалась бы одной грамматикой, часть другой, и вердикт о деньгах
  зависел бы от того, с какого сегмента начали;
- **ни одна из этих проверок не отменяет запрос, который прежний живой процесс
  уже успел отправить.** Это исключает только правдивое утверждение владельца
  в основании перехвата, а не файловый протокол.

Сегодня платного исполнения нет — но держится это уже не отсутствием кода.

**Production-entrypoint существует** (пакет 10f-O, принят независимым аудитом 03.09.2026):

```bash
npm run poi:collect -- --model-execute \
  --model-plan-file <имя>.envelope.json --model-approval <имя>.json
```

Режим принимает ТОЛЬКО эти три флага, и проверяется это по фактически
переданным флагам, а не по получившимся значениям: `--samples 8` ставит ровно
умолчание и всё равно отвергается. У конверта и разрешения нет пути — только
имя: конверт читается из `tmp/poi-model-plans/`, разрешение — собственным
store из `tmp/poi-model-approvals/`, и вложенность обоих проверяется физически.

Исполняемый артефакт — **конверт**, а не отчёт. `--model-plan --out x.json`
пишет рядом с отчётом `x.envelope.json` (`poi-model-plan-envelope/v1`) ровно
из трёх полей: `contractVersion`, `planArtifactDigest`, `plan`. Отчёт — выгрузка
данных источника; полномочий он не несёт, и читатель отвергает его, называя
конверт. Голый план отвергается так же. Времени прогона, `dryRun` и списка
порталов в конверте нет: их источник — подписанный план внутри, второй внешней
копии этих величин конверт не даёт. Объявленный отпечаток пересчитывается из
плана и обязан совпасть.

Профиль и таблица цены выводятся из подписанного плана и канонических реестров,
вторым вводом не принимаются, а отпечаток профиля из реестра сверяется с
отпечатком в плане.

Что происходит при запуске сегодня: preflight отказывает на воротах, процесс
получает точный код возврата (`11` — разрешение отвергнуто, `10` — прочие
ворота), журнал не открывается, переменная с секретом не читается, провод не
вызывается. Три причины, по которым живой вызов не состоится:

1. policy всех двенадцати источников запрещает модельную обработку (ворота P7);
2. разрешения владельца в репозитории нет;
3. отдельная переменная `POI_MODEL_EXECUTION_OPENAI_API_KEY` не задана — общий
   `OPENAI_API_KEY` этот путь не открывает намеренно.

Поэтому ни одного production-журнала по-прежнему не существует. Проверяется
всё перечисленное исполнением: `tests/poi-model-entrypoint.mjs` и
`tests/poi-model-reachability.mjs`.

## 2б. `--portal japan-guide` — discovery-обход

Отдельный режим и отдельный род данных. Он НЕ производит кандидатов в POI и
ничего не пишет: результат — записи `poi-discovery-record/v2` с
неподтверждёнными подсказками, сложенные в отчёт `--out`.

```bash
node scripts/poi-portals/collect-pois.mjs --portal japan-guide --out tmp/jg.json
```

**Что отказывает до первого сетевого запроса.** `--write`, `--dry-write`,
`--base-snapshot`, `--model-plan`, `--model-provider-profile`, `--names`,
`--existing` — любой из них вместе с discovery-порталом останавливает прогон
целиком. Отказ глобальный, а не «портал пропущен»: пропуск выглядел бы как
успешный прогон, в котором просто ничего не записалось.

**Что в отчёте.** По каждому объекту: имя с H1, привязки (`placements`),
подсказки, `omissions` с причинами потерь и `pageEvidence` со свидетельством
наблюдения, включая роль страницы. По каждой коллекции: её порядок и его
отпечаток — начиная с `v3` это одна последовательность элементов
`{ role, sourceKey }`, где роль `poi` или `collection`, поэтому вложенная
коллекция стоит в списке на своём месте, а не выдаёт себя за объект.
Свидетельства коллекций разделены по происхождению: `catalogueTargetEvidence` —
цели каталога, `nestedCollectionEvidence` — коллекции, найденные ниже него.
Отдельно — ЧЕТЫРЕ списка отказов: по целям каталога, карточкам, узлам графа
(`rejected.nodes` — страница, роль которой установить не удалось, с указанием
коллекции-источника) и объектам.

**Привязка бывает трёх видов.** `destinationRanking` — карточка в списке
коллекции, с позицией, уровнем рекомендации и категорией. `catalogueDirect` —
объект, указанный прямо в каталоге. `containerChild` — ребёнок зонтичной
страницы `/e/eNNNN.html`, найденный по ссылкам на `/e/eNNNN_ddd.html`. У
последних двух все три поля ранжирования равны `null`, потому что ранга сайт
не показывает вовсе, а выдуманную единицу нельзя отличить от измеренной.

Вид размещения сверяется с `collectionKind` порядка (`ranked` либо
`container`), и это поле входит в `orderDigest`; с `v3` в отпечаток входит и
роль каждого элемента. Текущие форматы — `poi-discovery-snapshot/v3` и
`poi-discovery-order/v3`; `v1` и `v2` заморожены и читаются каждый по своим
правилам. Формат ЗАПИСИ остался `poi-discovery-record/v2` и не менялся:
на одну спецификацию записи ссылаются две политики снимка, и совпадение их
правил проверяется при загрузке контракта.

**Роль страницы — данные, а не форма адреса.** Каталог перечисляет цели трёх
измеренных форм, и роль каждой вычисляется по структуре: `/destinations/<slug>/`
бывает и коллекцией, и объектом. Цель, проходящая обе грамматики сразу или ни
одной, отвергается и делает снимок неполным.

**Чего в отчёте нет.** Прозы источника в любом виде, изображений, сырых байтов
страниц и текста отвергнутых значений: в `omissions` попадает код причины,
локатор и длина, но не содержимое.

**Подсказка фактом не является.** `confidence` — перечисление из одного
значения `unverified`, `verified_at` всегда `null`. Публиковать часы и цены по
этому источнику нельзя: он говорит, ЧТО искать, а не какой ответ верен.

**robots.txt первым и перед каждым обменом.** Прогон начинается с
`robots.txt`; policy разбирается один раз и спрашивается перед каждым
запросом, включая цели редиректов. Сопоставление по RFC 9309 (`*`, `$`,
percent-encoding); группы выбираются по product token, `*` — только при
отсутствии именной. Запрет, недоступность или негодное содержимое
останавливают прогон, а не превращаются в очередную недоступную страницу.

**Снимок или диагностика.** Результат — `poi-discovery-snapshot/v3` с полями
`scope`, `complete` и `incompleteReasons`. Полным снимок считается только
после полного обхода без потерь. Неполный снимок пригоден как диагностика, но
основанием для сравнения не является.

**Счётчик обменов у `v3` снизу ограничен составом снимка.** Обход графа
получает КАЖДУЮ классифицированную страницу, поэтому `networkRequests` — не
свободное число: контракт требует не меньше чем `2` (robots и каталог) плюс
свидетельства целей каталога, плюс свидетельства вложенных коллекций, плюс
достижимые объекты вне прямых, плюс отказы целей и узлов, у которых обмен
всё-таки состоялся.

Стадию отказа определяет НЕ код сам по себе, а канал, в котором он записан.
Досетевых исходов у цели два — `networkBudgetExhausted` и
`unsupportedCatalogueLinkShape`; у узла графа один — `networkBudgetExhausted`.
Всё остальное границу поднимает, включая коды канонизации адреса: цель и узел
приходят в обход уже с каноническим адресом, поэтому такой код может прийти
только из `Location` уже полученного 3xx-ответа. Отказы объектов в границу не
входят: их страница уже посчитана достижимым объектом.

Неравенство, а не равенство: редиректы законно увеличивают счётчик.

**Потолки обхода снимок несёт в себе.** Поле `networkPolicy` —
`maxNetworkRequests` и `maxRedirects` — входит в `snapshotDigest` и даёт два
безусловных правила: обменов не бывает больше бюджета, а снимок, объявивший
`networkBudgetExhausted`, обязан стоять ровно на потолке. Без этого одна цель
могла получить два ответа 3xx, упереться в бюджет — и снимок объявил бы вдвое
меньше обменов, чем потратил, оставаясь внутри нижней границы. Потолки пишет
сам обход из тех `limits`, под которыми шёл; сверять их с `FETCH_LIMITS` — дело
потребителя, контракт этого доказать не может.

`maxRedirects: 0` — законный режим «за редиректами не ходить»: первый же 3xx
отвергает цель кодом `redirectLimit`. Бюджетные правила при нуле те же.

К замороженным `v1` и `v2` ни граница, ни потолки не применяются — там
`--limit` действительно экономил сеть. Счётчик попыток построить запись у `v3`
называется `recordsAttempted`: в графе страница объекта получена ещё на
классификации, и прежнее имя `poisVisited` описывало бы не ту величину.

**Обход — граф коллекций, а не два уровня.** Измерение 21.08.2026 показало,
что карточка ранжированной коллекции может вести на другую коллекцию: 29 из
1170 «объектов» первого полного обхода оказались коллекциями, а настоящий
уникальный корпус — 1141 объект. Начиная с `v3` порядок коллекции — одна
последовательность элементов с явной ролью `poi` либо `collection`, обход
идёт детерминированным BFS, каждый канонический адрес запрашивается один раз,
а коллекция никогда не считается объектом. Снимки `v1` и `v2` заморожены и
читаются прежними правилами; сравнивать снимки разных версий нельзя, и
монитор отказывает до сравнения отпечатков.

**Мониторинг.**
 `--monitor` даёт по discovery-порталу отдельный раздел
`discoveryMonitor` с независимыми частями: семантические изменения, изменения
наблюдения (размер и отпечаток страницы объекта), перестановки внутри
коллекций, родительские страницы, топология графа и сигналы кодировки.
Разделение не косметическое: страница источника меняется в размере несколько
раз в день, и без него каждый прогон объявлял бы изменившимися все объекты.

Родительские страницы и кодировка покрывают ВЕСЬ граф — каталог, его цели и
вложенные коллекции. Топология сообщает появление и исчезновение самой
коллекции: до 24.08.2026 такой узел мог прийти и уйти при нулевом отчёте.
Перестановкой называется только изменившаяся последовательность; переверстка
страницы с тем же списком карточек идёт в родительские страницы, а не
выдаёт себя за перестановку.

**Исчезнувший объект не считается закрытым.** Раздел называется
`vanishedForHumanReview` именно поэтому: выпадение из списка — редакционное
решение источника, а не факт о мире.

## 2в. Baseline живого обхода и сопоставление с Airtable

**Baseline — манифест И артефакт, оба в Git.** Отчёт полного обхода весит
6 507 108 байт; в репозиторий он положен gzip'ом С НОРМАЛИЗОВАННОЙ ШАПКОЙ, без метаданных машины
(683 037 байт):

```
docs/poi-intake/baselines/japan-guide-v3-2026-08-25.json          — манифест
docs/poi-intake/baselines/japan-guide-v3-2026-08-25.artifact.json.gz — данные
```

Контейнер собран вручную — `deflateRawSync(level 9)` плюс фиксированная
шапка, — чтобы в файл не попали метаданные машины: `gzipSync` пишет в шапку байт
операционной системы и время. Байт ОС выставлен в `0xff` («неизвестна»), время —
нулём.

**Воспроизводимость байт между средами НЕ обещается.** Шапку мы задаём сами, а
тело потока пишет `deflateRawSync`, и его вывод — свойство сборки zlib, а не
формата: аудит 25.08 пересобрал тот же отчёт в 714 522 байта против 683 037 у
файла в репозитории. Поэтому tracked-байты считаются НЕИЗМЕНЯЕМЫМ артефактом:
их не пересобирают и с пересобранными не сравнивают.

Доказывают его ТРИ отпечатка, каждый отдельно: сжатых байт, распакованных байт
и снимка (`snapshotDigest`). Первый доказывает, что в репозитории лежит ровно
тот файл; второй — что из него получается ровно тот отчёт; третий — что внутри
ровно тот снимок. Совпадение любых двух не заменяет третьего.

```bash
node scripts/poi-portals/verify-discovery-baseline.mjs \
  docs/poi-intake/baselines/japan-guide-v3-2026-08-25.json
```

Порядок проверок — от доказуемого байтами к требующему разбора: форма
манифеста (точная, с путём каждого расхождения) → чтение и распаковка ПОД
ПОТОЛКОМ в 12 МБ → сверка обоих представлений → разбор JSON → выбор портала
ПОИМЁННО (`japan-guide`, а не «первый в отчёте») → производственный контракт
снимка → и только теперь сверка описания.

`poi-discovery-baseline/v1` описывает РОВНО ОДИН формат снимка —
`poi-discovery-snapshot/v3`. Манифест с меткой `v1`, `v2` или будущего `v4`
отвергается поимённо: для другого формата нужен `poi-discovery-baseline/v2`
либо явный мигратор. Сверяется и ФАКТИЧЕСКИЙ формат внутри архива: снимок
другой версии, упакованный каноническим gzip с пересчитанными отпечатками,
отвергается ПОСЛЕ контракта и ДО описания — иначе байты сходятся, контракт
снимок принимает, а описание разваливается на первом отсутствующем поле. Та же
проверка стоит и на самой `describeDiscoveryBaseline`. Это не осторожность, а факт о модуле — описание читает
`nestedCollectionEvidence`, которого у `v1` нет, и на настоящем `v1`-снимке
просто падает.

Манифест проверяется ДО ЛИСТА и по версии формата. У `scope`, `networkPolicy` и
причин неполноты — точные ключи и области значений, взятые из политики версии
снимка, а не переписанные вторым списком; у отпечатков — синтаксис
(`sha256:` и 64 hex), у чисел — область, у моментов наблюдения — вид
`2026-08-25T01:30:23.730Z`; `complete` обязано следовать из состава, а не
объявляться. Путь артефакта обязан быть каноническим относительным путём прямо
в `docs/poi-intake/baselines/` и оканчиваться на `.json.gz`; загрузчик проверяет
манифест САМ и ДО чтения файла, а затем судит разрешённый путь второй раз —
файловой системой, потому что символьная ссылка внутри каталога уводит чтение
наружу, оставаясь безупречной строкой.

Кодов возврата два: `0` — сошлось, `1` — расхождение, отказ контракта или
ОТСУТСТВУЮЩИЙ АРТЕФАКТ. Прежний код `3` («артефакта нет, сверка не
выполнялась») отменён вместе с причиной: артефакт версионируется вместе с
манифестом, и его отсутствие означает не «локально не скачан», а порчу клона.
По той же причине `npm test` выполняет настоящую сверку baseline в свежем
клоне всегда, а не при удачном стечении обстоятельств, и ничего не берёт из
`tmp/`.

**Мониторинг `v3` → `v3`** проверен на живом снимке: сравнение baseline с самим
собой не сообщает ни одного изменения на 1140 записях, а каждое возмущение
попадает ровно в свой раздел — переименование в смысловые, другие байты
страницы в наблюдение, перестановка карточек в перестановки, перевёрстка
страницы коллекции (включая вложенную и сам каталог) в родительские страницы,
исчезновение коллекции в топологию. Возмущения собираются производственными
строителями, и сначала доказывается, что пересборка без изменений даёт тот же
`snapshotDigest`.

**Сопоставление с Airtable — только чтение и только раскладка.**

```bash
node scripts/poi-portals/match-discovery-to-airtable.mjs \
  docs/poi-intake/baselines/japan-guide-v3-2026-08-25.artifact.json.gz \
  tmp/airtable-poi-export-2026-08-25.json \
  tmp/poi-airtable-match-2026-08-25.json
```

Скрипт не умеет писать в Airtable и не ходит в сеть: выгрузка подаётся файлом.

**Что считается одной страницей.** Адрес разбирается СВОИМ строгим выражением,
без `new URL`: разбор WHATWG чинит адрес за нас и раньше нас — заменяет
обратные слэши прямыми, отбрасывает лишние слэши перед authority, схлопывает
точечные сегменты, — и обе подделки
`https://www.japan-guide.com\e/e3003.html` и
`https:////www.japan-guide.com/e/e3003.html` на живой паре входов
автоматически связывались с `e3003`.

Принимается ровно: `http://` или `https://`, непустой authority только из букв,
цифр, точек и дефисов, путь из сегментов через ОДИН прямой слэш. Приводятся
схема, регистр имени хоста, точный префикс `www.` и один хвостовой слэш.
РЕГИСТР ПУТИ СОХРАНЯЕТСЯ: в HTTP `/e/E1.html` и `/e/e1.html` — разные ресурсы.
На вход принимается только ПРИМИТИВНАЯ СТРОКА, и она не подрезается: объект
`URL` (он чинит написание сам) и строка с внешними пробелами идентичности не
получают. Идентичности не дают вовсе: обратный слэш, лишние слэши, запрос,
фрагмент, учётные данные, неумолчаный порт, точечные сегменты, процентное
кодирование, пробельные знаки в пути и хост с хвостовой точкой — раскрывать псевдоним значит решать за источник, какие
его адреса одинаковые.
ОБА ВХОДА ПРОВЕРЯЮТСЯ ДО РАБОТЫ. Снимок: полный производственный контракт —
в скрипте, до вызова; в самой границе — то, чем пользуется раскладка и что
попадает в отчёт как привязка (известная версия формата, настоящий отпечаток,
записи с ключом, именем и адресом). Выгрузка — контрактом
`poi-airtable-export/v1`. Проверяются: каноническая пара
база/таблица (берётся из `src/lib/airtable-schema.ts`, публичной подмены нет),
дата выгрузки, `totalRecordCount` против длины, уникальные `recordId` и POI ID,
типы и ОБЛАСТИ ЗНАЧЕНИЙ полей — и ПРОЕКЦИЯ: `fields` обязан доказывать, что
каждое используемое сопоставлением поле было запрошено. Выгрузка
`fields: ["poiId"]` формально исправна и объявила бы все 1140 объектов
несопоставленными — «не найдено» означало бы «мы не спрашивали».

Публичная граница принимает БАЙТЫ выгрузки и сама считает их SHA-256: отпечаток
в отчёте — доказательство, а не объявление вызывающего. Отчёт привязан к обоим
входам — `snapshotDigest` снимка и отпечаток байт выгрузки вместе с её версией,
базой, таблицей, датой и числом записей.

Исходы и сила свидетельства: `Source Key` — утверждение базы о себе; адрес
страницы — совпадение источника; совпадение имени — только КАНДИДАТ,
требующий человека. Имя не идентификатор: `Rinnoji Temple` есть и в Никко, и в
Сэндае, и такой случай уходит в `ambiguous`.

Противоречие свидетельств связью не становится НИКОГДА:

* `duplicateSourceKey` — один `Source Key` стоит у нескольких записей: дефект
  базы, о котором надо сказать, а не выбор «последней по порядку выгрузки»;
* `sourceKeyWebsiteDisagreement` — `Source Key` указывает на один объект, а
  `Website` на другой: такая запись выбывает из ВСЕХ указателей сразу, иначе
  второй объект молча связался бы с ней по адресу;
* `sourceKeyUnknownToCrawl` — `Source Key` непустой, но обходу неизвестен
  (исчезнувший объект, чужой портал, опечатка), а `Website` ведёт на страницу
  обхода: строка утверждает о себе, что она другой объект, и отката к связи по
  адресу здесь нет. Строка, чей адрес в обход вообще не попадает, конфликтом не
  объявляется — иначе конфликтом стала бы вся остальная база;
* `severalRowsOnOnePage` — несколько записей базы ссылаются на одну страницу
  источника: какая из них об этом объекте, решает человек. Обратной ветви —
  «несколько объектов обхода на одной странице» — нет и быть не может:
  контракт снимка требует, чтобы `sourceKey` выводился из адреса, значит одна
  страница даёт ровно один объект.

Автоматическая связь обязана быть один-к-одному, и это ПРОВЕРЯЕТСЯ отдельным
сторожем: состояние, в котором на одну запись Airtable претендуют два объекта,
обязано быть громким, а не улаженным выбором первого.

|---|---|---|
| `npm test`, `npm run typecheck`, `npm run lint`, `npm run check:docs` | нет | нет |
| `npm run verify`, если ключей нет ни в окружении, ни в `.env.local` | нет: живые проверки печатают пропуск или берут фикстуру | нет |
| `npm run verify`, если ключи доступны через окружение или `.env.local` | **да** — read-only-запросы к Airtable | **да** |
| `poi:collect` без флагов записи | **да** — датасет портала | нет |
| `poi:collect --base-snapshot` | **да** — датасет портала | **нет**: база читается из файла |
| `poi:collect --dry-write` | **да** | **да** — читает живую базу |
| `poi:collect --write` | **да** | **да** — читает и пишет |

Сеть нужна любому сбору: датасет портала загружается всегда. `--base-snapshot` избавляет только от Airtable — снимок базы берётся из файла, поэтому смотреть на исходы гейта можно, не имея прав на запись.

## 3а. Опознание места: офлайн-приёмка и разовый живой canary

Опознание места стоит денег: каждое обращение к Google Places платное. Поэтому
проверяется оно двумя разными прогонами, и путать их нельзя.

**Офлайн-приёмка** идёт в `npm test` и денег не стоит:
`node tests/poi-canary-osaka-offline.mjs` — двадцать настоящих строк портала
`bodik-osaka-tourism` и замороженные ответы Google из
`tests/fixtures/poi-canary-osaka/`. Ни сети, ни Airtable, ни ключей. Это
единственный прогон, который допустимо запускать без разрешения.

**Живой canary — разовое наблюдение**, каждый раз по отдельному разрешению
владельца. Условия, при которых он вообще запускается:

1. объявленный потолок обращений задан **флагом**, а не намерением:
   `--max-place-lookups <n>`; превышение останавливает прогон до первого
   запроса;
2. Airtable не читается и не пишется — хранилище берётся снимком в памяти или
   файлом (`--base-snapshot`);
3. автоматического повтора нет: не получилось — прогон объявляется
   заблокированным (`liveCanaryBlocked`), а не повторяется;
4. в отчёт кладётся только то, что разрешено хранить: `place_id` — бессрочно,
   координаты — с явным сроком годности 30 суток, отображаемые имена Google не
   сохраняются вовсе (это содержимое, а не идентификатор);
5. отчёт обязан покрывать **весь вход**. Три терминальных исхода — запись,
   «место не опознано» и «границу места прошла, но записью не стала» — и сумма
   по ним равна числу строк. Отчёт, в котором строк меньше, чем на входе,
   выглядит полным, не будучи им.

Ключа, сети или разрешения нет — живой canary не запускается, и его результат
не выдумывается: приёмка остаётся на офлайн-прогоне.

## 4. `--write` без решения владельца запрещён

Это единственная команда во всей подсистеме, которая создаёт записи в боевой базе. Запускается только по явному решению владельца, на конкретный портал, после того как отчёт от `--base-snapshot` разобран.

## 5. Инварианты, которые проверяются на каждом прогоне

Все три падают с текстом ошибки и останавливают прогон.

1. **Сумма терминальных исходов.** Каждый кандидат попадает ровно в один исход; сумма девяти очередей обязана равняться числу выгруженных записей.
2. **Цепочка `poiEligible`.** `poiWritable + outsideRegion + cityUnresolved + poiDeduped` обязано равняться числу `poiEligible`. Расхождение означает, что часть выгрузки исчезла без следа.
3. **`canAutoImport` = `portal.writable`.** Множества обязаны совпадать по ключам; условие в системе одно, и если оно разъедется, прогон остановится.

Плюс остановки на пути записи, все до обращения к Airtable:

4. **Контракт снимка базы** — при `--base-snapshot` файл читается и проверяется до обращения к порталу и до любой сети.
5. **Preflight маршрута** — каждая входящая строка перепроверяется реестром до чтения файла имён.
6. **Покрытие файла имён** — до создания store.
7. **Представимость таксономии** (10f-P) — до чтения файла имён, той же функцией, что собирает поля записи.
8. **Схема живой базы** (10f-P) — writer сам сверяет четыре поля таксономии с реестром по живой схеме, которую отдаёт хранилище (`readSchemaTables`), до первого чтения базы и до резолвера; снимок базы — только объект фабрики `createMemoryPoiStore`, узнаваемый по тождеству, — схемы не имеет, и проверка называется пропущенной.

## 6. Где искать полные очереди

В stdout печатается сводка: счётчики и выборки. Полные списки в консоль намеренно не идут — они не читаются. Всё полное лежит в файле `--out`:

| Поле в `--out` | Что внутри |
|---|---|
| `queues.poiEligible` | прошли таксономию и качество |
| `queues.classificationNeedsReview` | решает человек |
| `queues.excludedByTaxonomy` | исключено политикой, с причиной |
| `queues.routedElsewhere` | ушло в другой каталог; в строке `catalogTarget` — какой именно |
| `queues.awaitingClassification` | правила не разобрали, ждёт модель |
| `writable` | финальный список к записи |
| `cityUnresolvedQueue` | муниципалитет не распознан |
| `collisionQueue` | коллизии дедупа с исходом каждого кандидата |
| `all` | все кандидаты с оценкой и исходом |

В каждой строке очереди: `sourceKey`, `nameJa`, вид сущности, тип, исход приёма, каталог, причина отказа, идентификатор правила реестра, происхождение классификации и текстовая причина исхода. Почтового адреса и координат в очередях нет — они лежат в `writable` и `all`.

## 7. Диагностика по исходам

| Исход | Что означает | Куда смотреть |
|---|---|---|
| `poiWritable` | **допущен к пути записи**, а не гарантированно заведён | `writable` |
| `classificationNeedsReview` | правило совпало, но однозначного типа нет, либо вид сущности не опознан | `reason` в очереди: там текст, почему шаблон неоднозначен |
| `excludedByTaxonomy` | политика исключает — инфраструктура, розница, услуга | `excludeReason`; если исключение кажется неверным, это вопрос к правилу, а не к записи |
| `routedElsewhere` | объект принадлежит другому каталогу — отель, ресторан, событие, впечатление | `catalogTarget` |
| `awaitingClassification` | ни один шаблон не совпал | очередь к модели, потребитель № 2b |
| `qualityRejected` | блокер или недобор баллов | `blockingReasons` в `all` |
| — география | город не определён или не маршрутный | `cityUnresolvedQueue`, `outsideRegion` |
| — дедуп | совпало с другой записью партии | `collisionQueue`, поле `candidateTerminal` |

### `poiWritable` — это допуск, а не гарантия

Попасть в `writable` значит пройти таксономию, качество, географию и дедуп внутри партии. После этого запись всё ещё может не появиться, и это нормальный ход:

1. **Файл имён** — если покрытие не сходится, `writeRun` останавливается целиком.
2. **Legacy-мост** — если тип не переводится в старое значение категории, останавливается целиком (§8).
3. **Гейты самого Intake** — канон, идемпотентность по `Source Key`, поиск дублей и `needs_review`. Здесь отказ уже поштучный: одна запись может не создаться, а соседняя создаться.

Итог прогона по исходам — счётчики в `write.outcomes`: `created`, `already_ingested`, `needs_review`, `rejected_canon`, `blocked_duplicate`.

Порядок ветвления: **сначала таксономия, потом качество.** Рёкан не «отклонён по качеству» из-за блокера «средство размещения» — он `routedElsewhere`, потому что принадлежит отельному каталогу. Это осознанный порядок, а не побочный эффект.

## 8. Legacy-мост, поля таксономии и схема живой базы

Старое поле категории в Airtable говорит русскими названиями. Мост переводит код реестра в старое значение **только там, где перевод точен**: таких кодов девять из двадцати. Для остальных одиннадцати он возвращает `null` с причиной.

С 10f-P (кандидат, до независимого аудита) мост **не останавливает запись**: истина о типе едет кодом в четыре канонических поля — `POI Type`, `POI Facets`, `Type Source`, `Taxonomy Version` (связь реестр↔схема — `src/lib/poi-taxonomy-airtable.ts`). Старое поле заполняется там, где перевод точен, иначе остаётся пустым; такие строки видны в `write.legacyCategoryMissing` / `legacyCategoryMissingQueue` и в Notes записи («старое поле категории не выражает тип …»). Пустое старое поле при заполненном `POI Type` читается как «мост не выражает», а не «не заполнили».

Две остановки на этом пути остались, обе до обращения к базе:

- **представимость таксономии** — каждая строка `writable` проверяется той же функцией, которой писатель собирает поля; чужой код, повтор фасета, чужой источник или версия реестра не loader'а (устаревший отчёт) останавливают прогон до чтения имён: «Таксономия N строк … не представима в схеме POI»;
- **схема живой базы** — ветку снимка открывает только тождество: хранилище в памяти создаётся фабрикой `createMemoryPoiStore` и узнаётся `isMemoryPoiStore` (WeakMap-тождество объекта и его методов). Строка `writeTarget: 'memory'`, spread-копия, прототип или подмена метода на месте тождества не дают, и такой объект идёт по эффектной ветке. Эффектное хранилище обязано отдать живую схему методом `readSchemaTables` (Airtable-store читает её через Meta API `GET /v0/meta/bases/{baseId}/tables`, чтение; токену нужен scope `schema.bases:read`), а writer сам (`ensureTaxonomySchemaForWrite`) находит таблицу по каноническому `POI_TABLE_ID` (таблица «POI» под чужим ID — отказ) и сверяет четыре поля с реестром до первого чтения базы и до резолвера; самоаттестация хранилища («я проверил») не принимается, хранилище без `readSchemaTables` при полях таксономии — отказ, не пропуск. Пока полей нет — «Схема таблицы POI не соответствует реестру таксономии: нет полей …»; поля создаются только цепочкой § 8б по замороженной карточке и отдельному разрешению. `--base-snapshot` пишет в память, схемы не имеет по построению, и отчёт честно пишет `taxonomySchema.checked: false, memory: true`.

То же расхождение видит `npm run check:poi`: `WARN taxonomy_schema_missing`, пока полей нет; `FAIL taxonomy_schema_drift`, если поле есть, но тип или опции не те.

### 8а. Решения владельца о политике координат

`representativePoint` и `notApplicable` машиной не выводятся. Они доходят до записи одним путём — реестром `config/poi-coordinate-decisions.v1.json` (`poi-coordinate-decision/v1`), который writer читает статическим импортом по каноническому пути. Другого канала в коде нет: ни `options`, ни `deps`, ни фабрики, ни поля запроса. Честно о том, что это доказывает: статический импорт и контрольная сумма **не доказывают авторство** — импорт закрывает обходные каналы в коде, а сумму пересчитает кто угодно; полномочие задаётся процессом owner review — правка реестра попадает в main только через ревью владельца, и удостоверяет решение именно этот процесс, а не код. Запись: `sourceKey` в форме `<источник>:<ключ>`, `subject` (канонический слаг города и хотя бы одно имя объекта — `nameJa`, `nameEn`, `nameRu`), `decision`, `point` только у `representativePoint`, `decisionRef`, `approver`, канонический `decidedAt`, обязательная `note`, `integrityDigest`. Контрольная сумма считается и проверяется скриптом; она — целостность записи (ловит правку без пересчёта и опечатку), **не подпись и не доказательство авторства**:

```bash
node scripts/poi-coordinate-decision.mjs --stamp draft.json   # печатает запись с integrityDigest
node scripts/poi-coordinate-decision.mjs --check              # проверяет реестр под git тем же loader'ом
```

Решение применяется только к записи, совпавшей с `subject` по городу и всем названным именам: у части порталов ключ строки нестабилен (`row-N`), и после перестановки под тем же ключом стоит другой объект — такая строка останавливается именованным отказом `decisionSubjectMismatch` (очередь `write.coordinateDecisions.rejectedQueue`), а не получает чужое решение.

`writeRun` консультирует реестр до резолвера: решённая строка Google не оплачивает, точка берётся из решения либо остаётся пустой; `ingestPoi` перепроверяет предмет и согласие решения с записываемой парой и пишет след решения в Notes. Отчёт прогона показывает `write.coordinateDecisions` (`applied`, `rejected`) и `placeBudget.skippedByCoordinateDecision`. Пустая пара без решения по-прежнему останавливает запись: отсутствие координат — не `notApplicable`.

Тест композиции не подставляет реестр в код: он кладёт фикстурный файл по каноническому пути в песочницу-копию дерева (`tests/support/production-sandbox.mjs`) и запускает там тот же production-код.

### 8а-2. Обновление координат существующих записей подчинено политике

Решение владельца должно переживать не только приём, но и все последующие писатели координат. До 3 сентября 2026 года два refresh-пути — ежедневный крон `src/app/api/cron/refresh-coords/route.ts` и ручной `scripts/refresh-google-coords.mjs` — не читали `Coordinate Policy` и перезаписывали точкой Google любую запись с `place_id`: у `representativePoint` точка владельца молча заменялась центроидом Google (политика и след в Notes при этом продолжали говорить о точке, которой в записи больше нет), у `notApplicable` появлялись координаты, половину пары один писатель дописывал, другой объявлял сдвигом в одиннадцать тысяч километров. Контрпример воспроизведён на production-коде обоих путей без сети: `tmp/10f-p-p07-refresh-repro-cron-OLD-2026-09-03.log`, `tmp/10f-p-p07-refresh-repro-manual-OLD-2026-09-03.*`.

Теперь допуск и состав записи решает один контракт — `src/lib/poi-coordinate-refresh.ts` (`coordinateRefreshEligibility`, `planCoordinateRefresh`); оба писателя импортируют его, запрашивают у Airtable все поля контракта, включая `Coordinate Policy`, и отправляют ровно `plan.fields`. Таблица допуска явная и fail-closed:

| Запись | Refresh |
|---|---|
| `exactObjectPoint`, полная пара | обновляется: точка и есть кэш точки места; сдвиг > 3 км — `hold`, пишется только `Coords Checked At` |
| политика пуста (legacy), полная пара, `place_id` | обновляется как прежде (`legacyGoogleCache`); политика НЕ назначается — refresh не миграция |
| `representativePoint` (с парой, без пары, с половиной) | никогда: точка принадлежит решению владельца; ни координаты, ни отметка не трогаются |
| `notApplicable` | никогда: координат по решению нет; refresh их не заводит |
| неизвестное непустое значение политики | никогда |
| `exactObjectPoint` без полной пары | никогда: противоречие для `check:poi`, не работа для refresh |
| половина пары (любая политика, кроме решённых выше) | никогда: сломанная запись, не кэш |
| legacy без координат | никогда: refresh не решает, незакрытая это работа или снятая точка |

Записи, не подлежащие обновлению, в очередь крона не попадают и в Google не спрашиваются; сводка крона (`пропущеноПоПолитике`) и вывод скрипта называют их по причинам. Открытая граница названа явно: legacy-запись с полной парой обновляется, не имея явного решения владельца, — это единственный такой случай, и закрыть его может только миграция 444 legacy-записей, которая в область 10f-P не входит.

Решение владельца, принятое ПОСЛЕ первоначального чтения, не затирается. Между чтением очереди и PATCH проходят запросы к Google, и владелец может успеть поставить `representativePoint` или `notApplicable`. План строится не по снимку очереди, а по СВЕЖЕМУ чтению ровно тех записей, что идут в пачку (`filterByFormula` по `RECORD_ID()`), и только если политика, пара и `place_id` не изменились со снимка (`ownerStateDifference`); иначе именованный отказ `changedSinceRead` — запись откладывается до следующего прогона (крон: `отложено` в сводке; скрипт: `↺ … отложено`), а не перезаписывается. Недоступное свежее чтение — `freshReadUnavailable`, тоже без записи. Честно о границе: у Airtable нет условной записи, окно между свежим чтением и PATCH остаётся — один запрос, а не минуты прогона; оно названо, а не спрятано.

Повреждённое значение `Coordinate Policy` (не строка — число, массив, объект; строка из пробелов) — не пустая политика: именованный отказ `corruptPolicy`, не `legacyGoogleCache`. Пусто — только `null`/`undefined`/`''`. Различает их `readPolicyField`.

Семантика `hold` и «пара не изменилась» одна у обоих писателей: и `write` (пара Google + отметка, даже если пара совпала), и `hold` (сдвиг > 3 км: только отметка) — это PATCH ровно `plan.fields`; разница между писателями лишь в режиме (показ или запись), не в трактовке плана. Прежняя редакция скрипта неизменившуюся пару и `hold` просто пропускала, оставляя `Coords Checked At` устаревшим, — и такая запись возвращалась в каждый прогон; теперь отметка ставится всегда, когда запись подлежит обновлению.

Остаточная гонка обнаруживается, а не молчит (круг 3). Условной записи у Airtable нет, и владелец, успевший в окно между свежим чтением и PATCH, получал смешанное состояние — свою политику рядом с парой Google — при рапорте об успехе. Теперь итог КАЖДОЙ записи устанавливается только независимым чтением после пачки PATCH (`classifyPatchOutcome`): `verified` — политика и `place_id` как до записи, пара как в плане (`write`) либо как до записи (`hold`); `notApplied` — PATCH не принят и запись не изменилась (повтор в следующий прогон); иначе `recoveryRequired` с причиной `outcomeMismatch` (что разошлось) или `outcomeUnverified` (чтение недоступно). При `recoveryRequired` крон отвечает `ok: false`, `recoveryRequired: true`, HTTP 500 и перечисляет записи в `требуетВосстановления` (record ID, POI ID, причина, поля); скрипт печатает «ТРЕБУЕТСЯ ВОССТАНОВЛЕНИЕ» с record ID и завершается кодом 1. Ровно один PATCH на уже начатую пачку: ни повтора, ни отката, ни исправляющей записи — смешанное состояние остаётся человеку. Сверяется КАЖДОЕ поле `plan.fields`, включая `Coords Checked At` (круг 4): моменты сравниваются по значению после строгого разбора ISO 8601 в epoch milliseconds (`parseMoment` — календарно строгий и не опирающийся на `Date.parse`, который нормализует «31 февраля» в 3 марта: невозможные день, месяц, время и смещение зоны отвергаются до сравнения, високосный год — по правилу 4/100/400; круг 5), писатель ставит отметку целыми секундами (`checkedAtMoment`) — так честное хранилище с секундной точностью возвращает тот же момент; старая отметка, вернувшаяся после PATCH, — `outcomeMismatch [checkedAt]`, у `hold` это единственный записываемый эффект. После первого `recoveryRequired` пачка классифицируется целиком, а оставшиеся пачки не отправляются вовсе (крон — `остановлено` в сводке с хвостом POI ID; скрипт — «ОСТАНОВЛЕНО после пачки N»); хвост дожидается следующего прогона. Все брошенные значения на границах первичного, свежего и итогового чтения и самого PATCH описываются `describeThrownSafely` (`src/lib/thrown-value.ts`) и писатель не покидают: недоступное свежее чтение — `freshReadUnavailable`, недоступное итоговое — `outcomeUnverified`, PATCH без ответа — итог по чтению.

### 8б. Схемная операция: execution-grade цепочка с bootstrap

Поля таксономии создаются только цепочкой `scripts/poi-schema/`, и только по отдельному разрешению владельца. Точка входа — bootstrap `run-taxonomy-schema.mjs` из одних встроенных модулей Node: для `--verify`, `--witness` и `--execute` она сначала хеширует **все пятнадцать модулей цепочки** (включая саму себя, CLI, состояние четвёрки, gate, `byte-digest`, `canonical-contract`, `src/lib/poi-taxonomy-airtable.ts`, `poi-taxonomy.ts`, `airtable-schema.ts` и `config/poi-taxonomy.v2.json`), сверяет их с карточкой и только потом делает первый динамический импорт (`taxonomy-schema-cli.mjs`). Изменённый runner, исполнитель или реестр делают карточку неприменимой — «bootstrap: цепочка не совпадает с карточкой — ничего не импортировано», и ни один изменяемый модуль не исполняется. `--freeze` — единственный режим без сверки (карточки ещё нет).

```bash
node scripts/poi-schema/run-taxonomy-schema.mjs --freeze tmp/<card>.json    # заморозить карточку (+ .sha256), без сети; повторная запись запрещена
node scripts/poi-schema/run-taxonomy-schema.mjs --verify tmp/<card>.json    # bootstrap-сверка, затем карточка против диска и loader'а, без сети
node scripts/poi-schema/run-taxonomy-schema.mjs --witness tmp/<card>.json   # read-only свидетель: GET схемы по каноническому ID против тел карточки
node scripts/poi-schema/run-taxonomy-schema.mjs --execute tmp/<card>.json --approval <approval.json>   # единственный режим с эффектом
node scripts/poi-schema/run-taxonomy-schema.mjs --verdict tmp/<card>.json --approval <a.json> [--journal <j.jsonl>]   # поздний вердикт: журнал + новое чтение, без POST
```

Точка входа опознаёт себя по РЕАЛЬНЫМ путям (`realpathSync` с обеих сторон сравнения), поэтому запуск через символическую ссылку, `/var` → `/private/var`, путь с пробелом или URL-кодируемым символом вызывает `main` и возвращает настоящий код, а не завершает пустой процесс кодом 0.

Карточка (`poi-taxonomy-schema-card/v5`) — закрытая область ровно четырёх полей, выведенных из loader'а, с отпечатками всех модулей цепочки; правка карточки или любого модуля делает разрешение неприменимым. Исполнение:

- **предполёт read-only, до журнала** — карточка и модули против диска, разрешение против SHA-256 байтов карточки и срока, живая схема в исходном состоянии (`assertQuartetState(…, 0)`: таблица по каноническому ID, ни одного из четырёх полей); любой отказ — до создания журнала и без единого POST;
- **журнал** (`poi-taxonomy-schema-journal/v2`, `tmp/poi-schema-executions/<отпечаток>/journal.jsonl`) открывается эксклюзивно (`wx`, повтор для того же отпечатка запрещён), записи сцеплены отпечатками; на каждое поле — `stateBefore` → `dispatching` (намерение, отпечаток тела) → `sent` → `outcome`;
- **перед КАЖДЫМ POST — свежее чтение и полное состояние четвёрки**: применённый префикс присутствует ровно один раз и совпадает с карточкой, текущее поле и весь суффикс отсутствуют; изменение поля 1 после его сверки останавливает прогон до POST 2;
- **срок обмена**: КАЖДЫЙ полный обмен Meta API — соединение, заголовки и тело — ограничен одним сроком (`deadlineMs`, по умолчанию 30 с). Зависший GET или POST процесс не удерживает: обмен прерывается сигналом. Истёкший GET — недоступное чтение с причиной `readTimeout`; истёкший POST — НЕОПРЕДЕЛЁННОСТЬ (`ambiguous`), которую разрешает только отдельное ограниченное чтение, без повтора POST;
- **форма ответа**: сырой ответ схемы проверяется целиком до обращения к вложенным значениям (таблицы, поля, `options.choices`, `description`); повреждение даёт именованную причину `schemaCorrupt` с адресом (`tables[0].fields[2].options.choices: ожидается массив`), а не исключение из глубины классификации;
- **исход любого POST — только свежим чтением**: 2xx без поля в схеме — `notApplied` и остановка; 4xx при поле в схеме — `applied`; недоступное чтение после POST ПО ЛЮБОЙ причине (срок, провод, отказ, повреждённая форма, СЫРОЕ брошенное значение — включая отозванный Proxy — прямо на границе, которую потребляет исполнитель; `error.cause`/`error.timedOut`/`error.message` читаются безопасными обёртками, а не через `?.`) — `outcome: unknown` с названной причиной, журнал закрыт `unknown`, `recoveryRequired: true`, и разбираться обязан человек по тем же принципам, что в § 9б: ничего не откатывать и не повторять, фактический префикс установить чтением схемы, журнал и карточку сохранить неизменными, на неприменённый остаток — отдельная карточка и отдельное разрешение; повтора и отката в исполнителе нет (у транспорта только GET и POST);
- **недоступна ТОЛЬКО заключительная сверка** (четыре поля уже подтверждены поштучно свежими чтениями): это не обычная остановка. Журнал закрывается терминалом `pendingFinalWitness`, `recoveryRequired: true`, и вердикт выносится позже — `--verdict` читает НЕИЗМЕНЯЕМЫЙ журнал и берёт НОВОЕ живое свидетельство; ни одного нового POST и никакого отката (у вердикта нет транспорта записи). Если журнал закрыт `stopped`, `unknown` или подделан, вердикт отрицательный;
- **финальный gate** (`scripts/poi-schema/taxonomy-schema-gate.mjs`) — строгая грамматика журнала: ровно четыре поля в порядке карточки, намерение до каждого POST, исход `applied`, установленный чтением, `closed` с `allApplied` и четырьмя именами, ни одной лишней записи, привязка к точным байтам карточки и разрешения; **и** независимый свидетель по каноническому ID. Журнал из одних `opened` + `closed(allApplied, applied: [])` gate отвергает. `verifiedSuccess` — только «грамматика ∧ свидетель»; затем `npm run check:poi` без находок `taxonomy_schema_*`;
- **независимость свидетеля** (`taxonomy-schema-witness.mjs`) — свидетель не импортирует из исполнителя ничего: он читает живую схему СВОИМ ограниченным сроком чтением, САМ ПОЛНОСТЬЮ проверяет форму сырого ответа (`shapeProblem`) и классифицирует её СВОИМ кодом (`classifyWitness`), а не `assertQuartetState` исполнителя. Поэтому согласованная ошибка классификации исполнителя вердикта не проходит: свидетель считает другим кодом и расхождение видит;
- **каноническая область — до маршрута, credentials и сети** (10f-P R5, находка 2) — свидетель СНАЧАЛА проверяет карточку каноническим контрактом (`assertTaxonomySchemaCard`: база `apppwhjFN82N9zNqm`, таблица `POI_TABLE_ID`, четыре поля из loader), и только потом строит URL. Ни baseId, ни tableId, ни ожидаемые поля карточка переопределить не может: URL строится из КОНСТАНТЫ канонической базы, таблица ищется по КОНСТАНТЕ `POI_TABLE_ID`, а gate дополнительно требует у свидетеля именно каноническую таблицу. Карточка с валидными отпечатками модулей, но чужим baseId или чужим именем поля (bootstrap сверяет только модули) отвергается ДО единственного сетевого чтения — credentialed GET в чужую базу невозможен. В CLI та же каноническая проверка стоит ДО загрузки окружения и чтения токена;
- **ровно по одному разу, счётом а не Map/Set** (10f-P R4, находка 1) — свидетель считает вхождения: каноническая таблица по ID существует ровно один раз, каждое из четырёх полей — ровно один раз, ID полей уникальны, select-опции — список без повторов, равный опциям карточки как мультимножество. Второй, побайтно идентичный `POI Type` после корректного `allApplied` — не «пять полей приняты», а `ambiguous: true` и отказ: схлопнуть дубль нечем, потому что ничего не складывается в Map или Set. Повреждённая форма ответа — именованный отрицательный вердикт (`свидетель: ответ схемы повреждён: …`), не исключение;
- **gate не верит одному флагу** (10f-P R4, находка 1) — `finalGate`/`verdictFromJournal` независимо требуют у свидетеля отсутствие неоднозначности и РОВНО четыре уникальных непустых `fieldId`. Пять `fieldId` (лишнее идентичное поле), неоднозначная схема или подделанный `verifiedSuccess: true` при таких данных успеха не дают;
- **исключение после входа в границу POST** (10f-P R4, находка 2) — ЛЮБОЙ бросок `transport.createField` (отозванный Proxy, не-Error, `undefined`, объект с бросающим геттером) и любая нераспознанная форма ответа считаются потенциально неоднозначным эффектом: исполнитель безопасно описывает брошенное значение (`describeThrownSafely` — сам не бросает), помечает запись `sent` как `ambiguousEffect` и устанавливает исход ТОЛЬКО свежим ограниченным чтением — `applied`, если эффект произошёл; `notApplied` → `stopped`, если нет; `unknown` + `recoveryRequired`, если перечитать нельзя. Исключение из исполнителя не выходит, повтора POST и отката нет. Защита стоит и в транспорте (`createField` враждебного `fetchImpl` не выпускает исключение, только `ambiguous`), и в исполнителе, который на обещание транспорта не полагается.

**Что входит в проверяемое состояние.** Карточка называет это явно: `scope.verifiedProperties` — таблица (канонический ID и имя) и у каждого поля имя, тип и МНОЖЕСТВО опций-кодов (лишняя опция — расхождение). `scope.unverifiedProperties` — `description`: он посылается при создании как первичная документация, но в авторизованное состояние НЕ входит, потому что подпись правится в интерфейсе Airtable. Изменённый в базе `description` вердикт не роняет, и «точное совпадение» поля целиком нигде не обещается; изменённые опции — роняют.

Карточки R0 (`dbda92a8…`) и R1 (`11f68231…`) объявлены устаревшими (`tmp/*.OBSOLETE.md`); bootstrap отвергает их по составу модулей до импорта.

## 9. Что делать при сбое

**Транзакций и автоматического отката нет.** Airtable их не даёт, и мы их не эмулируем. `ingestPoiBatch()` — это цикл: он последовательно вызывает `ingestPoi()` на каждую строку. Один вызов batch-функции атомарности не означает.

Отсюда две принципиально разные зоны, и первое, что нужно установить при сбое, — в какой из них он произошёл.

### Зона A: сбой ДО начала записи — в базе ничего нет

Сюда попадают:

- preflight маршрута — каждая строка перепроверяется реестром;
- проверка покрытия файла имён;
- legacy-мост, когда тип не переводится в старое значение категории;
- проверка контракта источников внутри `ingestPoiBatch` — идентификаторы всех строк проверяются до снимка базы и до первой записи.

Все четыре срабатывают раньше, чем создаётся первая запись. Если сбой здесь — база не изменена, можно чинить причину и запускать заново.

### Зона B: сбой ПОСЛЕ начала записи — пакет записан частично

Как только цикл пошёл, каждая успешная строка — это уже созданная запись в Airtable. Падение на сотой означает, что первые девяносто девять могут быть в базе. Отката не будет: ни транзакции, ни компенсирующего удаления в системе нет.

Прогон при этом **не падает наружу**. Исключение из `writeRun` перехватывается: в отчёт кладётся `write: { error }`, файл `--out` пишется как обычно, код возврата остаётся нулевым. Нулевой выход коллектора не означает, что запись прошла.

Порядок действий:

1. **Не считать базу неизменённой.** Это главное. `write.error` говорит, на чём остановились, и ничего не говорит о том, сколько строк успело записаться до этого.
2. **Ничего не удалять автоматически.** Скрипта отката нет, и писать его на ходу нельзя: удаление POI не смотрит на входящие ссылки, и `Parent POI` с Route Stops оборвутся молча.
3. **Установить, что реально создано — по базе.** При таком сбое списка созданного в отчёте нет вовсе, поэтому источник истины один: Airtable. Признаки для выборки:
   - `Source Key` — по нему видно, какие строки пакета уже заведены;
   - `Intake Origin` — вид `portal-collector:<портал>`;
   - `Intake Run ID` — один на весь запуск, отсекает записи прошлых прогонов;
   - время создания записи.
4. **Сохранить отчёт `--out` и полный текст ошибки.** Отчёт даёт список `writable` — то, что уходило в запись. Это верхняя граница пострадавшего множества, а не список созданного.
5. **Перед повторным production-запуском сделать новый dry-run** — `--base-snapshot` против свежего снимка. База уже изменилась, и старый отчёт описывает не её.

### Про идемпотентность

Повторный запуск не создаст дублей уже заведённых портальных записей: `ingestPoi()` ищет запись по `Source Key` и возвращает `already_ingested`, ничего не создавая.

Это защищает **повтор**, но не превращает **первый** запуск в транзакцию. Частичный пакет остаётся частичным; идемпотентность лишь позволяет безопасно доехать до конца, а не откатить начало.

### Что показывает отчёт, а что нет

| Ситуация | Что лежит в `report.write` |
|---|---|
| запись дошла до конца | `outcomes` — счётчики по исходам; `created` и `notCreated` — поимённо |
| запись прервалась исключением | только `{ error }` — ни счётчиков, ни списков |

Даже в успешном случае списки не полны: `created` и `notCreated` обрезаны первыми ста строками, а `already_ingested` не попадает ни в один из них — он виден только счётчиком в `outcomes`. Отчёт годится, чтобы понять исход прогона; реестром созданных записей он не является. Реестр — база, выборка по `Intake Run ID`.

Удаление созданного идёт руками через интерфейс Airtable. Отдельный известный долг — см. `docs/poi-writers-registry.md`.

## 9а. Контролируемая L3-серия в живой Airtable

Для небольшой серии ручной канонизации сначала готовится карточка исполнения:

```text
точные record ID и поля
old → new для каждого поля
ожидаемые счётчики до и после
writer и ключ идемпотентности
порядок зависимых операций
сигнал частичного отказа
reconciliation query
rollback: есть / нет
post-write проверки
```

Предметное решение владельца не заменяет разрешение на эффект. Перед запуском карточка предъявляется целиком и получает отдельное недвусмысленное разрешение; неопределённый ответ не трактуется в пользу записи.

Разрешение связано с карточкой и её отпечатком, а не с устройством: сообщение владельца в том же авторизованном чате одинаково действительно с телефона и с компьютера. Локальный системный диалог macOS, песочницы или другого хоста — не повторное предметное разрешение, а технический допуск к исполнению команды.

До первого эффекта проверить не только writer, но и весь обязательный хвост: независимое чтение, финальный gate и production-проверки. У всех команд должны быть доступный хост, репозиторий, credentials, сеть и заранее понятный узкий системный допуск. Если обязательный постгейт потребует локального подтверждения, недоступного владельцу удалённо, writer пока не запускать.

Системное подтверждение ждут не более 60 секунд. Затем фиксируют `hostPermissionPending`, называют точную команду и прекращают ожидание. Разрешение карточки повторно не запрашивают. Если writer уже применил изменения, повторять его нельзя: после восстановления доступа продолжаются только независимая сверка и финальный gate по существующему журналу.

Порядок исполнения:

1. Повторить Git-preflight и свежий live-read. Проверить все `old`, отсутствие создаваемых стабильных ключей и ожидаемые исходы production dry-run. До этого шага writes = 0.
2. Запустить тот же production writer, который был исполнен в dry-run. Поля результата сравнить с одобренным предложением, а созданную запись сразу перечитать по ключу идемпотентности.
3. Перед каждым последующим update снова прочитать его `old`. После каждого эффекта перечитать изменённые поля и сохранить запись в append-only журнале фактически выполненного префикса.
4. Зависимые операции упорядочить fail-safe. При передаче единственного ресурса сначала создать и проверить нового потребителя, затем очищать старого. Это не транзакция, а уменьшение ущерба при остановке.
5. При первом расхождении или исключении остановить оставшийся хвост. Ничего не удалять и не «докатывать» без новой сверки и нового решения владельца.
6. После полного успеха независимо перечитать затронутые таблицы и проверить множества, уникальность ключей, ссылки и счётчики. Затем запустить затронутые живые гейты и полный `npm run verify`.

Проверочный скрипт обязан моделировать тот же вход, что production-потребитель. Integrity-guard, читающий поле, которого renderer не использует, создаёт ложную защиту. Мутационный runner сначала доказывает зелёность немутированного дерева в той же песочнице и с теми же зависимостями; падение на импорте или отсутствующем `node_modules` не считается убитой мутацией. Для убоя требуется именованное утверждение своей регрессии.

## 9б. Восстановление после прерванной L3-серии

Серия может оборваться не по ошибке данных, а по среде: процесс убит, соединение оборвано, вызов оболочки завершился. Порядок восстановления одинаков для всех этих случаев.

1. **Ничего не откатывать и не повторять.** Ни компенсирующего удаления, ни автоматического повтора хвоста.
2. **Установить фактический префикс чтением базы.** Журнал показывает, что исполнитель успел записать; истину даёт независимое чтение затронутых полей по каждой строке карточки. Расхождение журнала и базы — самостоятельный вывод, а не помеха.
3. **Сохранить исходные улики неизменными.** Исходный журнал `.ndjson` и исходная карточка не дописываются и не переписываются. Их дайджесты вносятся в список устаревших, чтобы повторный запуск по ним был отвергнут, а имя исходного журнала — в список запрещённых для новой серии.
4. **Собрать отдельную карточку восстановления** ровно на неприменённые строки: те же поля, свежие `old`, свой дайджест. Число строк выводится из карточки; фиксированного счётчика в исполнителе быть не должно.
5. **Перепривязать модули к новому дайджесту** и прогнать серию в режиме проверки. Только после этого карточка предъявляется владельцу на отдельное разрешение.

Сетевой транспорт серии обязан ограничивать операцию целиком, включая чтение тела ответа. Истёкший срок означает «исход неизвестен», а не «не записано»: строка остаётся кандидатом на проверку чтением, а не на повтор.

## 10. Канонизация Airtable перед новым импортом

Перед подключением cron и любой записью нового массового корпуса нужен свежий read-only baseline действующей базы. Он отделяет старый долг от результата нового прогона и даёт дедупу координаты и решения по составным объектам. Полный read-only discovery-обход можно выполнять параллельно: он Airtable не читает и не меняет.

Очереди не смешиваются: сначала связи Route Stops и редакционные статусы, затем кандидаты на дубль/`Parent POI`, затем координаты. Legacy-категории массово не заполняются до потребителя № 4 и утверждения новых полей taxonomy v2: старое поле выражает только часть реестра и закрепило бы переходную схему.

Полный порядок, стоп-условия и форма proposed mapping: `docs/poi-intake/airtable-canonicalization.md`.
