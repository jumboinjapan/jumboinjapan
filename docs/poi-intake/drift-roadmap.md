# Контроль дрейфа: порядок работ

Не календарный план и не цепочка. **Направленный ациклический граф зависимостей**: этап начинается, когда закрыты те и только те этапы и решения, без которых его нельзя сделать правильно, и заканчивается, когда выполнен его критерий, а не когда кончилось время. Номер этапа — имя, а не очередь: часть этапов идёт параллельно.

Зависимости целиком:

| Этап | Зависит от | Может идти параллельно с |
|---|---|---|
| 1а код возврата | ничего | всем |
| 1в fail-closed `--existing` | ничего | всем |
| 1б экспортёр снимка | решение по retention | 1а, 1в, 2-ядро, 4 |
| 1г ось `place_id` | решение владельца | всем остальным |
| 2-ядро манифеста | ничего | 1а, 1в, 4 |
| 2-снимок | 1б | — |
| 2-версия matcher policy | правило версионирования | 2-ядро |
| 2-сырой digest | решение по retention | 2-ядро |
| 3 baseline | 1а, 1б, 2-ядро, 2-снимок | 4 |
| 4 eval | ничего для classification; 3 для наполнения matching из живого прогона | 1, 2 |
| 5 pre-write gate и сравнение | 2-ядро, 3 | 4 |
| 6 calibration series | 2-ядро, 3, 5 | 4 |
| 7 вывод порогов | 6 | 8 |
| 7а проверка порогов | 7 | 8 |
| 8 shadow/challenger политики | 2-ядро, 4 | 6, 7, 7а |
| 9 пересмотр DDE | 5, 7а и измеренная стоимость | — |

**Ни один этап не начат.**

**Глобальной блокировки «сначала все решения владельца» нет.** Каждый подэтап блокируется только тем решением, без которого его нельзя сделать правильно. Часть работ этапа 1 не зависит от решений владельца вовсе.

Термины, слои, реакции и научные основания — в `docs/adr/0002-poi-drift-control-v1.md`. Здесь только порядок.

## Что внедряем, а что нет

| | Что | Почему так |
|---|---|---|
| **полностью** | манифест прогона с версиями, digest входного набора и контрактным fingerprint схемы | без него decision drift неотличим от нашей же правки |
| **полностью** | версия matcher policy | сегодня её нет вовсе; без неё нельзя сказать, изменились решения из-за источника или из-за нас |
| **полностью** | pre-write drift gate до `writeRun()` | сегодня сравнение прогонов считается после записи и допуском не является |
| **полностью** | точные структурные проверки как `BLOCK` | контракт нарушен — статистика не нужна |
| **полностью** | eval классификации и eval сопоставления | правило меняется по фикстуре, а не по примеру |
| **полностью** | ориентированный граф зависимостей сигналов | известен из кода, стоит дёшево; аудит раскрывается по транзитивному замыканию |
| **частично** | расширение `--monitor` | сравнение распределений и профиля добавляем; автоматических решений по результатам сравнения — нет |
| **частично** | хранение сырого входа | digest вычисляется всегда; сам payload хранится только там, где это разрешено retention-матрицей |
| **частично** | проактивные проверки | только для заранее известных изменений; всё остальное ловит реактивный гейт |
| **частично** | shadow/challenger | считается и показывается; продвижение — только решением владельца |
| **позже** | статистические пороги | выводятся на calibration series (этап 7) и проверяются на независимых прогонах (этап 7а) — это разные данные и разные этапы |
| **позже** | `REVIEW` → `BLOCK` для статистических сигналов | после калибровки и решения владельца |
| **не внедряем** | DDE с корреляцией признаков | граф зависимостей известен точно; статистическая оценка его не улучшает |
| **не внедряем** | ADWIN и детектор на каждое поле | нет непрерывного потока с обучением |
| **не внедряем** | online retraining, автоподстройка порогов, автоправка таксономии | политика меняется владельцем |
| **не внедряем** | LLM как автор и судья одновременно | не независимая проверка |
| **не внедряем** | отдельная база ради мониторинга | манифест — файл рядом с отчётом |

## Этап 0. Архитектура и решения владельца

- **Предотвращает:** реализацию контура, который придётся переделывать, потому что хранение данных окажется недопустимым, а пороги — назначенными автором документа.
- **Входит:** утверждение ADR-0002; ответы на вопросы §12.
- **Не входит:** любой код.
- **Зависимости:** нет.
- **Артефакт:** статус ADR меняется с «предложен» на принятый, ответы записаны в ADR.
- **Проверка:** чтение владельцем.
- **Меняет production-поведение:** нет.

**Этап 0 не блокирует всё разом.** Каждое решение блокирует только то, что без него нельзя сделать правильно:

| Решение §12 | Что блокирует | Что НЕ блокирует |
|---|---|---|
| retention-матрица | подэтап 1б (экспортёр пишет файл с координатами), хранение сырого payload в этапе 2, форму baseline в этапе 3 | подэтапы 1а и 1в, вычисление digest, весь этап 4 |
| override при отсутствии baseline | обязательность гейта в этапе 5 | сам расчёт вердикта и сравнение манифестов |
| риск ложного авто-совпадения | разметку спорных пар в matching eval (этап 4) | classification eval |
| кто утверждает baseline | завершение этапа 3 | этапы 1 и 2 |
| `REVIEW` → `BLOCK` и объём независимой проверки | завершение этапа 7а | этапы 6 и 7 |
| частота контрольного прогона, срок хранения манифестов | эксплуатацию после этапа 2 | внедрение этапа 2 |
| правило версии matcher policy | наполнение поля в манифесте | введение самого поля — оно обязательно |
| ось `place_id` | подэтап 1г и статус baseline | остальные подэтапы этапа 1 |

- **Критерий завершения этапа:** ADR принят; каждое решение либо закрыто, либо явно отложено с указанием, какие подэтапы оно держит.

## Этап 1. Закрытие блокеров достоверного прогона

- **Предотвращает:** прогон, который выглядит успешным и им не является.
- **Не входит:** сам контроль дрейфа; сетевой прогон Осаки.
- **Меняет production-поведение:** да, подэтапы 1а и 1в. Отдельными коммитами.

Четыре независимых подэтапа. Общего блокера у них нет.

| Подэтап | Что | Блокируется | Критерий завершения |
|---|---|---|---|
| **1а** | ненулевой код возврата при перехваченной ошибке прогона | ничем — правится сразу | прогон с перехваченной ошибкой портала или записи возвращает ненулевой код; тест исполняет обе ветки |
| **1б** | экспортёр снимка базы | решением по retention (§8.2 ADR): экспортёр пишет файл с координатами | снимок получен штатной командой и проходит контракт `base-snapshot` |
| **1в** | fail-closed `--existing` | ничем. Это **отдельный долг**, а не блокер команды с `--base-snapshot`: при снимке из файла путь `--existing` не участвует | нечитаемый или неверный файл роняет прогон, а не выключает сверку молча |
| **1г** | ось `place_id` | решением владельца | либо резолвер подключён и ось исполняется, либо ограничение **явно принято владельцем для конкретного baseline** и записано в его манифесте |

- **Проверка:** исполняющие тесты на каждую ветку; мутация каждого нового сторожа.

## Этап 2. `run-manifest/v1`

- **Предотвращает:** невозможность отличить дрейф источника от нашей собственной правки. Сегодня в отчёте нет ни версии таксономии, ни digest, ни версии matcher policy, ни fingerprint схемы.
- **Не входит:** сравнение манифестов между собой, пороги, реакции.
- **Проверка:** исполняющий тест на состав и на то, что версии берутся из канонических источников, а не переписаны рядом.
- **Меняет production-поведение:** нет — только добавляет файл.

Четыре части с разными зависимостями. Ядро реализуется независимо от всех решений владельца.

| Часть | Что входит | Зависит от | Критерий завершения |
|---|---|---|---|
| **2-ядро** | время, портал, режим, коммит коллектора, версия и digest таксономии, версия контракта приёма, контрактный fingerprint схемы, число строк и уникальных `sourceKey`, заполненность, распределения, причины остановок, длительность и стоимость, вердикт | **ничего** — всё берётся из кода и реестра | два прогона подряд дают манифесты, по которым видно, одинаковы ли версии политики |
| **2-снимок** | digest, возраст и покрытие снимка базы | подэтап 1б: пока снимка нет, поле нечем заполнять | манифест несёт digest снимка, совпадающий с фактическим файлом |
| **2-версия matcher policy** | поле версии политики матчера | решение владельца о правиле версионирования (ADR §12, решение 9). Само поле обязательно | поле есть и заполняется из единственного источника |
| **2-сырой digest** | digest сырого payload источника | решение по retention: вычисление и хранение | либо digest есть, либо в манифесте записано, что он запрещён, и указано, чем заменён |

Без частей 2-снимок, 2-версия и 2-сырой digest ядро остаётся полезным: оно уже отличает «политика та же» от «политика другая».

## Этап 3. Авторитетный baseline Осаки

- **Предотвращает:** сравнение с прогоном, про который никто не может сказать, чем он авторитетен. Сегодня сверка с baseline пропускается, если файла нет, а файл лежит в `tmp/`, которая не в репозитории.
- **Входит:** прогон на зафиксированном коммите, манифест, digest, запись в документации, кто и когда утвердил.
- **Не входит:** запись в Airtable.
- **Зависимости:** подэтапы 1а и 1б, части 2-ядро и 2-снимок. Подэтап 1г — либо закрыт, либо ограничение записано в манифесте этого baseline.
- **Артефакт:** baseline с манифестом, digest входного набора и digest снимка базы.
- **Проверка:** повтор **на сохранённом входе** даёт совпадающие агрегаты. Повторный сетевой запрос к порталу этого не проверяет и проверять не может: источник вправе измениться между запросами, и расхождение агрегатов тогда — не дефект прогона, а другой вход.
- **Критерий завершения:** владелец утвердил baseline; в каноническом документе записаны digest входного набора, версия способа канонизации и версии политики.
- **Меняет production-поведение:** нет.

### Два режима baseline

Режим определяется retention-матрицей, а не удобством. Смешивать их нельзя: они дают разные гарантии.

| | **replayable** | **observation-only** |
|---|---|---|
| условие | хранение входа разрешено | хранение входа запрещено; хранится только разрешённый digest |
| что сохранено | сырой payload или канонический набор кандидатов целиком, плюс все версии | digest, способ канонизации и его версия, идентификатор адаптера, дата и источник получения |
| что можно | пересчитать прогон на том же входе после правки кода; отделить «изменился вход» от «изменился код» экспериментом | сказать, тот же сегодня вход или другой |
| чего нельзя | — | пересчитать прогон; проверить, что правка кода не изменила исходы на старом входе |
| критерий завершения | повтор на сохранённом входе даёт совпадающие агрегаты при совпадающих версиях | digest, версии и происхождение записаны и подтверждены владельцем; в манифесте явно указан режим `observation-only` |

**В режиме `observation-only` offline replay не обещается ни в каком виде.** Расхождение агрегатов между прогонами в этом режиме не разделяется на «источник изменился» и «мы изменились» иначе, чем по версиям в манифесте: эксперимента, который бы это разделил, поставить не на чем.

Режим записывается в манифест baseline. Baseline без указанного режима считается неполным.

## Этап 4. Classification eval и matching eval

- **Предотвращает:** правку правил по единичному примеру.
- **Входит:** две фикстуры (ADR §9); matching eval с пятью классами, а не с бинарной меткой.
- **Не входит:** изменение самих правил.
- **Зависимости:** classification eval — ни от чего; matching eval — от этапа 3, если пары берутся из авторитетного прогона. Размеченные вручную пары можно готовить раньше.
- **Артефакт:** две фикстуры в репозитории.
- **Проверка:** прогон фикстур на текущих правилах; расхождения разобраны поимённо и объявлены известными.
- **Критерий завершения:** обе фикстуры непусты, исполняются в наборе тестов, и их падение **не пускает версию** — это release gate перед выкладкой изменения, а не проверка каждого портального прогона (ADR §5.2). Matching eval размечена двумя полями — `duplicateDecision` и `relationship` (ADR §9.2).
- **Меняет production-поведение:** нет.

## Этап 5. Расширение `--monitor`

- **Предотвращает:** незаметное изменение состава и решений. Сегодня сравниваются только часы, сайт и терминальный исход по каждой записи; распределений нет.
- **Входит:** сравнение профиля и распределений между манифестами; отдельный вывод по классам дрейфа; точные структурные расхождения как `BLOCK`; **перенос вердикта в pre-write gate** — он считается до `writeRun()`, а не после, как сегодня.
- **Не входит:** статистические пороги — на этом этапе статистика только показывается.
- **Зависимости:** 2-ядро манифеста и этап 3.
- **Артефакт:** раздел сравнения в манифесте; вердикт до записи.
- **Проверка:** исполняющий тест на паре подготовленных манифестов; **тест порядка с хранилищем, падающим на любом вызове** — при `BLOCK` до него не дошли; мутация «сравнение выключено» роняет набор.
- **Критерий завершения:** по двум манифестам видно, какой класс дрейфа сработал и на каком слое, **и** production-запись не проходит без успешного pre-write gate: отсутствие или ошибка обязательного baseline либо манифеста останавливает прогон до создания store. Аудируемый override владельца — только если владелец его разрешил (ADR §12, решение 6).
- **Меняет production-поведение:** да — `BLOCK` на структурных дефектах и обязательность гейта перед записью. Отдельными коммитами.

## Этап 6. Calibration series: накопление сопоставимых прогонов

- **Предотвращает:** назначение порогов по одному наблюдению.
- **Входит:** серия прогонов на неизменной политике с сохранением манифестов.
- **Не входит:** любые выводы о нормальности до конца серии; проверка порогов на этой же серии.
- **Зависимости:** 2-ядро манифеста, этапы 3 и 5.
- **Артефакт:** calibration series — набор манифестов с совпадающими версиями политики.
- **Проверка:** версии политики во всех манифестах серии совпадают — иначе это не серия, а смесь.
- **Критерий завершения:** серия набрана, различия между прогонами объяснены.
- **Меняет production-поведение:** нет.

## Этап 7. Вывод порогов на calibration series

- **Предотвращает:** числа, взятые из головы.
- **Входит:** пороги статистических сигналов, выведенные **только** из calibration series; правило пересмотра.
- **Не входит:** оценка качества этих порогов; любое их включение в реакции.
- **Зависимости:** этап 6.
- **Артефакт:** пороги-кандидаты с указанием, из какой серии получены.
- **Проверка:** у каждого порога записано происхождение.
- **Критерий завершения:** пороги-кандидаты выведены и зафиксированы.
- **Меняет production-поведение:** нет — пороги-кандидаты ни на что не влияют.

## Этап 7а. Независимая проверка порогов

- **Предотвращает:** самообман: **порог, выведенный и проверенный на одной серии, всегда выглядит хорошим**. Оценка на данных, из которых порог получен, качества не измеряет.
- **Входит:** shadow-прогоны или rolling validation на прогонах, **не входивших в calibration series**; отчёт о ложных `REVIEW` и ложных `BLOCK` — сколько раз порог сработал бы там, где всё было в порядке, и промолчал бы там, где нет.
- **Не входит:** включение порогов в реакции до решения владельца; автоматическая подстройка по результатам проверки.
- **Зависимости:** этап 7.
- **Артефакт:** отчёт о ложных срабатываниях на независимых прогонах.
- **Проверка:** прогоны проверки не пересекаются с calibration series — это проверяется по манифестам, а не по памяти.
- **Критерий завершения:** отчёт есть, владелец принял решение по каждому порогу. **Сколько прогонов должна занять проверка — открытое решение владельца**, здесь число не назначается.
- **Меняет production-поведение:** да, если владелец включает пороги в реакции. Отдельным коммитом.

## Этап 8. Shadow/challenger для политики

> Не путать с shadow-прогонами этапа 7а: там проверяются пороги на неизменной политике, здесь — новая политика на неизменных порогах.

- **Предотвращает:** выкладку новой политики без сравнения решений.
- **Входит:** параллельный счёт новой политики на тех же входах; расхождения в манифесте поимённо.
- **Не входит:** автоматическое продвижение; запись решениями challenger.
- **Зависимости:** этап 4 (обе фикстуры) и 2-ядро манифеста, плюс изолированный расчёт без пути записи. **От этапов 6, 7 и 7а не зависит**: challenger сравнивает решения политики с решениями действующей политики, статистические пороги ему для этого не нужны. Если challenger вводит собственные пороги — тогда и только тогда добавляется зависимость от 7а.
- **Артефакт:** раздел расхождений в манифесте.
- **Проверка:** тест на то, что решения challenger не доходят до пути записи.
- **Критерий завершения:** владелец может увидеть список расхождений и принять решение по каждому классу.
- **Меняет production-поведение:** нет, пока продвижения нет.

## Этап 9. Пересмотр необходимости DDE

- **Предотвращает:** внедрение метода не под задачу — и одновременно догматический отказ от него навсегда.
- **Входит:** проверка условия: выросло ли число наблюдаемых величин настолько, что наблюдать все стало дорого.
- **Не входит:** внедрение до выполнения условия.
- **Зависимости:** этапы 5 и 7а плюс измеренная стоимость наблюдения.
- **Артефакт:** запись решения в ADR.
- **Проверка:** измеренная стоимость, а не ощущение.
- **Критерий завершения:** решение принято и обосновано числами.
- **Меняет production-поведение:** нет.
