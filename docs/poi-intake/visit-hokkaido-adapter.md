# Адаптер Visit Hokkaido

Контракт работ, 14.09.2026. Статус: адаптер реализован; публичное чтение и офлайн-приём проверены. Массовый импорт не запускался.

Задача владельца: подключить японскую и английскую версии HOKKAIDO LOVE! к общему процессу POI. Японская версия — основная, английская дополняет сведения. Обе версии принадлежат одному издателю и не считаются независимыми подтверждениями.

## Граница

Адаптер обнаруживает карточки в двух каталогах `spot`, читает обе версии каждой карточки, сохраняет полную содержательную область статьи и выдаёт общий `poi-portal-intake/v1` вместе с материалами для исследователя. Стабильный ключ `visit-hokkaido:spot-<id>` не зависит от языка. Ссылки на маршруты и статьи сохраняются как связанные материалы; соседние места не становятся дочерними автоматически.

Не входят в эту работу: массовое создание записей, новая таксономия, новый писатель Airtable и публикация текстов. Последующие этапы используют общий Intake, поиск, проверку фактов, копирайтера и `poi:sync`, описанные в [общем процессе](cross-portal-operations.md).

## Ошибки, которые предотвращаем

- Пагинация или английская версия не должны исчезнуть из счётчиков. Неполный каталог прямо помечается неполным.
- HTTP 404/410 означает отсутствие версии; ошибка сети, редирект, повреждённая кодировка и смена шаблона означают отдельный отказ, а не отсутствие POI.
- Адрес, японское чтение имени, ссылки на официальные сайты и точки назначения карты доходят до поиска. Центр отображения карты координатой POI не считается.
- Абзацы, примечания, продолжения после `br`, подписи, таблицы и карты входят в материал исследования. Вспомогательный блок «рядом» хранится отдельно от статьи.
- Часы ресторана или магазина внутри комплекса не становятся часами всего комплекса. Сырые поля посещения требуют определения предмета и условий; неизвестные часы не означают круглосуточный доступ.
- Непроверенный материал и машинные подсказки не получают статус разрешённой записи. Каждому содержательному блоку исследователь назначает факт либо объяснение; копирайтер получает уже проверенное досье v2.

## Проверка и восстановление

Входы и весь список URL проверяются до сети. Каждый запрос учитывается до отправки, проходит актуальный robots, общий дедлайн и ограничение размера; редиректы не выполняются автоматически. Частичные результаты сохраняются с исходами по страницам. Повторный запуск создаёт новый каталог и не перезаписывает предыдущий.

Доказательства приёмки: положительные и отрицательные сценарии на синтетическом HTML, тесты подмены тождества и потери условий, мутации защит, чтение пяти реальных пар карточек, общий контракт Intake и непрерывный `npm run verify` с сохранённым кодом выхода. Полные тексты чужих страниц и рабочие доказательства остаются в `tmp/`, в git — код и синтетические фикстуры.

## Команды для следующего агента

Node 22. Новый каталог результата для каждого запуска; его родитель должен существовать. Команды чтения не загружают `.env.local`, не вызывают Google API, модель или Airtable.

```bash
# Оба каталога целиком. Не более 100 страниц на язык.
npm run poi:hokkaido -- discover tmp/hokkaido-catalogue

# Ограниченная проверка: одна страница каждого каталога; complete=false, exit 2.
npm run poi:hokkaido -- discover tmp/hokkaido-sample 1

# JSON-массив URL: одна ссылка на место, японская либо английская; 1–100 мест.
# Читатель всегда проверяет обе версии каждого выбранного места.
npm run poi:hokkaido -- read tmp/hokkaido-selection.json tmp/hokkaido-read

# Повторный разбор сохранённых байтов, без сети.
npm run poi:hokkaido -- replay tmp/hokkaido-read/bundle.json tmp/hokkaido-replay

# Общий коллектор: только обнаружение, без записи.
npm run poi:collect -- --portal visit-hokkaido --out tmp/hokkaido-discovery.json
```

`--limit` общего коллектора для этого адаптера отклоняется: количество мест не равно количеству страниц. Ограниченный обход задаётся явно второй командой. Старый `--monitor` Japan Guide имеет другую схему и также отклоняется до сети. Отсутствующая языковая версия допустима только после 404/410; любой иной отказ сохраняет место как `incomplete`.

| Артефакт | Содержание и назначение |
|---|---|
| `discovery.json` | Объединение обоих каталогов, количество и полнота по языкам, следующие страницы и причины остановки |
| `page-*.json` | Полученная страница либо отказ; исходный HTML при наличии, время и SHA-256 байтов |
| `bundle.json` | Страницы, исходы чтения и воспроизводимая проекция карточек; при повторном использовании проекция строится заново из HTML |
| `intake.json` | Общий `poi-portal-intake/v1`: имена, адрес, география и неподтверждённые подсказки |
| `evaluation.json` | Результат действующей общей оценки; это ещё не разрешение записи |
| `research.json` | Обе версии доказательства, сырые поля с предметом, который нужно определить, связанные материалы и незаполненный шаблон досье v2 |
| `run.json` / `code.json` | Граф исполняемого кода и зависимости; у чтения карточек также бюджет и нулевые эффекты Airtable/Google API/модели |
| `failure.json` | Ошибка выполнения и число уже сохранённых страниц; предыдущие файлы сохраняются |

Коды завершения специализированной команды: 0 — запрошенное чтение выполнено; 2 — неполный каталог или карточки с незавершённым чтением; 1 — ошибка входа или выполнения. `readyForWrite=false` означает, что исследователь и редактор ещё не подготовили материал для записи. Это не ошибка парсера.

## Как передавать материал дальше

1. Выбирать следующие места из объединённого каталога, исключая уже обработанные стабильные ключи. Язык не входит в ключ и не создаёт вторую карточку.
2. После `read` исследователь читает оба доказательства и извлекает собственные формулировки фактов. `research.json` — рабочий шаблон, а не принятое досье: пустые факты и неразобранные блоки не проходят проверку. Не копировать статьи в описания или Notes.
3. Для каждой строки практических сведений определить предмет: всё место, ресторан, музей, вход, отдельная услуга. В частности, поле часов Камуи описывает ресторан и магазин. Условия после переноса строки обязательны. Противоречия проверять по сайту оператора; язык страницы сам по себе не даёт ей приоритет актуальности.
4. Передать имена, полный адрес, муниципалитет и все `map_destination` в контекст опознания. Общий `resolvePlace` ищет по имени, муниципалитету и префектуре, используя точку как предпочтение; полный почтовый адрес сохраняется в доказательстве, но не добавляется в `textQuery`. Иначе Google может вернуть дом или район вместо места. Значение `publisherDestinationUnverified` — точка, указанная издателем; оно не заменяет опознание, Google Place ID или действующую политику координат. При разных точках наблюдаемая пара остаётся пустой, а `coordinate_conflict` сохраняет причину.
5. Проверить тождество через общий matcher. Новая карточка использует действующий `ingestPoi` с досье v2, доказательствами, оценкой предмета и редакторской приёмкой. Существующая — сравнение фактов и общий `poi:sync`; основной Source Key не переписывается. Адаптер не содержит альтернативного писателя или локального списка категорий.
6. Передать принятые факты [копирайтеру](poi-copywriter.md), затем отдельному редактору. Полный состав языковых источников и блоков сохраняется в досье. Блоки изображений и карт нельзя объявлять просмотренными только потому, что сохранена ссылка. Статьи и маршруты из `related` здесь не загружаются: агент читает нужные материалы отдельно и учитывает их бюджет.

Политика `source-policy/v1` используется здесь для доступа по robots. Её `allowedFacts` описывает старое структурное обогащение JA-3; состав нового доказательства задают `parsePortalEvidence` и этот адаптер по [общему процессу](cross-portal-operations.md). Разрешение обхода не разрешает перепубликовывать текст.

## Измеренный результат

Полный обход 14.09.2026: **809 японских и 636 английских карточек; объединение — 828 ключей**. В обоих каталогах — 617, только в японском — 192, только в английском — 19. Это состав каталогов, а не 828 новых POI: часть уже существует в нашей базе, а наличие карточки только в одном каталоге ещё не доказывает отсутствие второго перевода.

Пять пар для проверки: Упопой, канатная дорога Моива, Голубой пруд, канал Отару и мыс Камуи. Сохранены все десять страниц, адреса и ссылки карт, оговорки о погоде и бронировании, дополнительные сведения английской версии. Полный каталог: 73 страницы и один robots; карточки: десять страниц и один robots. Коммерческие API и живые записи в этих прогонах не использовались.

В тесте через настоящий `ingestPoi` и память сохранены Draft/Todo, классификация и досье с двумя источниками; повтор вернул `already_ingested` и `nextAction=compareFacts`. Отдельно проверено отсутствие автоматической подстановки часов ресторана. Это доказательство совместимости адаптера с ядром, а не отчёт о создании живых POI.

Рабочие логи и доказательства: `tmp/visit-hokkaido-adapter-2026-09-14/`. Основная регрессия: `node tests/poi-visit-hokkaido.mjs`, входит в `npm test`.

Все 59 исходов подтверждены независимым чтением. Два отдельных магазина

Итоги и строки: `tmp/visit-hokkaido-first100-2026-09-14/first100-result.json`
и `first100-result.md`; события очереди — `review-items.json`. Общий разбор
`/admin/poi-review` принимает ключи Visit Hokkaido, сохраняет комментарии
и помещает done/deferred в архив. Статус обсуждения не разрешает запись POI.

Полные официальные дополнения сохраняются компактно без потерь; правила
совместимости — в `cross-portal-operations.md`. Reader размещён до первой
записи компактного формата. Досье исторической деревни (10029) даже после
упаковки превышает предел: материалы и редакционная приёмка сохранены,
запись не выполнялась. Не усекать источники и историю ради объёма.

`poi:jg-intake --portal-batch FILE` подключает подготовленный Visit Hokkaido
к прежнему исполнителю создания. Историческое имя команды сохранено; новый
writer не добавлен. Файл `poi-portal-draft-batch/v1` содержит `portal`, исходный
`bundle`, подписанный `identification` и 1–25 строк `rows`. Строка содержит
`sourceKey`, `nameRu`, `siteCity`, модельное `proposal`, досье v2,
`evidence`, `subjectAssessment`, `copyReview`. Начало evidence точно совпадает
с обеими прочитанными версиями; далее допустимы официальные дополнения того же
предмета. Альтернативное имя поиска требует identity-факта с цитируемым блоком
источника. Состав строк точно совпадает с bundle и
опознанием; доказательства строятся заново из сохранённого HTML.

Проверяются источники, обе языковые версии, предмет фактов, текущая редакционная
приёмка, имя и адрес запроса поиска, классификация, качество и координаты.
Город, мутации схемы, журналы, дедуп, лимит создания и независимое чтение
остаются у общих функций. Имена источника не превращаются в метку human.
Подготовка находится в `lib/portal-draft-batch.mjs`, её единственный исполнитель —
`intake-japan-guide.mjs`. При добавлении следующего источника расширяется
подготовка входа; второй сетевой писатель не создаётся.

```bash
# Свежая база и репетиция: только чтение.
npm run poi:jg-intake -- --portal-batch tmp/hokkaido-ready.json --live-read
# Draft / Todo по постоянному решению VI, максимум 25 новых POI.
npm run poi:jg-intake -- --portal-batch tmp/hokkaido-ready.json --write
```

Известное место в результате Intake получает `compareFacts`: передавать его
в общий `poi:sync`, а не менять основной Source Key. Код подготовки не выполняет
sync автоматически. Итог первого прохода должен отдельно назвать созданные,
дополненные, существующие без изменений и незавершённые строки.
