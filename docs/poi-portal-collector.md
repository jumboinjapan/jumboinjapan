### 1.2. POI — автосбора нет

Четыре канала наполнения, все ручные: Telegram-агент по одной точке (`intakePoi`, OpenAI + web_search), правка в админке, прямой ввод в Airtable, хардкод в `intercity-pois.ts` (`routePoiIdsBySlug` — 12 маршрутов, ~50 пар «название остановки → POI ID» прямо в TypeScript).

**Два блокера, без снятия которых автосбор запускать нельзя:**

**Блокер 1 — у POI нет ключа источника.** У Resources есть `Source Key`, `Seed Source`, `Last Seeded At`, и на них держится вся дедупликация и обслуживание. У POI происхождение фиксируется прозой в свободном поле `Notes`. Следствие: повторный прогон коллектора создаст дубли, нельзя выбрать «все POI из источника X» для ревизии или отката, нельзя понять, когда точка сверялась последний раз.

**Блокер 2 — нет координат.** Ни широты/долготы, ни `place_id`. Поле `maps_link` объявлено в типе `Poi`, но не пишется и не читается. Это ломает и потребление (логистика дня, «что рядом»), и сам сбор: самый надёжный способ дедупа географических объектов недоступен, остаётся сравнение строк.

> Снят на 39% 9 августа 2026: 161 запись из 428 с координатами, 128 с `Wikidata QID`. Подробности и остаток — в статусе ниже.

Дополнительно: дедуп через двустороннее вхождение подстроки при пороге 3-4 символа (`findDuplicateCandidates`) — «Сад Кэнрокуэн» матчится с любым «Сад». Для пяти точек в день с человеком-читателем это приемлемо, для двух тысяч — нет. `findParentCandidate` при этом берёт **первое** совпадение без ранжирования и молча проставляет `Parent POI`.

Два несогласованных типа: `src/types/poi.ts` описывает 18 полей, из которых реально не пишется почти ничего; фактический контракт — `AirtablePoi` в `airtable.ts:26-38`.

## 2. Источники: что проверено 6 августа 2026

### Чего НЕ существует

- **Единой национальной открытой базы POI Японии нет.** 国土数値情報 (слои P12 観光資源, P33 集客施設) — данные **2014 года** и лицензия **非商用**: для коммерческого сайта закрыты юридически. P12 по Токио — 36 точек. Не использовать.
- **JNTO не отдаёт данные.** API нет, `japan.travel/robots.txt` запрещает обход `/*/travel-directory/*`. Русской версии больше нет — `japan.travel/ru/` отдаёт 401.
- **Google Places нельзя использовать для наполнения базы.** Maps Platform ToS §3.2.3(a) прямо запрещает «copy and save business names, addresses»; кэшировать разрешено **только координаты и только 30 дней**, `place_id` — бессрочно. Легальная модель одна: хранить `place_id`, всё остальное подтягивать в момент показа.
- `hakone-japan.com` не отвечает (connection reset), `fujisan-yamanashi.jp` не существует, `ishikawa-datapf.jp` — домен перехвачен спамом.

## 3. Ключевой вывод из прогона по реальным данным

Прототип прогнан по живым выгрузкам Осаки и Киото. Результат объясняет, почему «просто импортировать открытые данные» — плохая идея:

| | Осака | Киото |
|---|---|---|
| Записей в источнике | 2012 | 1631 |
| Прошло в `import` | **382** (19%) | **599** (37%) |
| В `review` (нужен человек) | 903 | 896 |
| Отбраковано | 727 | 136 |
| Категорию разобрали правила, бесплатно | 910 | 698 |
| Нужен LLM для категории | 444 | 810 |
| **Часы/цены протухли, публиковать нельзя** | 0 | **1289** |

Причины отбраковки Осаки: 104 средства размещения, 88 названий-событий (это фестивали, им место в событийном пайплайне), 22 продавца мастер-классов, 20 координат вне границ префектуры, 14 розничных точек, 10 муниципальных учреждений.

Покрытие полей Осаки, замерено: координаты — **48%**, японское описание — 99%, **английское название — 0%, часы работы — 0%** (колонки существуют, но пустые).

**Вывод: открытые данные дают объём и координаты, но не дают ни часов работы, ни качества отбора.** Слой скоринга — не украшение, а условие того, чтобы база осталась пригодной.

Отдельно про Киото: выгрузка датирована апрелем 2022. Название и координаты храма за четыре года не изменились, часы работы и цена билета — почти наверняка. Поэтому коллектор помечает эти поля `volatileFieldsUnverified` — импортировать можно, публиковать до сверки нельзя.

## 4. Архитектура

```
  РЕЕСТР ПОРТАЛОВ (registry.mjs)
  добавление источника = добавление записи, а не новый скрипт
         │
         ├── licence.commercial !== true → прогон пропускается
         ▼
  АДАПТЕРЫ                     один парсер на класс источников
    opendata-csv   ✅ готов    стандарт 自治体標準オープンデータセット
    jsonld         ○ следующий  sitemap + schema.org/Place
    sitemap-html   ○           обход с собственным селектором
    overpass       ○           OSM по административной области
    wikidata       ○           SPARQL, скелет идентичностей
         │
         ▼  общая форма кандидата
  СКОРИНГ (scoring.mjs)        чистая функция, без I/O
    блокеры ≠ баллы            import / review / reject
         │
         ▼
  ДЕДУП (dedupe.mjs)           3 ключа: sourceKey → координаты → имя
         │                     гаверсинус + триграммы вместо includes()
         ▼
  КАСКАД AI (enrich.mjs)
    0. правила      бесплатно  разбирают 45% категорий
    1. классификатор дёшево    только остаток, batch API
    2. извлечение    дёшево    часы/цены/транспорт → поля схемы
         │
         ▼
  ЧЕЛОВЕК                      корзина review, ничего не публикуется само
         │
         ▼
  3. РУССКИЙ ТЕКСТ  дорого     Claude по skill'ам проекта
```

Три принципа, унаследованные от событийного пайплайна:

1. **Скоринг — чистая функция.** Тестируется, переиспользуется, вызывается из админки для предпросмотра.
2. **Блокеры отделены от баллов.** Высокий балл не может протащить отель: `canAutoImport` требует одновременно отсутствия блокеров, порога, разобранной категории и координат.
3. **Каждое решение объяснимо.** Сигналы вида `positive:has_coords:2` пишутся в отчёт по каждой записи — на вопрос «почему эта точка не прошла» отвечаем без перезапуска.

### Урок первого прогона, вшитый в код

Первая версия скоринга пропустила в `import` аптеку `コクミンドラッグ 心斎橋筋１丁目店` и отель `OMO7大阪 by 星野リゾート`. У бизнес-листинга ровно тот же профиль сигналов, что у достопримечательности: координаты, описание, телефон, сайт, транспорт. Отличает их то, что объект не ложится ни в одну категорию канона.

Отсюда правило: **нераспознанная категория ограничивает решение потолком `review`**. После правки `import` = `autoImportable` = 382, расхождение исчезло.

Финальный русский текст — Claude по вашим skill'ам (`jj-title-copywriter`, `russian-naturalness-editor`), только по одобренным карточкам, порядка $0,02 за точку на Sonnet 5.

**Две срочные заметки по моделям:**
- `gpt-4.1-mini`, на котором сейчас работает `src/lib/poi-intake.ts`, **убран с прайс-листа OpenAI**. Модель в существующем агенте придётся менять независимо от этой задачи.
- Вводная цена Claude Sonnet 5 ($2/$10 вместо $3/$15) действует **до 31 августа 2026**. Если планируется массовый прогон текстов — выгоднее до конца месяца.

### Что нельзя отдавать модели

Механическая работа передаётся: классификация по категориям, нормализация форматов часов и цен, транслитерация, извлечение полей из японского текста, разметка дублей на проверку, суммаризация японского описания в факты.

**Не передаётся:** финальный русский текст на сайте, решение о публикации, проставление `Parent POI` (сегодня это делается молча по первому совпадению — так нельзя), утверждение часов работы объекта. По этим четырём пунктам ошибка модели попадает клиенту.

## 6. Мониторинг

Портал подключается не ради разового импорта, а ради регулярной сверки. Режим `--monitor` сравнивает прогон с предыдущим снимком и выдаёт три списка:

- **added** — новые объекты у источника
- **removed** — пропали из выгрузки, возможное закрытие
- **changed** — изменились часы, сайт или решение скоринга

Проверено на подготовленном расхождении: изменение часов и появление объекта детектируются корректно.

**Автоматически по результатам мониторинга не делается ничего.** Пропажа объекта из выгрузки — это чаще всего перестроение выгрузки, а не закрытие храма. Список идёт человеку.

Частота задаётся полем `cadence` в реестре: открытые данные — раз в месяц, порталы — раз в квартал, платная база (если подключим) — раз в неделю.

## 7. Дорожная карта

### Шаг 1. Схема Airtable — до всего остального

Без этого коллектор запускать нельзя, поэтому `--write` в прототипе намеренно выбрасывал ошибку.

> **Статус на 7 августа 2026.** Шаг 1 выполнен частично: поля `Source Key`, `Seed Source`, `Last Seeded At`, `Latitude`, `Longitude` в таблице заведены, запрет на запись снят, запись идёт через `ingestPoiBatch`. Флаги переименованы: репетиция — `--preview`, запись — `--apply` (прежние `--write` / `--dry-write` принимаются с предупреждением; у них был общий корень, и обрезанная команда превращала репетицию в запись).
>
> **Статус на 9 августа 2026.** Обратная засыпка координат сделана на треть: было 33 записи из 428, стало 161. Скрипт — `scripts/backfill-coords.mjs`, источник Wikidata. Заодно заведены `Name (JA)` (127 записей) и `Wikidata QID` (128). Геометрическая часть гейта теперь работает против 39% базы.
>
> Кандидат принимается автоматически, только если проходит **все** проверки сразу: одно совпадение имени, точка внутри рамки Японии, наша префектура встречается в цепочке `P131`, точка не дальше 25 км от медианы своего города. Медиана считается по самим кандидатам и во втором проходе — уже без выбросов. Плата за строгость известна поимённо: пара верных дальних точек уезжает на ручную проверку. Это правильная цена — отказ читают глазами, а принятие уходит в тур молча.
>
> **Google Places, тот же день.** Владелец завёл ключ через `/admin/integrations`, засыпка добавила ещё 146 записей. Итог: **307 из 417 несистемных записей с координатами (74%)**, 146 с `Google Place ID`, 128 с `Wikidata QID`, 127 с `Name (JA)`. Осталось 110.
>
> **Координата, полученная от Google, — это кэш, а не запись.** Условия Maps Platform разрешают хранить `place_id` бессрочно, всё остальное содержимое — не дольше тридцати дней. Поэтому вместе с координатой пишется `place_id`, а `npm run refresh:coords` раз в месяц перечитывает координаты по нему. Обновление идёт именно по `place_id`, а не поиском по имени: поиск каждый раз решает заново, какой объект имелся в виду, и однажды решит иначе — тихо, посреди ночного прогона. Сдвиг больше трёх километров не применяется молча, а выводится списком: это уже не уточнение геометрии, а признак того, что место переехало или срослось с другим.
>
> Отбор у Google тот же, что у Wikidata, и по той же причине — он почти всегда что-нибудь возвращает. На «Samurai Museum Tokyo» он уверенно отдаёт музей в Асакусе, тогда как наш объект в Кабуки-тё: Япония, Токио, музей самураев, всё сходится. Разводит их только то, что мы знаем сами. Добавилось одно правило сверх прежних: **имя сверяется и там, где геометрия уже сошлась**. Без этого «Numa-no-Daira Plateau» принял «Daisetsuzan National Park» — тот же Хоккайдо, 22 км от центра, обе геометрические проверки проходят; Google просто отдал объемлющий парк вместо плато.
>
> Города, где опорных точек не было вовсе, открываются постепенно: первая точка принимается по строгому правилу (префектура совпала, кандидат единственный, имя сходится) и становится опорой для остальных. Поэтому прогон идёт в три круга.
>
> **Уточнение владельца, тот же день: если у горы есть подъёмник, точка — станция подъёмника, а не вершина.** Причина деловая, а не географическая: у нас машина с гидом, и точка нужна та, куда машина подъезжает. Вершина как координата бесполезна — на неё не приедешь. Применено к трём горам: Сёся (станция канатной дороги вместо вершины), Хакодатэ (станция Санроку вместо смотровой наверху), Асахидакэ (станция канатной дороги вместо вершины из Wikidata).
>
> У Такао и Митакэ подъёмник оставлен на вершине намеренно: канатная дорога у обеих — **отдельная запись POI** (`POI-000361`, `POI-000364`), и перевод горы на ту же станцию создал бы двух POI с одним `place_id` — ровно тот дефект, что описан ниже. Правило «точка там, куда подъезжает машина» здесь уже выполнено, просто другой записью.
>
> **Правило владельца 10 августа 2026: точка горы — вершина.** У горы нет одной очевидной точки: подножие, станция подъёмника, вход на тропу, вершина. Берём то, что Google помечает типом `mountain_peak`, — проверено на Такао: 35.6254 / 139.2437 совпадает с известной вершиной до метров. Гора при этом может быть родительским POI для храмов и других объектов на ней; горный туризм — отдельная тема на будущее, в японских горах объектов много.
>
> Одна проверка на этом правиле сразу окупилась. На «Mount Iō» Google уверенно отдал вершину в Сирэтоко (44.13 / 145.16), а наша Иодзан — фумарольное поле у Кавайю-онсэна (43.61 / 144.44), в ста тридцати километрах. Совпадали и префектура, и тип объекта; разошлись бы молча. Опровергло только описание записи: «в двух шагах от парковки, без какого-либо подъёма» — то есть не вершина вовсе. Отсюда следствие для правила: у горы проверяем не только имя и тип, но и то, что говорит о ней наш собственный текст.
>
> **Правило владельца: если объект делит `place_id` с другим, координату лучше не ставить вовсе — но связь обязана остаться через `Parent POI`.** Пустая координата честна: она видна в отчётах, её закроют. Чужая координата не видна ничем и уводит машину не туда. Применено к «Горной деревне Митакэ»: Google на неё отдаёт то саму гору, то конкретный рёкан, поэтому координата и `place_id` сняты, а родителем поставлена гора Митакэ. Заодно проставлены родители у смотровой Омихарасидай и канатной дороги на Такао и у канатной дороги Такимото — теперь гора собирает вокруг себя свои объекты, как вы и описывали для будущего горного туризма.
>
> **Один `place_id` — один POI. Проверка обязательна.** Два разных объекта не могут быть одним местом в Google, и совпадение идентификаторов означает, что одна из записей опознана неверно. Геометрия этого не ловит: 10 августа «Мыс Сирэтоко» и «Водная прогулка Сирэтоко» получили один и тот же `place_id`, потому что в городе `shiretoko` не было опорных точек — первая запись стала опорой, а вторая прошла проверку расстоянием против самой себя. Две ошибки подтвердили друг друга. Скан всей базы нашёл три такие пары; две оказались настоящими дублями, третья — горой и деревней на ней.
>
> **Чего не хватает:** 110 записей. Из них 43 — «имя найденного не сходится», 41 — города без опоры с неоднозначным кандидатом, 13 — расхождение по префектуре (часто наша ошибка: Токийский Диснейленд стоит в Тибе). Разбор по причинам — `coords-review.html`.
>
> Два случая, где все проверки проходят, а опознание неверное: Wikidata подставляет **станцию** вместо самого объекта (`Kawayu Onsen` → 川湯温泉駅, `Kasai Rinkai Koen` → 葛西臨海公園駅). Координаты при этом в пределах километра от верных, то есть геометрия такую подмену не ловит в принципе. Ловится суффиксом японской метки — то же правило разводит квартал, его станцию, мост и историческое село того же имени.

Добавить в таблицу POI:

| Поле | Тип | Зачем |
|---|---|---|
| `Source Key` | singleLineText | Идемпотентность повторного прогона. Формат `<portalId>:<id>` |
| `Seed Source` | singleLineText | Выборка «всё из источника X» для ревизии и отката |
| `Last Seeded At` | dateTime | Когда запись пришла |
| `Source Checked At` | dateTime | Когда факты сверялись последний раз |
| `Latitude` / `Longitude` | number (7 знаков) | Дедуп по расстоянию, логистика, «что рядом» |
| `Source URL` | url | Куда идти проверять |
| `Data Licence` | singleSelect | `CC BY 4.0` / `ODbL` / `contract` — атрибуция обязательна по лицензии |
| `Volatile Fields Verified` | checkbox | Часы и цены сверены человеком. Без галочки не публикуются |

Заодно снять две мины, найденные при разборе:
- `getPoisByCity` и `getPoisByIds` подставляют значение в `filterByFormula` **без экранирования апострофа** (в `getRouteStopsByIds` экранирование есть — про проблему знают, применили в одном месте из трёх).
- `getNextPoiId` читает максимум и делает +1 в памяти: два параллельных интейка дают коллизию `POI ID`.

### Шаг 2. Разрезать `intakePoi`

`intakePoi` первой строкой вызывает `researchPoi`, дальше вся оркестрация работает только с объектом `PoiResearchResult`. Расщепить на `intakePoi(input)` и `intakePoiFromResearch(research)` — правка в одну строку, после которой **любой** источник, приведённый к `PoiResearchResult`, проходит остаток пайплайна без изменений. Это главный шов архитектуры.

Заодно: `createPoiRecord` и `createStubPoi` сделать экспортируемыми и перевести на батч по 10 записей (лимит Airtable), как уже сделано в `fix-poi-typos.mjs`.

### Шаг 3. Обкатать на Осаке

Прогнать коллектор с `--existing` (текущий дамп POI), проверить корзину `review` глазами на 50 записях, подстроить пороги. Осака выбрана потому, что это маршрутный регион с самой свежей выгрузкой (март 2026).

### Шаг 4. Подключить ступени 1-2 каскада

Batch API, strict JSON schema. Начать с Gemini 2.5 Flash-Lite; если возня с валидацией окажется дороже разницы в цене — перейти на gpt-5.6-luna.

### Шаг 5. Адаптер `jsonld`

Обкатывать на `dive-hiroshima.com` — там `Place` + `GeoCoordinates` в разметке, парсер проверяется на эталоне. Затем `osaka-info.jp` ради структурированных часов.

**Юридическая оговорка:** у обоих порталов лицензия проприетарная, поэтому в реестре они помечены `commercial: false` и коллектор их пропускает. Использовать их как источник **сверки фактов** (часы, адрес) для уже существующих POI — другой правовой режим, чем копирование текста. Прежде чем включать — решить вопрос прав.

### Шаг 6. Слой скелета: Wikidata + OSM

Wikidata (CC0) даёт стабильные QID как якорь идентичности между источниками. OSM даёт плотность и координаты — 78 тысяч святилищ и храмов, больше любого государственного реестра.

**Про ODbL:** пока база внутренняя и наружу идёт только вёрстка страниц с атрибуцией «© OpenStreetMap contributors» — обязательств нет. Публикация самой базы или передача третьим лицам потребует открыть её под ODbL.

Для регулярной работы брать дампы Geofabrik, а не Overpass API — последний жёстко режет частоту.

### Шаг 7. Cron

Только когда прогон устоялся. Отдельная таблица прогонов в Airtable вместо `console.error` — сейчас персистентного лога нет ни у событий, ни у POI.

### Параллельно: минимальная починка событий

Не связано с POI технически, но два пункта того же дня работы:
- `archiveEndedJapanTravelEvents` в cron с `--write`, иначе протухшие висят активными.
- Убрать дыру в `getAllEvents:149-155`: если протухли все события, показывать пустой список, а не все протухшие.

## 8. Что в прототипе

```
scripts/poi-portals/
  registry.mjs            реестр порталов, 10 записей, все проверены 06.08.2026
  collect-pois.mjs        CLI, dry-run по умолчанию, режим --monitor
  lib/
    opendata-csv.mjs      адаптер 自治体標準オープンデータセット с алиасами колонок
    scoring.mjs           чистая функция оценки кандидата
    dedupe.mjs            гаверсинус + триграммное сходство
    enrich.mjs            каскад AI и расчёт стоимости по факту
```

Почему алиасы колонок, а не фиксированные имена: Осака отдаёт 58 колонок с адресом в `所在地_連結表記` и **полуширинными** скобками в `料金(基本)`; Киото — 32 колонки с адресом в `住所` и **полноширинными** скобками в `料金（基本）`. Один парсер закрывает обе префектуры и всех остальных, кто следует тому же стандарту.

Запуск:

```bash
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --out tmp/osaka.json
node scripts/poi-portals/collect-pois.mjs --portal bodik-kyoto-tourism --limit 300
node scripts/poi-portals/collect-pois.mjs --portal bodik-osaka-tourism --monitor tmp/osaka.json
```

Зависимость: `csv-parse` (в проекте пока нет, `npm i csv-parse`).

Запись: `--preview` — полный прогон против живой базы без создания записей,
`--apply` — запись. По умолчанию не пишется ничего.

## 9. Атрибуция

Лицензии требуют указания источника на страницах, использующих данные:

- BODIK / открытые данные префектур — CC BY 4.0: «大阪府», «京都府»
- OpenStreetMap — ODbL: «© OpenStreetMap contributors»
- 国指定文化財等データベース — свободно с указанием источника
- Wikidata — CC0, атрибуция не требуется

Поле `Data Licence` в схеме POI нужно именно для того, чтобы страница знала, что подписать.
