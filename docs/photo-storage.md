# Как устроено хранение фото

**Контракт показа на сайте от 2026-07-24; уточнение архива 2026-09-22.**
Для любой работы с архивом, ID и приёмом фотографий сначала читать
[photo-management.md](photo-management.md). Dropbox-библиотека уже создана и проверена.
Её подключение не меняло пути сайта. CLI приёма и схема медиатаблиц реализованы; подключение Dropbox API и живой пилот
ещё не выполнены: [photo-intake.md](photo-intake.md). Фоновый приём из чата и Vercel Blob/CDN не подключены. RFC от 2026-07-24 описывает историю решения.

## Три правила, которые нельзя нарушать

1. **Файлы для показа на сайте — в `public/` этого репо.** Архивные варианты также хранятся в Dropbox по отдельному реестру; Dropbox не служит источником загрузки картинок на страницах. Airtable хранит путь-строку, не двоичное вложение. Отдельный CDN для изображений этим этапом не подключён.
2. **У каждого изображения ровно один источник правды пути** (см. таблицу ниже). Дублировать путь во втором месте запрещено — так возникал тихий дрейф (инциденты «Мэйдзи/Сибаматы», «Сибуя 2026-07-24»: правка кода была no-op, потому что Airtable молча перекрывал).
3. **Замена содержимого = новое имя файла** (`-v2`, `-v3`, …). Кэш оптимизатора картинок Vercel ключуется по URL: перезапись байтов под старым именем показывает старый кадр непредсказуемо долго. Перезаписывать байты под тем же путём запрещено.

## Карта источников правды

| Поверхность | Источник пути | Где именно |
|---|---|---|
| Фото остановок city-tour (day-one/day-two/hidden-spots) | **Airtable** | `Route Stops`.«Photo Path» / «Photo Alt» |
| Фото POI-остановок intercity | **Airtable** (тот же контракт) | `Route Stops`.«Photo Path» (сегодня заполнено только у city-tour; кодовый seed Хаконе в `intercity-pois.ts` — унаследованное исключение, мигрировать при случае) |
| Hero многодневных маршрутов | **Airtable** | `Routes`.«Hero Image Path» (пусто → дефолтная обложка раздела) |
| Hero статических страниц (intercity/<slug>, city-tour/*, транспортные) | **Код** | `page.tsx` → `<PageHero image=…>` |
| Карточки, OG, JSON-LD | **Код** | `src/data/tours.ts`, `page.tsx` metadata |

Кодовых `photo:`/`alt:` в `stops[]` городских страниц больше НЕТ. Fallback при недоступности Airtable — `src/data/route-stop-photos.generated.json`: генерируется `npm run sync:photo-fallback`, руками не редактируется, источником правды не является.

## Раскладка и именование `public/`

```
/tours/<раздел>/<объект-съёмки>[-vN].jpg
```

- `<раздел>` — направление, не поверхность показа: `city-tour` (все городские точки Токио — одна папка), `fuji`, `hakone`, … `multi-day`.
- `<объект-съёмки>` — что на кадре, kebab-латиницей: `shibuya-hachiko.jpg`, `harajuku-takeshita.jpg`. Никаких `photo1.jpg`, `image.webp`, `img_1234.jpg`.
- Новые файлы через Intake экспортируются в `public/tours/photo-library/<assetId>__<subject>__<width>x<height>__<hash>.webp`. Хеш в имени создаёт новый URL для новых байтов; старые URL не переименовываются.
- Это структура файлов для сайта. Действующий Dropbox-архив организован по постоянным ID: `photo-library/assets/IMG-…/`; его реестр сохраняет прежние пути и места использования. Зеркало `site/` из старой спеки не является текущим устройством архива.

## Контроль целостности

`npm run check:images` (`scripts/check-image-refs.mjs`) сверяет файлы `public/` ↔ пути в коде/скриптах/generated-JSON ↔ пути в Airtable. Битая ссылка → exit 1 (гейт для CI). Сироты, дубли по SHA-1 и кросс-папочные ссылки — warning. **Гонять перед каждым коммитом, трогающим фото.** Сирот определять только валидатором, не `grep` по src (ссылка может жить в Airtable).

## Процесс замены/добавления фото остановки

1. Положить файл в `public/tours/<раздел>/<объект>.jpg` (новое имя!), закоммитить, задеплоить.
2. Прописать путь в Airtable `Route Stops`.«Photo Path» (+ «Photo Alt») — только после деплоя файла.
3. Нажать «Обновить кэш сайта» в админке (Route Texts) — прямые правки Airtable не сбрасывают ISR (иначе ждать до часа).
4. `npm run sync:photo-fallback` и закоммитить обновлённый снапшот.
5. `npm run check:images` — убедиться: 0 битых. Отсутствие ссылок означает кандидата на отдельный разбор, а не разрешение на удаление; проверить другие назначения и окружения. Архивирование и замена фото не включают автоматическую очистку исходников.

Порядок «файл раньше пути» обязателен: Airtable читается лайвом немедленно, файл появляется только с деплоем.

## Миграция 2026-07-24 (переходное состояние)

Исторический план ниже не является командой к повторному запуску. Перед продолжением
сверять нынешние данные, код и деплой; перенос в Dropbox 2026-09-22 эту миграцию не выполнял.

Ветка `fix/photo-architecture-2026-07-24` добавила канонические копии в `tours/city-tour/`, но лайв-Airtable ещё указывает на старые пути. После деплоя ветки на прод:

1. `node scripts/migrate-photo-paths-2026-07-24.mjs` (dry-run) → `--write` — переключает 14 записей Route Stops на новые пути (+ Сибуя получает кадр Хатико и новый alt).
2. «Обновить кэш сайта» в админке.
3. `npm run sync:photo-fallback` + коммит.
4. Cleanup-коммит: удалить старые папки `tours/city-tour-day-one|day-two|hidden-spots` (валидатор покажет их сиротами) и сам migrate-скрипт.

## Открытые хвосты на момент решения 2026-07-24

Исторический список. Перед новой задачей проверять текущую ветку и данные;
совпадения файлов и назначения ниже не являются результатом свежей проверки.

- Такао/Митакэ: остановки сознательно без фото (раньше стояли чужие кадры с ложными alt). Нужны реальные кадры от владельца; класть по канону и прописывать в Airtable (записей Route Stops для этих маршрутов пока нет — фото задаются только через будущие записи или код-хиро).
- Hero-файлы Такао/Митакэ (`/hero-city-tour-takao|mitake.jpg`) не существуют; hero и OG обеих страниц временно используют hero day-one.
- `dest-intercity.jpg` == `tours/kamakura/kamakura-2.jpg` по байтам (оба живые, два URL) — можно унифицировать при следующей правке intercity-метаданных.
- Кодовый seed фото Хаконе в `src/lib/intercity-pois.ts` (2 пути) — перенести в Airtable Photo Path тем же процессом, что выше.
