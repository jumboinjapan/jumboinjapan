# Как устроено хранение фото сайта

Актуализировано 25.09.2026. Этот документ описывает выдачу фотографий сайтом,
а не учёт оригиналов в фотоархиве.

## Архив и сайт

Оригиналы и варианты учитываются в Dropbox `photo-library`: текущий
`catalog/registry.json` определяет идентификаторы и пути архива. Подключение
Dropbox и первый импорт уже проверены. Порядок работы начинается с общего
руководства `/Users/jumbo/Projects/jumboinjapan/docs/photo-management.md`.
Новый CLI Intake и его инструкция находятся в отдельной ветке `codex/photo-intake`,
в `/Users/jumbo/Projects/jumboinjapan-photo-intake/docs/photo-intake.md`.
Наличие архива не означает автоматическую публикацию фотографии на сайте.

Сайт продолжает выдавать свои версии из `public/` через Next Image.
Отдельный CDN и автоматическая загрузка вложений из чата не подключены.

## Источники путей

| Поверхность | Источник |
|---|---|
| Фотографии остановок | Airtable `Route Stops`: `Photo Path`, `Photo Alt` |
| Резервные фотографии остановок | `src/data/route-stop-photos.generated.json`, генерируемый `npm run sync:photo-fallback` |
| Обложки маршрутов | Поля `Routes` там, где страница применяет override; кодовые обложки остаются резервом |
| Статические обложки, карточки, OG и JSON-LD | Код страниц и `src/data/tours.ts`; потребители каталога могут применять поля `Routes` |

Фото остановок подключены также у загородных маршрутов. Утверждение, что
они есть только у трёх токийских туров, устарело. У Такао уже есть собственная
обложка и фотографии остановок; общий резерв обложки задан в
`src/data/route-hero-images.ts`.

Единого реестра всех обложек пока нет. Перед заменой нужно проследить источник
конкретной поверхности и её override: правка резервного пути не заменит
непустое поле Airtable. Generated JSON не редактируют вручную.

## Правила публикации

1. Новые байты получают новый URL: версию имени или имя с хешем. Не заменять
   содержимое файла под старым URL из-за кэша оптимизатора.
2. Веб-файл сначала публикуют из `public/`, проверяют его доступность,
   затем назначают путь в Airtable. Оригинал остаётся в архиве.
3. После назначения обновляют кэш через админку и снимок командой
   `npm run sync:photo-fallback`.
4. `npm run check:images` проверяет пути в коде, снимке и Airtable.
   Отсутствующий файл — ошибка; сироты и дубли требуют отдельного разбора.

Существующие адреса сохраняют. Для новых файлов применяют содержательные имена
в `public/tours/<направление>/` либо имя варианта фотоархива в
`public/tours/photo-library/`. Пометка «сирота» сама по себе не разрешает удаление:
необходимо проверить назначения и внешние ссылки.

## Исторические миграции

Июльская инструкция переноса путей больше не является очередью работ.
Скрипт сохранён как [неисполняемый снимок](archive/scripts/README.md).
Его нельзя повторно запускать по старому списку записей. Любой новый перенос
требует свежей проверки назначений и отдельного плана.

Техническая очистка пакета 1 не меняет фотографии, их назначения или реестр.
