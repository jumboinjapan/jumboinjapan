## Сводка

Данные в неплохом состоянии: иерархия `Parent POI` чиста — ни висячих ссылок, ни самоссылок, ни циклов. Флаг `Is System` стоит ровно на тех 11 служебных записях (трансферы, заселение), у которых нет города. Инвалидация кэша по тегу `airtable:pois` разведена и работает.

Проблемы — в трёх местах: одна ошибка уже видна на сайте, одна группа сработает при ближайшей же работе со слиянием дублей, остальное — механизмы, которые пока не выстрелили по везению.

## 1. Уже сломано на живом сайте

### Остановка «Морская свеча» тянет данные Сада Кокинга

На странице `intercity/enoshima` две остановки указывают на один и тот же POI:

| Остановка | Снимок имени | POI ID |
|---|---|---|
| RST-ENOSHIMA-02 | Сад Самюэля Кокинга | POI-000016 |
| **RST-ENOSHIMA-03** | **Смотровая башня «Морская свеча»** | **POI-000016** ← неверно |

Третья остановка показывает описание, часы работы и сайт ботанического сада под заголовком смотровой башни. В базе есть отдельная запись **POI-000263 «Маяк "Морская свеча"»** — на неё и должна ссылаться остановка.

Правится одним полем в Airtable: `Route Stops` → RST-ENOSHIMA-03 → `POI ID` = `POI-000263`. Заодно обновить `POI Name Snapshot`.

## 2. Сломается при слиянии дублей

Это самое важное, потому что вы как раз собираетесь разбирать очередь дублей.

**Три независимых способа сослаться на POI, и ни один не защищён:**

1. **`Route Stops.POI ID` — обычный текст**, не связь между таблицами (`singleLineText`). Airtable не помешает удалить POI, на который ссылаются.
2. **`deleteAirtablePoi`** (`src/lib/airtable.ts:329`) удаляет запись, **не проверяя ссылок вообще** — ни на Route Stops, ни на Parent POI, ни на Tickets.
3. **50 POI ID вшиты прямо в TypeScript** — `routePoiIdsBySlug` в `src/lib/intercity-pois.ts`. Их не видит ни Airtable, ни любая проверка внутри базы.

Итог: удалили не ту половину дубля — страница молча теряет описание, часы и фото точки. Ошибки не будет, будет пустое место.

### Какие дубли задействованы на живых страницах

Проверено пересечением очереди дублей с Route Stops и хардкодом. **Во всех семи парах «правильная» половина — та, на которую есть ссылки. Оставлять надо её.**

| Оставить (есть ссылки) | Удалить (ссылок нет) |
|---|---|
| POI-000182 Замок Осака | POI-000343 Osaka Culturarium at Tempozan |
| POI-000200 Храм Тодайдзи | POI-000252 Храм Тосёдайдзи *(разные объекты — не сливать)* |
| **POI-000239 Пятая станция линии Фудзи-Субару** | **POI-000160 Пятая станция Фудзи** |
| POI-000210 Квартал Хигаси Тяя | POI-000215 Квартал Ниси Тяя *(разные — не сливать)* |
| POI-000212 Музей современного искусства 21 века | POI-000446 Музей MonET *(разные — не сливать)* |
| POI-000124 Храм Рёандзи | POI-000049 Храм Тёандзи *(разные — не сливать)* |

Реально сливать здесь нужно только пару Фудзи. Остальные — ложные срабатывания матчера, но список важен: он показывает, какие ID трогать нельзя.

Подтверждённые дубли из очереди (Небута 521/383, Сендай 504/469, Масю 488/400) **ссылками не задействованы** — их можно сливать свободно.

### Что предусмотреть

- Перед удалением POI проверять ссылки: Route Stops, Parent POI, Tickets, `routePoiIdsBySlug`. Сейчас это делает `npm run check:poi` постфактум — лучше встроить в сам путь удаления.
- Долгосрочно: перевести `Route Stops.POI ID` в настоящую связь (`multipleRecordLinks`). Тогда Airtable сам не даст удалить используемую запись, и денормализованный `POI Name Snapshot` перестанет расходиться.
- Завершить миграцию `routePoiIdsBySlug` в Airtable. Комментарий в `intercity-pois.ts:288` фиксирует, что она начата и не закончена; `getIntercityRouteSeed` бросает исключение для всех слагов кроме `hakone`.

## 3. Механизмы, которые пока не выстрелили

### Copy Status не участвует в публикации

Редакционный конвейер `Draft → Review → Approved → Synced` существует в схеме, но **на отбор к публикации не влияет никак**:

- публичные выборки фильтруют только `NOT({Is System})` (`airtable.ts:229, 263`) — Copy Status в формуле нет;
- страница рендерит `poi.approvedRu || poi.descriptionRu` (`intercity-pois.ts:255`), то есть **`Description Approved (RU)` показывается первым, независимо от статуса**.

Значит текст становится публичным в момент заполнения поля Approved, а не в момент синхронизации. Шаг Sync ничего не охраняет.

Сейчас в базе **81 запись с заполненным Approved-текстом вне статусов Approved/Synced**. На живых маршрутах из них не стоит ни одна — но это стечение обстоятельств, а не защита: достаточно поставить такую точку в маршрут.

**Предусмотреть:** добавить `Copy Status` в условие отбора публичных выборок, либо рендерить `approvedRu` только при статусе `Approved`/`Synced`.

### Подстановка в формулу без экранирования

`getPoisByCity` (`airtable.ts:229`), `getPoisByIds` (`:251`) и запрос по `{CITY ID}` (`:206`) подставляют значение в `filterByFormula` напрямую. В `getRouteStopsByIds` (`:487`) экранирование апострофа есть — про проблему знают, применили в одном месте из трёх.

Пока значения приходят из ваших же слагов, это неопасно. Как только слаг придёт из внешнего источника или из формы — сломается формула, а вернётся пустой список, то есть страница без точек.

### Гонка при выдаче POI ID

`getNextPoiId` (`poi-intake.ts:181`) читает максимум и прибавляет единицу в памяти. Два одновременных интейка выдадут один и тот же `POI-XXXXXX`. Для Telegram-бота с одним пользователем терпимо; для пакетного сбора — нет. Пакетный путь (`collect-pois.mjs`) поэтому и не имеет `--write`.

### Telegram-агент не сбрасывает кэш

`intakePoi` пишет в Airtable напрямую и `revalidateTag('airtable:pois')` не вызывает — в отличие от админских маршрутов. Новая точка не появится на сайте до истечения часового окна ISR. Не поломка, но объясняет «я завёл, а его нет».

### `Site City` без справочника

Свободная строка, при этом единственный ключ связи POI с городом. Проверки против таблицы `Locations/Cities` нет ни при записи, ни при чтении. Отсюда и дробление слагов — см. ниже.

## 5. Что добавлено в проект

`scripts/check-poi-integrity.mjs` — все десять проверок одним прогоном.

```bash
npm run check:poi           # проверить живую базу
npm run check:poi -- --json # машиночитаемый отчёт
```

Код выхода `1` при находке уровня ПОЛОМКА, `0` при уровне «внимание». Годится для запуска перед деплоем или по расписанию.

Проверки:

1. остановка ссылается на удалённый POI
2. две остановки маршрута указывают на один POI
3. дубли в базе — тем же матчером, что и на входе
4. неутверждённый текст стоит в живом маршруте
5. точка маршрута без описания
6. снимок имени разошёлся с базой
7. остановка не привязана к POI
8. иерархия: висячие ссылки, самоссылки, циклы
9. слаги городов: кириллица и дробление
10. полнота: город, категория, статус

Проверка дублей использует `src/lib/poi-matching.ts` — тот же модуль, что стоит на входе. Гейт не защищает от того, что было заведено до него, поэтому проверка задним числом нужна отдельно.

## 6. Порядок работ

**Сегодня, десять минут:**
1. Исправить RST-ENOSHIMA-03 → POI-000263. Это единственная ошибка, видимая клиенту прямо сейчас.
2. Заменить слаг `Кирю` на `kiryu` (2 записи).

**Перед разбором очереди дублей:**
3. Прогнать `npm run check:poi` и держать таблицу из раздела 2 под рукой: при слиянии оставлять ID со ссылками.
4. Свести слаги Фудзи к одному.

**Следующим заходом в код:**
5. Добавить `Copy Status` в отбор публичных выборок — иначе шаг Sync остаётся декоративным.
6. Экранировать значения в `filterByFormula` в трёх оставшихся местах.
7. Проверять ссылки перед удалением POI.
8. Вызывать `revalidateTag('airtable:pois')` после интейка из Telegram.

**Когда дойдут руки:**
9. Перевести `Route Stops.POI ID` в настоящую связь между таблицами.
10. Довести миграцию `routePoiIdsBySlug` из TypeScript в Airtable.
11. Привязать 8 остановок `city-tour` к POI.
12. Выдавать `POI ID` без гонки — либо через отдельный счётчик, либо диапазоном на прогон.
